# KV Cache

## 是什么

KV Cache 是大模型推理中缓存 Attention 计算中间结果的机制，目的是避免 Decode 阶段对历史 token 的重复计算。

---

## 为什么需要

LLM 生成文本是**自回归**的：每次只生成一个 token，把它拼到已有序列后面，再生成下一个。

```
输入：  "今天天气"
生成1：  "今天天气" → "很"
生成2：  "今天天气很" → "好"
生成3：  "今天天气很好" → "！"
```

Self-Attention 的计算需要当前 token 和**所有历史 token** 的 K、V：

$$
\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V
$$

**不用 KV Cache 的情况**：每步都对整个序列重算所有 K、V，计算量随长度平方增长：

```
生成第 t 个 token，需要对 [t1, t2, ..., t] 全部重算 K/V
总计算量 = O(1) + O(2) + ... + O(n) = O(n²)
```

**用 KV Cache**：把每个 token 的 K、V 算出来后缓存，后续直接复用：

```
Step 1：输入 [t1, t2, t3]，计算并缓存 K/V[1..3]
Step 2：输入 [t4]，复用 K/V[1..3]，只算 K/V[4]
Step 3：输入 [t5]，复用 K/V[1..4]，只算 K/V[5]
→ 每步新增计算 O(1)，总体 O(n)
```

---

## 对性能的影响

### 加速效果

| | 不用 KV Cache | 用 KV Cache |
|--|--------------|------------|
| 每步计算量 | O(n)，随序列增长 | O(1)，只算新 token |
| 总计算量 | O(n²) | O(n) |
| 典型加速比 | — | 10x ~ 100x（序列越长越明显） |

### 代价：显存占用

KV Cache 随序列长度线性增长，是长上下文场景的显存瓶颈：

$$
\text{KV Cache 大小} = 2 \times n_{\text{layers}} \times n_{\text{heads}} \times d_{\text{head}} \times L \times \text{dtype\_bytes}
$$

以 LLaMA-3 8B（32 层，32 头，128 维，FP16）为例：

```
单个 token 的 KV：
  2 × 32 × 32 × 128 × 2 字节 = 524,288 字节 ≈ 0.5 MB

序列长度 4096 token 的 KV Cache：
  0.5 MB × 4096 ≈ 2 GB

并发 10 个请求：
  2 GB × 10 = 20 GB  ← 仅 KV Cache 就占满大部分显存
```

**KV Cache 和模型权重抢显存**，这是大模型推理并发上不去的根本原因。

---

## 优化方案

### 1. PagedAttention（vLLM 核心技术）

**问题**：传统方式为每个请求预分配连续显存，利用率低，碎片多。

**解法**：借鉴操作系统虚拟内存的分页机制，把 KV Cache 切成固定大小的"页"，按需分配：

```
传统分配（连续块，预分配最大长度）：
  请求A: [████████████████░░░░░░░░]  预留但未用
  请求B: [████████░░░░░░░░░░░░░░░░]  大量浪费

PagedAttention（分页，按需分配）：
  请求A: [页1][页2][页3]  实际用多少分多少
  请求B: [页4][页5]
  空闲页可以给新请求复用
```

效果：显存利用率从 ~60% 提升到 ~90% 以上，并发数大幅提升。

---

### 2. MQA / GQA（减少 KV 头数）

**问题**：标准 Multi-Head Attention，每个 Query Head 都有独立的 K、V Head，KV Cache 很大。

**Multi-Query Attention（MQA）**：所有 Query Head 共享同一组 K、V：

```
标准 MHA（32 个 Q Head，32 个 KV Head）：
  KV Cache = 32 × 2 × ...

MQA（32 个 Q Head，1 个 KV Head）：
  KV Cache = 1 × 2 × ...   ← 缩小 32 倍
  代价：效果略有下降
```

**Grouped Query Attention（GQA）**：折中方案，多个 Query Head 共享一组 KV：

```
GQA（32 个 Q Head，8 个 KV Head，每组 4 个 Q 共享 1 组 KV）：
  KV Cache = 8 × 2 × ...   ← 缩小 4 倍，效果接近 MHA
```

LLaMA-3、Mistral 等新模型默认使用 GQA。

---

### 3. Prefix Caching（前缀缓存）

**场景**：多个请求共享相同的前缀（System Prompt、长文档）。

```
请求1：[System Prompt（500 token）] + 用户问题A
请求2：[System Prompt（500 token）] + 用户问题B
请求3：[System Prompt（500 token）] + 用户问题C
```

**做法**：System Prompt 的 KV Cache 只算一次，所有请求复用：

```
首次请求：计算并缓存 System Prompt 的 KV
后续请求：直接读缓存，只算用户问题部分的 KV
```

效果：相同前缀的 TTFT（首 token 时延）大幅降低。vLLM、SGLang 均支持。

---

### 4. KV Cache 量化

把 KV Cache 的数据类型从 FP16 压缩为 INT8 或 FP8：

```
FP16：每个值 2 字节
INT8：每个值 1 字节  ← 显存减半，精度略有损失
FP8： 每个值 1 字节  ← 精度优于 INT8
```

实验结果：INT8 量化的 KV Cache 在大多数任务上精度损失极小（< 0.5%），显存节省 50%。

---

### 5. KV Cache Offloading

**场景**：显存不够时，把暂不活跃请求的 KV Cache 卸载到 CPU 内存或 SSD。

```
显存（GPU HBM）：当前活跃请求的 KV Cache   ← 最快
CPU 内存：      被换出的请求的 KV Cache     ← 次快
SSD：           DiskANN 等超大规模场景       ← 最慢
```

代价：从 CPU/SSD 读回时有延迟，适合对时延不敏感的离线场景。

---

## 各优化方案对比

| 方案 | 减少显存 | 提升并发 | 代价 |
|------|---------|---------|------|
| PagedAttention | ✓（减少碎片） | ✓✓ | 实现复杂 |
| GQA | ✓✓（减少 KV 头数） | ✓ | 需模型支持 |
| Prefix Caching | ✓（共享前缀） | ✓ | 前缀相同才有效 |
| KV 量化 | ✓✓（减半） | ✓ | 极小精度损失 |
| Offloading | ✓✓✓ | ✓ | 增加延迟 |

生产环境通常组合使用：**GQA 模型 + PagedAttention + Prefix Caching + KV 量化**。
