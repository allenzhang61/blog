# RAG（Retrieval-Augmented Generation，检索增强生成）

## 为什么需要 RAG

LLM 有三个根本局限：

```
① 知识有截止日期
   模型训练完就冻结了，不知道之后发生的事

② 不知道私有数据
   公司内部文档、合同、产品手册，模型从未见过

③ 会"幻觉"
   不知道的事会编造，且听起来很自信
```

### 核心思路

**不改变模型，改变输入**——把相关资料塞进 Prompt，让模型"开卷答题"。

```
闭卷（纯 LLM）：
  问："我们公司的退款政策是什么？"
  答：（瞎编一个）

开卷（RAG）：
  先检索出退款政策文档片段
  再问："根据以下内容回答：[退款政策原文]，问题：退款政策是什么？"
  答：（基于原文回答，有据可查）
```

---

## 完整流程

```
离线阶段（建库）：
  原始文档
     ↓
  Chunking（切块）        ← 把长文档切成小片段
     ↓
  Embedding 模型          ← 每个片段转成向量
     ↓
  存入向量数据库

在线阶段（查询）：
  用户提问
     ↓
  Embedding 模型          ← 问题也转成向量
     ↓
  向量数据库检索           ← 找最相近的 Top-K 片段
     ↓
  拼接 Prompt             ← 问题 + 检索到的片段
     ↓
  LLM 生成回答
```

---

## 解决的问题

| 问题 | RAG 的解法 |
|------|-----------|
| 知识有截止日期 | 向量库实时更新，不用重训模型 |
| 私有数据无法训练进模型 | 私有文档存向量库，按需检索 |
| 幻觉 | 答案有来源文档可追溯 |
| 全量微调成本高 | 检索比微调便宜得多 |

---

## 核心组件

```
RAG 系统
  ├── Chunking（文档切块策略）
  ├── Embedding 模型（文本 → 向量）
  ├── 向量数据库（存储和检索向量）
  ├── Reranker（对召回结果重排序，可选）
  └── LLM（基于上下文生成回答）
```

每个组件的选型都影响最终效果。

---

## 与其他方案的对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 纯 LLM | 简单 | 幻觉、无私有数据 |
| 全量微调 | 知识融入模型 | 成本极高，数据更新需重训 |
| RAG | 低成本、可追溯、易更新 | 检索质量影响上限，链路复杂 |
| RAG + 微调 | 效果最好 | 成本最高 |

RAG 不是万能的——检索召回的内容质量是上限，LLM 再强也无法从错误的上下文里生成正确答案。
