# Pixel 9 上可运行选项性能对比

> 这里整理 Pixel 9 上适合尝试的开源本地 LLM server / runtime，并记录通过 Mac + adb 做短时压测的方法和结果。

## 背景

Pixel 9 是 Android 手机，适合测试“随身边缘推理”的体验，但它和 Mac Studio / NVIDIA 服务器的约束很不一样：

- 手机散热空间小，长时间推理容易热降频。
- Android 普通权限下很难稳定采集真实 GPU utilization。
- 很多移动端 LLM 项目是 App 或 SDK，不一定直接暴露 HTTP server。
- 如果目标是“把手机当本地推理服务器”，优先选择能启动 HTTP API 的方案。

当前已连接设备信息：

| 项目 | 值 |
| --- | --- |
| 设备 | Pixel 9 |
| 厂商 | Google |
| Android | 16 |
| SDK | 36 |
| ABI | arm64-v8a |
| SoC | Tensor G4 |
| CPU | 8 核：1× Cortex-X4 约 3.1GHz，3× Cortex-A720 约 2.6GHz，4× Cortex-A520 约 1.9GHz |
| GPU | Mali-G715 MP7，最高约 940MHz |
| 内存 | 约 11.8GB |

其中 CPU 核心信息与本机 `/sys/devices/system/cpu` 采集值一致：

| 核心 | 最高频率 | 说明 |
| --- | ---: | --- |
| cpu0-cpu3 | 1.95GHz | 小核，对应 Cortex-A520 级别 |
| cpu4-cpu6 | 2.60GHz | 中核，对应 Cortex-A720 级别 |
| cpu7 | 3.105GHz | 大核，对应 Cortex-X4 级别 |

GPU 通过自编译 Vulkan 版 `llama-server --list-devices` 枚举为：

```text
Vulkan0: Mali-G715 (11443 MiB, 11443 MiB free)
```

系统可读的 Mali 频率档位为：

```text
940000 890000 850000 807000 723000 649000 580000 521000 467000 419000 376000 337000 302000 150000
```

`Mali-G715 MP7` 中的 `MP7` 表示 7 个 GPU core / shader core 配置；这个 core 数不是 Android sysfs 直接暴露出来的，而是按 Tensor G4 / Pixel 9 公开规格标注。

## 推荐清单

| 推荐度 | 项目 | Pixel 9 支持情况 | 适合场景 | 备注 |
| --- | --- | --- | --- | --- |
| 强烈推荐 | llama.cpp / llama-server | 支持 Android / arm64，可通过 Termux 或交叉编译运行 | GGUF 模型、本地 HTTP API、可控参数压测 | 最适合作为 Pixel 9 LLM server 的基线 |
| 强烈推荐 | ServLlama | Android App 形式包装 llama-server | 不想折腾 Termux，希望直接在手机上启停服务 | 核心仍是 llama.cpp，适合第一轮实测 |
| 可以尝试 | MLC LLM Android | 原生 Android runtime | 研究移动端 GPU / Vulkan / 编译优化 | 更偏 App/SDK，不一定直接暴露 HTTP server |
| 可以尝试 | Google AI Edge Gallery / MediaPipe LLM Inference | Google AI Edge 生态，面向 Android 本地推理 | 体验 Google 官方移动端 GenAI 能力 | 更偏示例 App/SDK；要压 HTTP API 需额外封装 server |
| 可以尝试 | LiteRT-LM | Google AI Edge 的端侧 LLM inference 框架 | 研究 Android 端侧推理框架 | 更偏底层框架，不是即开即用 server |
| 谨慎尝试 | Ollama via Termux / proot | 非官方主流路径 | 尝试复用 Ollama API 生态 | Android 上维护和性能不如 llama.cpp 路线稳定 |

## 不推荐作为 Pixel 9 主力

| 项目 | 原因 |
| --- | --- |
| vLLM / SGLang / TensorRT-LLM | 主要面向服务器 GPU / CUDA / Linux 环境，不适合直接跑在 Android 手机上。 |
| Hugging Face TGI | 主要面向 Linux 服务端部署，不是移动端路线。 |
| Triton Inference Server | 生产推理底座很强，但 Pixel 9 不是它的目标运行环境。 |
| LocalAI | 可以作为服务层，但 Android 手机上部署复杂度高；直接用 llama.cpp 更简单。 |

## 初步选择建议

如果目标是“Pixel 9 变成本地 HTTP LLM server”：

```text
ServLlama / llama.cpp llama-server
```

如果目标是研究移动端 runtime：

```text
MLC LLM Android / Google AI Edge / LiteRT-LM
```

如果目标是和 Mac Studio 的压测表保持口径一致：

```text
优先选择 OpenAI-compatible API，并固定 prompt、输出 tokens、单请求压测。
```

  AI/chapter-14/android/bench_android_llm.sh

## 压测结果

本轮使用 `llama.cpp` 官方 Android arm64 release 中的 `llama-server`，通过 adb 推送到 Pixel 9 的 `/data/local/tmp` 后启动。模型使用 `Qwen3-0.6B-Q4_K_M.gguf`，输出长度固定为 128 tokens，只做单请求压测。

启动方式：

```bash
adb shell "cd /data/local/tmp/llama-b9986; \
  export LD_LIBRARY_PATH=/data/local/tmp/llama-b9986; \
  nohup ./llama-server \
    -m /data/local/tmp/models/Qwen3-0.6B-Q4_K_M.gguf \
    --host 127.0.0.1 --port 8080 \
    -c 2048 -ngl 0 --jinja --no-webui \
    >/data/local/tmp/llama-server.log 2>&1 < /dev/null &"
```

压测命令：

```bash
SERVICE="llama.cpp llama-server" \
API_STYLE=openai \
DEVICE_PORT=8080 \
MODEL="Qwen3-0.6B-Q4_K_M.gguf" \
ANDROID_PROCESS_NAME="llama-server" \
  AI/chapter-14/android/bench_android_llm.sh
```

当前表格对应的 CSV 结果文件：

```text
AI/chapter-14/android/results/pixel9-llama-server-qwen3-0.6b-final.csv
AI/chapter-14/android/results/pixel9-llama-server-vulkan-qwen3-0.6b-final.csv
AI/chapter-14/android/results/pixel9-llama-server-cpu-usage-qwen3-0.6b-final.csv
AI/chapter-14/android/results/pixel9-llama-server-vulkan-usage-qwen3-0.6b-final.csv
```

| 服务 | API | 模型 | TTFT(ms) | output tokens | total/wall_s | tokens/s | avg_request_s | CPU(%) | GPU active(%) | GPU freq | 进程内存 | 系统内存增量 | 电池温度 | thermal |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- | --- | --- | --- | --- |
| llama.cpp llama-server CPU | openai | Qwen3-0.6B-Q4_K_M.gguf | 93.8 | 128 | 20.43 | 6.3 | 20.43 | 628.1% | 未采集 | 150 MHz | 1035.1 MB | -0.0 GB | 23.3°C | status=0; G3D=45.000004°C |
| llama.cpp llama-server Vulkan | openai | Qwen3-0.6B-Q4_K_M.gguf | 96.6 | 128 | 6.43 | 19.9 | 6.43 | 63.2% | 61.8% | 150 MHz | 945.0 MB | 0.0 GB | 23.2°C | status=0; G3D=45.000004°C |

这轮可以看到：

- Pixel 9 走 CPU 路线跑 `Qwen3-0.6B-Q4_K_M.gguf` 的单请求 decode 吞吐约 `6.2 tokens/s`。
- 自编译 Android Vulkan 版后，单请求 decode 吞吐提升到约 `19.9 tokens/s`，约为 CPU 路线的 `3.2x`。
- CPU 版 `llama-server` 日志中同一请求的 eval 口径为 `128 tokens / 20153.50 ms`，约 `6.35 tokens/s`；Vulkan 版 eval 口径为 `128 tokens / 6136.00 ms`，约 `20.86 tokens/s`。两者都与脚本的端到端 HTTP 口径基本一致。
- CPU 路线进程 CPU 约 `628.1%`，表示压测期间大约吃掉 6 个多 CPU core；Vulkan 路线进程 CPU 降到约 `63.2%`。
- Vulkan 路线通过 `dumpsys gpu` 按 UID 估算的 `GPU active` 约 `61.8%`；CPU 路线没有采到有效 GPU active 增量。
- 进程 RSS 约 `945 MB` 到 `1035 MB`，对于 0.6B Q4 模型是可接受的。
- Thermal Status 为 `0`，本次短测没有触发系统热限制；但 G3D 缓存温度读数到约 `45°C`，长时间连续生成仍建议单独观察降频。
- Android 非 root 环境下暂未稳定采集 GPU utilization；本文用 `--list-devices`、Vulkan backend 枚举结果和吞吐变化来确认 GPU 路线是否生效。

### GPU 路线验证

Pixel 9 系统本身暴露了 Vulkan compute 能力：

```text
android.hardware.vulkan.compute
android.hardware.vulkan.level=1
android.hardware.vulkan.version=4210688
```

本轮先测试了 `llama.cpp` 官方 Android arm64 release。它只有 CPU backend：

```text
libggml-cpu-android_armv8.0_1.so
libggml-cpu-android_armv8.2_1.so
libggml-cpu-android_armv8.2_2.so
libggml-cpu-android_armv8.6_1.so
libggml-cpu-android_armv9.0_1.so
libggml-cpu-android_armv9.2_1.so
libggml-cpu-android_armv9.2_2.so
```

没有看到 `libggml-vulkan.so`。同时执行：

```bash
./llama-server --list-devices
```

只返回：

```text
Available devices:
```

说明官方 Android CPU 包没有枚举到可用 GPU backend。

随后在 Mac 上交叉编译了 Android Vulkan 版 `llama.cpp`：

```bash
brew install cmake ninja shaderc spirv-headers spirv-tools vulkan-headers android-ndk
AI/chapter-14/android/build_llama_vulkan.sh
```

构建产物中包含：

```text
libggml-vulkan.so
llama-server
llama-cli
llama-bench
```

推送到 Pixel 9 后执行：

```bash
cd /data/local/tmp/llama-vulkan
LD_LIBRARY_PATH=/data/local/tmp/llama-vulkan ./llama-server --list-devices
```

可以看到：

```text
Available devices:
  Vulkan0: Mali-G715 (11443 MiB, 11443 MiB free)
```

为了验证 `-ngl` 参数是否能生效，又用同一个模型启动了一轮：

```bash
./llama-server \
  -m /data/local/tmp/models/Qwen3-0.6B-Q4_K_M.gguf \
  --host 127.0.0.1 --port 8080 \
  -c 2048 -ngl 999 --jinja --no-webui
```

结果如下：

| 启动参数 | TTFT(ms) | output tokens | total/wall_s | tokens/s | 进程内存 | 结论 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| `-ngl 0` | 93.8 | 128 | 20.43 | 6.3 | 1035.1 MB | CPU 路线 |
| 官方 CPU 包 `-ngl 999` | 94.9 | 128 | 20.07 | 6.4 | 1035.8 MB | 未观察到 GPU backend 生效 |
| 自编译 Vulkan 包 `-ngl 999` | 96.6 | 128 | 6.43 | 19.9 | 945.0 MB | Vulkan backend 生效 |

结论：**官方 Android arm64 包没有真正用上 GPU；自编译 `GGML_VULKAN=ON` 后，Pixel 9 可以通过 Vulkan 使用 Mali-G715，且本轮 0.6B Q4 模型吞吐从约 `6.3 tokens/s` 提升到约 `19.9 tokens/s`。**

## 结果口径

- 只做单请求压测，不做并发大于 1 的压力测试。
- warmup 请求不计入最终结果。
- `TTFT(ms)` 使用 streaming 请求的 `curl time_starttransfer` 近似首块响应时间，先 warmup 后取多次 p50。
- `tokens/s` 使用输出 token 数除以正式请求总耗时。
- `CPU(%)` 用 `/proc/<pid>/stat` 和 `/proc/stat` 前后差值估算。Android 多核机器上可能超过 100%，例如 `628.1%` 约等于 6.3 个 CPU core。
- `GPU active(%)` 用 `dumpsys gpu` 中目标 UID 的 active/inactive duration 前后差值估算。adb 直接启动的 `llama-server` 属于 `shell` UID，所以这是 UID 级口径，不是严格 PID 级口径。
- `GPU freq` 是压测结束附近读取到的 Mali `cur_freq`，只是采样点频率，不代表整段请求的平均频率。
- `进程内存` 优先使用 `ANDROID_PACKAGE` 采集 App PSS；对于 adb 直接启动的二进制，可用 `ANDROID_PROCESS_NAME` 采集 RSS。
- Android 非 root 环境下通常不能稳定采集真实 GPU utilization；本文用 `thermalservice` 中的 G3D 温度和 thermal status 辅助观察是否有热压力。
