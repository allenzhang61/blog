# vLLM 内存管理机制

## 整体结构

vLLM 启动时一次性将 GPU 显存划分为两个固定区域，运行期间不再动态申请：

```
GPU 显存（如 24GB）× gpu_memory_utilization（默认 0.92）
│
├── 模型权重区（静态）
│     Qwen3.5-9B BF16 ≈ 17.65GB
│     加载后固定不变
│
└── KV Cache Pool（静态）
      剩余显存全部预分配为 KV Cache 块
      Qwen3.5-9B 在 24GB 卡上 ≈ 1.41GB（max_model_len=8192）
```

这种设计的核心目标：**消除运行时 OOM，代价是启动时显存利用率看起来很高**。

---

## PagedAttention

传统 Attention 要求 KV Cache 在连续内存中存放，每个请求预留 `max_seq_len × hidden_dim` 的空间。问题：

- 请求实际长度未知，必须按最大值预留 → 大量内碎片
- 不同请求无法共享相同前缀的 KV → 重复计算

vLLM 借鉴操作系统的**虚拟内存分页**思想，实现 PagedAttention：

```
物理 KV Cache
┌──────┬──────┬──────┬──────┬──────┬──────┐
│ Block│ Block│ Block│ Block│ Block│ Block│  ← 固定大小的物理块（如每块 16 tokens）
│  0   │  1   │  2   │  3   │  4   │  5   │
└──────┴──────┴──────┴──────┴──────┴──────┘

Request A（实际长度 35 tokens）→ 映射到 Block 0, 1, 2（共 3 块）
Request B（实际长度 20 tokens）→ 映射到 Block 3, 4（共 2 块）
Block 5 → 空闲，等待分配
```

**按需分配**：请求生成过程中，每当 decode 超出当前块容量，才申请新块。不再按 max_seq_len 预留。

**外碎片消除**：块大小固定（通常 16~32 tokens），块内最后一块可能有少量浪费，但整体碎片率极低。

## KV Cache 共享（Prefix Caching）

PagedAttention 的延伸：相同前缀的 KV Cache 块可以跨请求共享。

```
Request A: [System Prompt][User Turn 1][Assistant Turn 1][User Turn 2]
Request B: [System Prompt][User Turn 1][Assistant Turn 1][User Turn 3]
                ↑_________________________↑
                        共享这部分 KV Cache 块（Copy-on-Write）
```

vLLM v0.4+ 的 **Automatic Prefix Caching（APC）** 用哈希标识每个块的内容，命中即复用，无需重新计算。

启用方式：

```bash
--enable-prefix-caching
```

适合场景：多轮对话、RAG（相同文档块）、批量推理（相同 system prompt）。

## Continuous Batching

传统静态 batching：一批请求必须等全部生成完才能处理下一批，GPU 利用率低。

vLLM 的 **Continuous Batching**（也称 iteration-level scheduling）：

```
Step 1: [Req A decode] [Req B decode] [Req C prefill]
Step 2: [Req A decode] [Req B done → Req D prefill] [Req C decode]
Step 3: [Req A done → Req E prefill] [Req D decode] [Req C decode]
```

每个 decode step 结束后，调度器立即检查：
- 已完成的请求 → 释放其 KV Cache 块
- 队列中等待的请求 → 填入空出的槽位

GPU 始终满载运行，无需等待最慢的请求。

## 请求调度与抢占

当 KV Cache 块耗尽时，调度器有两种处理方式：

### Swapping（换出到 CPU）

将低优先级请求的 KV Cache 换出到 CPU 内存，腾出 GPU 块给高优先级请求：

```
GPU KV Cache 满
    ↓
将 Req X 的 KV Cache → 换出到 CPU DRAM
    ↓
GPU 块空出 → 分配给新请求
    ↓
Req X 重新调度时 → 换回 GPU
```

缺点：PCIe 带宽是瓶颈，换出/换回耗时明显。

### Recomputation（重新计算）

直接丢弃被抢占请求的 KV Cache，等重新调度时从头 prefill。

适合 prefill 成本低（短 prompt）的场景，避免了换出的传输开销。

## 显存分配全流程

```
vllm serve 启动
    │
    ├─ 加载模型权重到 GPU（固定区）
    │
    ├─ profile_run：用一个虚拟请求跑一遍，测量激活内存峰值
    │
    ├─ 计算可用 KV Cache 显存：
    │   available = total × gpu_memory_utilization
    │             - 模型权重
    │             - 激活内存峰值
    │             - CUDA Graph 内存
    │
    ├─ 将可用显存划分为固定大小的 KV Cache 块
    │   block_size = 16 tokens（默认）
    │   num_blocks = available / (block_size × layers × heads × head_dim × 2 × dtype_size)
    │
    └─ 启动完成，开始接受请求
           ↓
       请求到来 → 从 block pool 分配块 → decode → 块逐步填满 → 生成结束 → 块归还
```

## request-rate 与 OOM 的关系

**request-rate 不会导致 OOM**，因为：

```
request-rate 控制的是请求到达速率（benchmark 参数）
                    ↓
超出处理能力的请求 → 进入等待队列（不占 KV Cache）
                    ↓
表现为 TTFT 升高，而非 OOM
```

真正影响显存的参数：

| 参数 | 影响 | 说明 |
|------|------|------|
| `gpu_memory_utilization` | KV Cache 总量 | 越高 KV Cache 越多，但挤占模型激活空间有风险 |
| `max_model_len` | 每个请求最多占用的块数 | 越大单请求可占用 KV Cache 越多 |
| `max_num_seqs` | 同时在飞的请求上限 | 超过 KV Cache 容量时触发抢占/排队 |

## 实测数据（Qwen3.5-9B，RTX 4090 24GB）

```
gpu_memory_utilization = 0.90
max_model_len          = 8192
cudagraph_capture_sizes = [1,2,4,8,16,32]

模型权重：17.65 GB
KV Cache：1.41 GB（37,510 tokens 容量）
CUDA Graph：0.08 GB
剩余缓冲：~0.40 GB
```

启动日志中的关键输出：

```
Model loading took 17.65 GiB memory
Available KV cache memory: 1.41 GiB
GPU KV cache size: 37,510 tokens
Maximum concurrency for 8,192 tokens per request: 4.58x
```

说明在 `max_model_len=8192` 下，最多可同时支持约 4~5 个请求并发推理。
