# CUDA 机器上可运行选项性能对比

> 这里整理 NVIDIA CUDA 机器上适合尝试的开源推理服务器/框架，并记录这台 Windows + RTX 3080 机器上的 8B 模型短时压测结果。

## 背景

CUDA 机器和 Mac Studio / Pixel 9 的约束不一样。它的主力路线不是 Metal / MLX / Vulkan，而是：

- NVIDIA GPU / CUDA
- CUDA kernel / FlashAttention / PagedAttention
- FP16 / BF16 / FP8 / INT8 / INT4 量化
- Docker / WSL / Linux 原生服务环境

如果目标是生产级 LLM serving，CUDA 上优先比较 vLLM、SGLang、TensorRT-LLM、TGI。llama.cpp CUDA 更适合作为本地开发、单机实验、GGUF 量化模型服务的轻量选择。

## 推荐清单

| 推荐度 | 项目 | CUDA 支持情况 | 适合场景 | 备注 |
| --- | --- | --- | --- | --- |
| 强烈推荐 | vLLM | NVIDIA CUDA 是主力平台 | OpenAI-compatible API、高吞吐、PagedAttention、生产服务 | 通常建议 Linux / Docker / WSL 环境 |
| 强烈推荐 | SGLang | 面向常见 NVIDIA GPU 平台 | 复杂推理、结构化输出、agent workflow、高并发 | Prefix cache / RadixAttention 场景值得重点测 |
| 强烈推荐 | TensorRT-LLM | NVIDIA 官方 LLM 推理优化框架 | 极致吞吐、低延迟、TensorRT engine、NVIDIA 生产环境 | 构建和模型转换复杂度最高 |
| 可以尝试 | Hugging Face TGI | NVIDIA GPU + Docker 是主流路径 | Hugging Face 模型生态、text-generation server | 更适合走 Hugging Face 官方 serving 路线时评估 |
| 可以尝试 | llama.cpp CUDA | Windows / Linux CUDA 预编译包可用 | GGUF 量化模型、本地 OpenAI-compatible server、轻量部署 | 本轮已在 Windows 原生实测 |

## 结果理解

这轮 8B 小压测可以先按这个顺序理解：

```text
吞吐优先：vLLM CUDA
轻量可用：llama.cpp CUDA
SGLang：需要提高并发压测，调优后 aggregate 吞吐可超过本轮 vLLM 并发 4 数字
```

几个观察：

- vLLM CUDA 在并发 4 下 aggregate 吞吐约 `470.3 tokens/s`，显存峰值约 `10.2GB`。
- llama.cpp CUDA 的 Q4_K_M 显存峰值约 `6.7GB`，并发 4 吞吐约 `194.8 tokens/s`，是这台 Windows 机器上最省心的 8B 本地基线。
- SGLang 低并发时 GPU 利用率确实偏低；把并发从 4 提到 16 后，吞吐从 `156.3 tokens/s` 提到 `597.2 tokens/s`，GPU max 从 `38%` 提到 `58%`。
- SGLang 默认 flashinfer attention 在并发 16 下约 `547.8 tokens/s`；本轮改成 Triton attention 后达到 `597.2 tokens/s`，作为本次更新后的 SGLang 结果。
- SGLang 尝试保留 CUDA graph 时，prefill / decode graph capture 在这台 12GB 3080 + Docker Desktop 环境下都出现启动阶段卡住；本轮采用关闭 CUDA graph 的稳定配置。
- 这轮 prompt 短、输出 128 tokens，只适合作为快速 baseline；如果要评估业务压测，需要补长 prompt、更高并发、p95/p99 latency 和长时间稳定性。
