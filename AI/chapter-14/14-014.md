# CUDA 机器上可运行选项性能对比

> 这里整理 NVIDIA CUDA 机器上适合尝试的开源推理服务器/框架，并记录 `lxa@192.168.1.110` 这台 Windows + RTX 3080 机器上的短时压测结果。

## 背景

CUDA 机器和 Mac Studio / Pixel 9 的约束不一样。它的主力路线不是 Metal / MLX / Vulkan，而是：

- NVIDIA GPU / CUDA
- CUDA kernel / FlashAttention / PagedAttention
- FP16 / BF16 / FP8 / INT8 / INT4 量化
- Docker / WSL / Linux 原生服务环境

如果目标是生产级 LLM serving，CUDA 上优先比较 vLLM、SGLang、TensorRT-LLM、TGI。llama.cpp CUDA 和 Ollama CUDA 更适合作为本地开发、单机实验、GGUF 量化模型服务的轻量选择。

## 推荐清单

| 推荐度 | 项目 | CUDA 支持情况 | 适合场景 | 备注 |
| --- | --- | --- | --- | --- |
| 强烈推荐 | vLLM | NVIDIA CUDA 是主力平台 | OpenAI-compatible API、高吞吐、PagedAttention、生产服务 | 通常建议 Linux / Docker / WSL 环境 |
| 强烈推荐 | SGLang | 面向常见 NVIDIA GPU 平台 | 复杂推理、结构化输出、agent workflow、高并发 | Prefix cache / RadixAttention 场景值得重点测 |
| 强烈推荐 | TensorRT-LLM | NVIDIA 官方 LLM 推理优化框架 | 极致吞吐、低延迟、TensorRT engine、NVIDIA 生产环境 | 构建和模型转换复杂度最高 |
| 可以尝试 | Hugging Face TGI | NVIDIA GPU + Docker 是主流路径 | Hugging Face 模型生态、text-generation server | RTX 3080 可尝试，但部分优化更偏数据中心卡 |
| 可以尝试 | llama.cpp CUDA | Windows / Linux CUDA 预编译包可用 | GGUF 量化模型、本地 OpenAI-compatible server、轻量部署 | 本轮已在 Windows 原生实测 |
| 可以尝试 | Ollama CUDA | Windows / Linux 上可使用 NVIDIA GPU | 本地开发、个人 API、快速拉模型 | 上手简单，但生产级 batching 能力不如 vLLM / SGLang |
| 上层框架 | Ray Serve / BentoML | 可封装 CUDA 后端 | pipeline、多模型服务编排、Python API 服务化 | 底层仍建议接 vLLM / SGLang / TensorRT-LLM 等 |
| 平台层 | Triton Inference Server | NVIDIA 推理服务底座 | 多框架统一 serving、TensorRT / ONNX / PyTorch 模型 | LLM 通常结合 TensorRT-LLM 或专用 backend 使用 |

## 不推荐作为 CUDA LLM 主力

| 项目 | 原因 |
| --- | --- |
| MLX / vLLM-Metal / SGLang MLX | 面向 Apple Silicon / Metal，不是 CUDA 路线。 |
| OpenVINO Model Server | 更偏 Intel 硬件生态。 |
| MLServer | 传统 ML serving 可以，LLM / CUDA 高吞吐不是重点。 |
| TorchServe | 能服务 PyTorch 模型，但本地 LLM serving 体验和吞吐通常不如 vLLM、SGLang、TGI、TensorRT-LLM。 |

## 初步选择建议

如果要快速跑 OpenAI-compatible LLM API：

```text
vLLM / SGLang
```

如果追求 NVIDIA GPU 上的极致性能：

```text
TensorRT-LLM + Triton
```

如果偏 Hugging Face 生态，想用官方 text generation server：

```text
TGI
```

如果是 Windows 单机、本地开发、GGUF 量化模型：

```text
llama.cpp CUDA / Ollama CUDA
```

如果要做业务服务封装：

```text
vLLM / SGLang / llama.cpp CUDA + FastAPI
Ray Serve / BentoML
```

## 压测脚本

本轮仓库中添加了压测脚本：

```text
AI/chapter-14/cuda/bench_llama_cpp_cuda.py
```

脚本依赖：

```bash
pip install requests
```

远端实际使用已有环境：

```text
D:\llm-bench\.venv\Scripts\python.exe
```

启动 llama.cpp CUDA server 示例：

```bat
D:\cuda-llm-bench\tools\llama-b10075\llama-server.exe ^
  -m D:\cuda-llm-bench\models\Qwen3-8B-Q4_K_M.gguf ^
  --host 127.0.0.1 ^
  --port 8089 ^
  --ctx-size 2048 ^
  --gpu-layers 999 ^
  --parallel 4 ^
  --cont-batching ^
  -b 2048 ^
  -ub 512 ^
  --alias qwen3-8b-q4km
```

运行压测：

```bat
set BASE=http://127.0.0.1:8089/v1/chat/completions&& ^
set MODEL=qwen3-8b-q4km&& ^
set MODEL_LABEL=Qwen3-8B Q4_K_M GGUF&& ^
set OUT=D:\cuda-llm-bench\results\llama-cpp-cuda-qwen3-8b.csv&& ^
D:\llm-bench\.venv\Scripts\python.exe D:\cuda-llm-bench\bench_llama_cpp_cuda.py
```

压测口径：

| 项目 | 值 |
| --- | --- |
| API | OpenAI-compatible `/v1/chat/completions` |
| prompt | 中文短问题：说明 prefill 和 decode 的区别 |
| 输出长度 | 128 tokens |
| context | 2048 |
| 并发 | 1 / 2 / 4 |
| TTFT | streaming 请求测 5 次，取 p50 |
| tokens/s | `usage.completion_tokens / wall time` |
| GPU | `nvidia-smi` 每 0.2 秒采样 |

注意：`--parallel 4` 时 llama.cpp server 日志显示：

```text
n_slots = 4, n_ctx_slot = 512
```

也就是总 `ctx-size=2048` 被切到 4 个 slot；本轮 prompt 很短、输出 128，因此够用。如果要测长上下文，应提高 `--ctx-size`，例如 `8192` 或更高。

## 结果理解

这轮可以看到：

- RTX 3080 12GB 可以轻松跑 Qwen3-8B Q4_K_M，显存峰值约 `6.7GB`。
- Qwen3-8B 单请求约 `95.4 tokens/s`，并发 4 aggregate 吞吐约 `194.8 tokens/s`。
- Qwen3-1.7B 单请求约 `186.0 tokens/s`，并发 4 aggregate 吞吐约 `327.6 tokens/s`。
- 1.7B 的显存峰值只有约 `1.6GB`，适合做 CUDA server 链路烟测，但不能代表 8B 或更大模型的真实业务性能。
- 8B 并发 4 时平均单请求耗时从 `1.34s` 增加到 `2.62s`，总吞吐提高，但单请求延迟也上升。
- 本轮 8B 的 GPU avg 并没有一直接近 100%，说明短 prompt + 128 decode 的小压测不一定能完全压满 RTX 3080。后续应补更长时间、更高并发、更长 prompt 的测试。

和 Mac Studio 那篇的 Qwen3-8B 表相比，不能直接下“谁更强”的结论，因为：

- Mac 那边测的是 Ollama / vLLM-Metal / SGLang MLX / LocalAI。
- 本轮 CUDA 只实测了 llama.cpp CUDA。
- Mac 那边 Ollama 用的是 `qwen3:8b`，其他是 MLX 4bit；这里是 GGUF Q4_K_M。
- prompt、服务调度、tokenizer、KV cache、batching 策略都不完全相同。

但就本轮单机结果看，Windows 原生 llama.cpp CUDA 已经能作为 RTX 3080 的可用本地推理基线。

## Docker 当前问题

Docker Desktop 已启动，`docker info` 显示 Linux engine 和 `nvidia` runtime 可见：

```text
OSType: linux
ServerVersion: 29.6.2
runtime: nvidia
```

但是通过 SSH 拉取新镜像失败：

```text
docker pull alpine:latest
docker pull nvidia/cuda:12.4.1-base-ubuntu22.04
```

都报：

```text
error getting credentials - err: exit status 1, out: `A specified logon session does not exist. It may already have been terminated.`
```

即使使用 D 盘独立 Docker config：

```bat
docker --config D:\cuda-llm-bench\docker-config pull alpine:latest
```

仍然失败。因此后续要测 vLLM / SGLang / TGI / TensorRT-LLM，需要先处理 Docker Desktop 的 registry credentials / credential helper 问题，或者在本机交互登录会话里先 pull 好镜像。

## 后续压测计划

Docker pull 修复后，建议优先补：

| 优先级 | 服务 | 模型口径 | 目标 |
| --- | --- | --- | --- |
| 1 | vLLM | Qwen3-8B / Qwen2.5-7B Instruct FP16 或 AWQ/GPTQ | CUDA 上的主流 serving baseline |
| 2 | SGLang | 同 vLLM 模型 | 对比并发吞吐、prefix cache、结构化输出能力 |
| 3 | TGI | 同 Hugging Face 模型 | 对比 HF 生态服务能力 |
| 4 | TensorRT-LLM | 选一个支持良好的 7B/8B 模型 | 评估 engine 构建成本与吞吐收益 |
| 5 | Ollama CUDA | Qwen3 8B | 对比 Windows 本地易用路线 |

推荐统一记录：

| 指标 | 含义 |
| --- | --- |
| TTFT | 首 token 延迟 |
| TPOT | 平均每个输出 token 时间 |
| output tokens/s | decode 阶段输出速度 |
| aggregate tokens/s | 并发总输出吞吐 |
| p50 / p95 / p99 latency | 延迟分位数 |
| GPU util | GPU 利用率 |
| VRAM | 显存占用 |
| power | GPU 功耗 |
| context length | 上下文长度 |
| cold start | 首次加载 / 首次请求耗时 |

## 当前结论

CUDA 机器上的优先级可以先按这个理解：

```text
生产高吞吐：vLLM / SGLang
NVIDIA 极致性能：TensorRT-LLM + Triton
Hugging Face 生态服务：TGI
Windows 本地 GGUF 基线：llama.cpp CUDA
个人开发易用入口：Ollama CUDA
```

对当前 `RTX 3080 12GB + Windows` 机器来说，最现实的第一步是：

```text
llama.cpp CUDA
```

它已经能在 Windows 原生环境下跑通 OpenAI-compatible API，并且 Qwen3-8B Q4_K_M 可以稳定放进显存。若后续要测生产 serving 能力，应优先修复 Docker 镜像拉取问题，再补 vLLM 和 SGLang。
