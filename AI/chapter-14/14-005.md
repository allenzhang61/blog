# vLLM 性能调优

大模型推理通常分成两个阶段：

- **Prefill**：一次处理完整 Prompt，生成 KV Cache。计算量大，偏计算密集。
- **Decode**：读取 KV Cache，每轮生成一个 Token。每轮计算量较小，但需要频繁访问显存，偏访存密集。

提高推理服务性能，本质上是在有限的 GPU 资源上更合理地安排不同请求的 Prefill 和 Decode，减少等待、空闲与 padding。

## 批处理

### 静态批处理（Static Batching）

先凑齐固定数量的请求，再把它们组成一个 Batch 一起执行。

```text
Batch 1: R1 R2 R3  ──────────> 等最慢的请求结束
Batch 2: R4 R5 R6  ──────────> 才能开始
```

同一个 Batch 中的请求生成长度不同。短请求已经结束时，仍要等待最长的请求，空出来的位置通常只能用 padding 填充。

主要问题：

- 必须等待凑齐一个 Batch，增加排队时间。
- 整个 Batch 由最慢的请求决定完成时间。
- 短请求完成后不能立即退出，产生 padding 和 GPU 空转。
- 新请求只能等待下一批，无法及时使用已经空出的计算槽位。

### 动态批处理（Dynamic Batching）

不再一直等待固定数量，而是在一个较短的时间窗口内收集请求；达到最大 Batch Size 或等待超时后立即执行。

```text
触发条件 = 请求数达到上限 OR 等待窗口超时
```

它减少了“为了凑满 Batch 一直等待”的问题，但 Batch 一旦开始执行，内部通常仍然要等这一批请求整体结束。因此，它改善了请求进入 Batch 的方式，却没有根除执行过程中的 padding 浪费。

### 持续批处理（Continuous Batching）

持续批处理也叫迭代级调度（Iteration-level Scheduling）。调度器不再等整个 Batch 完成，而是在每一轮 Decode 后重新检查请求：

- 已完成的请求立即退出。
- 新请求立即补入空出来的位置。
- Batch 中的请求集合可以不断变化。

```text
第 1 轮：[R1][R2][R3]
第 2 轮：[R1][R2][R3]
第 3 轮：[R1][R4][R3]  # R2 完成，R4 补入
第 4 轮：[R5][R4][R3]  # R1 完成，R5 补入
```

这样可以减少 padding，让 GPU 尽量保持满载，并降低新请求的排队时间。它是 vLLM 提高在线服务吞吐量的关键机制之一。

## Chunked Prefill

长 Prompt 的 Prefill 可能一次占用 GPU 很长时间。如果将它作为一个完整任务执行，正在 Decode 的其他请求就要等待，容易造成生成过程卡顿。

Chunked Prefill 将长 Prompt 拆成多个较小的 Chunk：

```text
未切分：
[----------- R1 Prefill -----------][R1 Decode]
                                     [R2 Decode]

切分后：
[R1 Prefill 1][R2 Decode][R1 Prefill 2][R2 Decode][R1 Prefill 3]
```

拆分后，调度器可以把 Prefill Chunk 与其他请求的 Decode 交错执行：

- 避免长 Prefill 长时间独占 GPU。
- 让已有请求的 Decode 更早得到调度，降低 Token 输出停顿。
- 更容易控制每轮调度的 Token 数量，平衡延迟与吞吐量。

Chunk 不是越小越好。过小会增加调度和 Kernel 启动开销；过大又会重新产生长 Prefill 阻塞 Decode 的问题，需要根据请求长度和延迟目标进行权衡。

## Prefill-Decode 分离（PD 分离）

Prefill 和 Decode 对 GPU 的使用特点不同：

| 阶段 | 主要特点 | 更关注的资源 |
|------|----------|--------------|
| Prefill | 并行处理大量 Prompt Token | 计算吞吐 |
| Decode | 每轮生成一个 Token，反复读取 KV Cache | 显存带宽与低延迟 |

PD 分离把两个阶段放到不同的 Worker：

```text
请求
  │
  ▼
Prefill Worker ── KV Cache ──> Decode Worker
  计算密集                      访存密集
```

这样可以：

- 避免长 Prefill 与 Decode 在同一张 GPU 上相互阻塞。
- 分别为两个阶段选择硬件、并发度和批处理策略。
- 独立扩缩容，例如 Prompt 很长时增加 Prefill Worker，生成很长时增加 Decode Worker。
- 更容易稳定 TTFT（Time To First Token）和 TPOT（Time Per Output Token）。

PD 分离并非没有成本。两个 Worker 之间必须传输 KV Cache，会增加网络带宽、传输延迟和系统复杂度。只有当请求规模较大、Prefill 与 Decode 的资源冲突明显时，收益才更容易覆盖这些额外开销。

## 总结

| 优化方式 | 主要解决的问题 | 核心思路 |
|----------|----------------|----------|
| 动态批处理 | 凑 Batch 等待时间过长 | 数量达到上限或等待超时就执行 |
| 持续批处理 | 请求长度不同导致 padding 和槽位空闲 | 每轮重新组批，完成即退出，新请求立即补入 |
| Chunked Prefill | 长 Prompt 阻塞其他请求 Decode | 将 Prefill 切块，与 Decode 交错调度 |
| PD 分离 | Prefill 与 Decode 争抢同一 GPU | 分别部署并传输 KV Cache |

实际调优不能只看总吞吐量，还要同时观察：

- **TTFT**：用户发送请求后，多久看到第一个 Token。
- **TPOT / ITL**：后续 Token 的平均生成间隔。
- **Throughput**：系统每秒处理的请求数或 Token 数。
- **P95 / P99 延迟**：高并发下慢请求的尾部延迟。

吞吐量与延迟通常需要权衡：更大的 Batch 往往能提高吞吐量，但也可能增加单个请求的等待时间。
