# Mac Studio 上可运行选项性能对比

> 这里整理 Mac Studio 上适合尝试的开源推理服务器/框架，并记录本机短时压测结果。

## 背景

Mac Studio 是 Apple Silicon 机器，主要依赖：

- CPU
- Apple GPU / Metal
- MLX
- 统一内存（Unified Memory）

它没有 NVIDIA CUDA，因此 CUDA/TensorRT 路线不是 Mac Studio 的主力选择。判断一个推理服务器是否适合 Mac Studio，重点看它是否支持 Apple Silicon、Metal、MLX、GGUF，或者至少能在 macOS 上作为上层服务框架运行。

## 推荐清单

| 推荐度 | 项目 | Mac Studio 支持情况 | 适合场景 | 备注 |
| --- | --- | --- | --- | --- |
| 强烈推荐 | Ollama | 原生支持 macOS / Apple Silicon | 本地开发、快速试模型、个人服务 | 上手最简单，适合作为第一选择 |
| 强烈推荐 | llama.cpp | 支持 Apple Silicon / Metal | GGUF 量化模型、CPU/GPU 本地推理、边缘部署 | 更底层，可控性更强，适合性能调优 |
| 可以尝试 | vLLM-Metal | Apple Silicon via vLLM-Metal | 想贴近 OpenAI-compatible serving、研究 continuous batching | 比 CUDA 版 vLLM 新，生态成熟度要单独验证 |
| 可以尝试 | SGLang MLX | Apple Silicon / MLX backend | 复杂推理、结构化输出、agent workflow | 适合尝鲜和研究，压测后再判断稳定性 |
| 可以尝试 | LocalAI | 可在 Mac 上跑，后端可接 llama.cpp/MLX 等 | 本地 OpenAI-compatible API、多模型统一入口 | 配置复杂度高于 Ollama |
| 上层框架 | Ray Serve | macOS 可安装 | 多模型 pipeline、复杂服务编排 | 底层推理仍需接 Ollama、llama.cpp、MLX 等 |
| 上层框架 | BentoML | macOS 可用 | Python API 封装、模型服务化 | 更偏服务封装，不是专门的 Mac LLM 推理引擎 |
| 平台层 | KServe | 可通过 kind/minikube 本地运行 | Kubernetes 模型服务平台 | 本地 Mac 可测试平台流程，不适合直接做单机 LLM 性能主力 |

## 不推荐作为 Mac Studio 主力

| 项目 | 原因 |
| --- | --- |
| TensorRT-LLM | 主要面向 NVIDIA GPU / TensorRT，Mac Studio 没有 CUDA。 |
| Triton Inference Server | 生产推理底座很强，但核心优势在 NVIDIA/TensorRT/ONNX 等服务端环境，本地 Mac Studio 不适合作主力 LLM 推理。 |
| Hugging Face TGI | 更偏 Linux/NVIDIA GPU 部署，Mac Studio 本地不是主流路线。 |
| TorchServe | 能服务 PyTorch 模型，但 LLM 本地推理体验通常不如 Ollama、llama.cpp、MLX 系工具。 |
| OpenVINO Model Server | 更偏 Intel 硬件生态。 |
| MLServer | 传统 ML serving 可以，LLM / Mac GPU 不是重点。 |

## 初步选择建议

如果只是本地开发和日常使用：

```text

```

如果想研究量化、上下文长度、KV cache、Metal 参数：

```text
llama.cpp
```

```text

```

```text

```

```text
Ollama / llama.cpp / vLLM-Metal + FastAPI
Ray Serve / BentoML
```

## 压测结果

本轮有效结果只取 warmup 后的正式请求，未把首次请求的模型加载、backend 初始化或 cache 初始化计入吞吐。单请求结果记录 decode 输出速度；并发结果记录所有并发请求合计的 aggregate 输出吞吐。

- Ollama：使用返回字段 `eval_count / eval_duration`，即 decode 阶段输出速度。
- vLLM-Metal / SGLang MLX / LocalAI：使用 `usage.completion_tokens / 请求总耗时` 估算输出速度。
- TTFT 使用 streaming 请求单独采集，取 `curl time_starttransfer` 作为首块响应时间的近似值；脚本会先做一次 streaming warmup，再测 5 次取 p50，避免把首次 streaming 路径懒初始化计入结果。单位为毫秒。
- `GPU active(%)` 通过 macOS `powermetrics` 采集 GPU active residency。该命令需要 sudo 权限；如果执行压测前没有 `sudo -v` 授权缓存，脚本会填 `未采集`。
- 内存使用按系统维度采集：先确认无 vLLM / SGLang / LocalAI / 压测脚本残留进程，再记录启动前和模型预热后的系统已用内存差值。系统已用内存近似按 `总内存 - free - speculative` 计算。
- LocalAI 返回的 `usage.prompt_tokens=1` 与其他服务 tokenizer 口径不一致，因此本轮只用 `completion_tokens=128` 计算输出吞吐，不用 `total_tokens` 比较总吞吐。

### GPU 与内存调优判断

本轮采集到的 SGLang MLX / vLLM-Metal GPU active 接近 95% 以上，因此当前瓶颈不应简单理解为“GPU 没吃满”。它们的主要差异在内存增量、batching 效果和 serving 调度策略。LLM decode 阶段即便 GPU active 很高，也仍然可能受这些因素限制：

- 每步只生成一个 token，矩阵计算规模较小，GPU kernel 难以长期打满。
- KV cache 读写和统一内存带宽可能比纯算力更关键。
- 单请求或低并发时 batch 太小，GPU active 可能已经不低，但 aggregate tokens/s 仍然上不去。
- vLLM-Metal / SGLang 为了降低延迟和支持 batching，可能预留较多内存，但这不等价于 GPU 计算利用率高。

更现实的调优方向是：

| 目标 | 做法 | 影响 |
| --- | --- | --- |
| 提高 tokens/s | 提高并发或 batch，例如 `CONCURRENCY_LIST="1 2 4 8"` | 通常能提高 aggregate tokens/s，但单请求延迟会上升。 |
| 控制内存 | 降低 context，例如 `CTX=1024` | KV cache 需求下降，长上下文能力变弱。 |
| 控制 vLLM-Metal 预分配 | 降低 `VLLM_METAL_MEMORY_FRACTION`，例如 `0.18`、`0.35` | 内存占用下降，但过低可能影响并发和稳定性。 |
| 降低模型内存 | 换更小模型或更激进量化 | tokens/s 可能上升，质量可能下降。 |
| 降低 serving 开销 | 对比 Ollama / llama.cpp / MLX direct | 接口能力会变少，但延迟可能更低。 |

因此，“提升 GPU 消耗并控制内存”不是一个单独开关能完成的事。下一步更应该在并发、context、KV cache 预分配和模型量化之间找平衡。可以重点试 `CONCURRENCY_LIST="1 2 4 8"`、`CTX=1024` 和更低的 `VLLM_METAL_MEMORY_FRACTION`。

### vLLM-Metal 内存优化

vLLM-Metal 这轮内存高的主要原因不是模型权重，而是 KV cache 预分配。日志里可以看到，未显式限制时它使用模型默认上下文：

```text
Using max model len 40960
KV cache: 30857.2 MB
Maximum concurrency for 40,960 tokens per request: 5.11x
```

而本轮压测实际只需要 `context=2048`。因此脚本已改成显式传入：

```bash
--max-model-len "$VLLM_MAX_MODEL_LEN"
--gpu-memory-utilization "$VLLM_GPU_MEMORY_UTILIZATION"
```

默认值为：

```text
VLLM_MAX_MODEL_LEN=2048
VLLM_METAL_MEMORY_FRACTION=0.18
```

本机短验证结果：

| 配置 | max model len | KV cache | 最大并发余量 |
| --- | ---: | ---: | ---: |
| 原始配置 | 40960 | 30857.2 MB | 5.11x / 40960 tokens |
| `fraction=0.35` | 2048 | 14177.0 MB | 46.95x / 2048 tokens |
| `fraction=0.18` | 2048 | 4713.9 MB | 15.61x / 2048 tokens |

对于当前 `CONCURRENCY_LIST="1 2 4"`、`CTX=2048` 的压测，`fraction=0.18` 仍然有足够 KV cache 余量。本轮重跑后，vLLM-Metal 的系统内存增量为约 16.0GB，明显低于旧参数下的 40.7GB。若后续要测试更长上下文或更高并发，再按需调大：

```bash
VLLM_MAX_MODEL_LEN=4096 VLLM_METAL_MEMORY_FRACTION=0.35 \
  AI/chapter-14/mac-server/bench_mac_servers.sh
```

### MLX 与 Mac GPU

MLX 是 Apple 开源的机器学习数组计算和模型推理框架，面向 Apple Silicon 做了优化。它可以使用 Mac 的统一内存，并通过 Metal 调用 Apple GPU。

本轮 `mlx-community/Qwen3-8B-4bit` 是 MLX 格式的 4bit 模型。LocalAI 的 `metal-mlx` backend、SGLang MLX、vLLM-Metal 都不是 CUDA 路线，而是走 Apple Silicon / Metal / MLX 相关能力。可以用下面的命令确认当前 MLX 默认设备：

```bash
AI/chapter-14/mac-server/localai/backends/metal-mlx/venv/bin/python - <<'PY'
import mlx.core as mx
print(mx.default_device())
PY
```

本机输出为：

```text
Device(gpu, 0)
```

这说明 MLX 默认会使用 Mac Studio 的 Apple GPU。需要注意的是，是否每个算子都完全跑在 GPU 上取决于 backend 和模型实现；但本轮使用的 MLX backend 不是纯 CPU 推理。

### LocalAI TTFT 优化判断

当前可以做的优化分两类：

| 方向 | 预期收益 | 说明 |
| --- | --- | --- |
| 关闭 LocalAI 非必要功能 | 很小 | 已在脚本中关闭 Web UI、metrics、gallery、MCP、agent 等，TTFT 基本不变。 |
| 改用 LocalAI `metal-llama-cpp` + GGUF | 可能改善 | llama.cpp / Metal 路线更成熟，但模型格式和量化口径会变，不再与 SGLang MLX / vLLM-Metal 完全同模型。 |
| 直接使用 SGLang MLX 或 vLLM-Metal | 明显改善 | 如果核心目标是低 TTFT 或高并发吞吐，本轮结果里这两者更适合。 |
| 继续用 LocalAI 做统一入口 | 接受较高 TTFT | LocalAI 更像多 backend 聚合层，优势是接口和模型入口统一，不是本轮 Mac Studio 上最低延迟的选择。 |

### SGLang MLX 修复结果

Qwen3.5 9B 在 SGLang MLX 上会触发 GDN / linear attention 相关初始化问题。切换到 Qwen3-8B 后，SGLang MLX 可以由统一压测脚本正常启动并完成请求：

```bash
SGLANG_MODEL="mlx-community/Qwen3-8B-4bit" \
  AI/chapter-14/mac-server/bench_mac_servers.sh
```

本轮实际返回 `/v1/chat/completions`，预热后结果为 `59.9 tok/s`。

### LocalAI 修复结果

已添加模型配置：

```text
AI/chapter-14/mac-server/localai/models/qwen3-8b-mlx.yaml
```

配置内容：

```yaml
name: qwen3-8b-mlx
backend: metal-mlx
parameters:
  model: mlx-community/Qwen3-8B-4bit
  temperature: 0
context_size: 2048
```

LocalAI 的 `metal-mlx` backend 原始 venv 中，`mlx_lm` 与 `transformers 5.13.0` 在本机导入时会报：

```text
AttributeError: 'str' object has no attribute '__module__'
```

处理方式是把 backend venv 的 `transformers` 固定到 4.x：

```bash
AI/chapter-14/mac-server/localai/backends/metal-mlx/venv/bin/python \
  -m pip install 'transformers<5'
```

修复后，LocalAI 可以加载 `mlx-community/Qwen3-8B-4bit`，并通过 `qwen3-8b-mlx` 对外提供 OpenAI-compatible API。

## 当前结论

Mac Studio 上优先考虑要分两种口径：

```text
单请求 decode 速度：vLLM-Metal / Ollama > LocalAI / SGLang MLX
并发总吞吐：SGLang MLX / vLLM-Metal > LocalAI / Ollama
```

在 Qwen3-8B 这个共同模型口径下，四个服务都已经跑通。当前脚本已统一为单模型、先预热、后压测；因此结果不再包含首次模型加载成本。vLLM-Metal 现在默认使用 `VLLM_MAX_MODEL_LEN=2048`、`VLLM_METAL_MEMORY_FRACTION=0.18`，避免按模型默认长上下文预留过大的 KV cache。具体单请求与并发结果统一见上面的压测结果表。

后续如果要比较冷启动耗时，可以单独记录首次 warmup 请求耗时；常规吞吐对比应继续使用当前这种 warm 后结果。若要模拟真实业务流量，还应补一轮更长时间、更多样 prompt、带 p50 / p95 / p99 latency 的压测。
