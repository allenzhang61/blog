# Mac Studio 上可运行选项性能对比

> 这里整理 Mac Studio 上适合尝试的开源推理服务器/框架，并记录本机短时压测结果。

## 背景

Mac Studio 是 Apple Silicon 机器，主要依赖：

- CPU
- Apple GPU / Metal
- MLX
- 统一内存（Unified Memory）

它没有 NVIDIA CUDA，因此 CUDA/TensorRT 路线不是 Mac Studio 的主力选择。判断一个推理服务器是否适合 Mac Studio，重点看它是否支持 Apple Silicon、Metal、MLX、GGUF，或者至少能在 macOS 上作为上层服务框架运行。

## 推荐清单

| 推荐度 | 项目 | Mac Studio 支持情况 | 适合场景 | 备注 |
| --- | --- | --- | --- | --- |
| 强烈推荐 | Ollama | 原生支持 macOS / Apple Silicon | 本地开发、快速试模型、个人服务 | 上手最简单，适合作为第一选择 |
| 强烈推荐 | llama.cpp | 支持 Apple Silicon / Metal | GGUF 量化模型、CPU/GPU 本地推理、边缘部署 | 更底层，可控性更强，适合性能调优 |
| 可以尝试 | vLLM-Metal | Apple Silicon via vLLM-Metal | 想贴近 OpenAI-compatible serving、研究 continuous batching | 比 CUDA 版 vLLM 新，生态成熟度要单独验证 |
| 可以尝试 | SGLang MLX | Apple Silicon / MLX backend | 复杂推理、结构化输出、agent workflow | 适合尝鲜和研究，压测后再判断稳定性 |
| 可以尝试 | LocalAI | 可在 Mac 上跑，后端可接 llama.cpp/MLX 等 | 本地 OpenAI-compatible API、多模型统一入口 | 配置复杂度高于 Ollama |
| 上层框架 | Ray Serve | macOS 可安装 | 多模型 pipeline、复杂服务编排 | 底层推理仍需接 Ollama、llama.cpp、MLX 等 |
| 上层框架 | BentoML | macOS 可用 | Python API 封装、模型服务化 | 更偏服务封装，不是专门的 Mac LLM 推理引擎 |
| 平台层 | KServe | 可通过 kind/minikube 本地运行 | Kubernetes 模型服务平台 | 本地 Mac 可测试平台流程，不适合直接做单机 LLM 性能主力 |

## 不推荐作为 Mac Studio 主力

| 项目 | 原因 |
| --- | --- |
| TensorRT-LLM | 主要面向 NVIDIA GPU / TensorRT，Mac Studio 没有 CUDA。 |
| Triton Inference Server | 生产推理底座很强，但核心优势在 NVIDIA/TensorRT/ONNX 等服务端环境，本地 Mac Studio 不适合作主力 LLM 推理。 |
| Hugging Face TGI | 更偏 Linux/NVIDIA GPU 部署，Mac Studio 本地不是主流路线。 |
| TorchServe | 能服务 PyTorch 模型，但 LLM 本地推理体验通常不如 Ollama、llama.cpp、MLX 系工具。 |
| OpenVINO Model Server | 更偏 Intel 硬件生态。 |
| MLServer | 传统 ML serving 可以，LLM / Mac GPU 不是重点。 |

## 初步选择建议

如果只是本地开发和日常使用：

```text
Ollama
```

如果想研究量化、上下文长度、KV cache、Metal 参数：

```text
llama.cpp
```

如果想贴近生产 LLM serving 接口：

```text
vLLM-Metal
```

如果想测试复杂推理工作流、结构化输出、agent 调用：

```text
SGLang MLX
```

如果只是需要把推理能力封装成服务：

```text
Ollama / llama.cpp / vLLM-Metal + FastAPI
Ray Serve / BentoML
```

## 待压测指标

后续压测时建议记录这些指标：

| 指标 | 含义 |
| --- | --- |
| TTFT | Time To First Token，首 token 延迟 |
| TPOT | Time Per Output Token，平均每个输出 token 用时 |
| tokens/s | 单请求生成吞吐 |
| 并发吞吐 | 多请求并发下总 tokens/s |
| p50 / p95 / p99 latency | 延迟分位数 |
| prompt tokens/s | Prefill 阶段处理速度 |
| output tokens/s | Decode 阶段生成速度 |
| 内存占用 | 进程内存、统一内存压力、是否触发 swap |
| 上下文长度 | 不同 context length 下的性能变化 |
| 模型加载时间 | 从启动到可服务的耗时 |

## 压测脚本

压测脚本放在：

```text
AI/chapter-14/mac-server/
```

当前已添加：

```text
AI/chapter-14/mac-server/bench_ollama.sh
AI/chapter-14/mac-server/bench_openai_compat.sh
```

默认压测本机已有的 Ollama MLX 模型：

```bash
AI/chapter-14/mac-server/bench_ollama.sh
```

默认只测本轮四个服务都跑通的共同模型：

```text
qwen3:8b
```

可以通过环境变量控制输出 token 数和 context：

```bash
MODEL="qwen3:8b" PREDICT=128 WARMUP_PREDICT=16 CTX=2048 \
  AI/chapter-14/mac-server/bench_ollama.sh
```

Ollama 脚本每次只压测一个模型：先 warmup 一次，再记录第二次正式压测结果。

结果会写到：

```text
AI/chapter-14/mac-server/results/
```

另外补充了 OpenAI-compatible API 压测脚本，可用于后续压测 vLLM-Metal、SGLang、LocalAI：

```bash
BASE_URL="http://127.0.0.1:8000/v1" MODEL="your-model-name" \
  AI/chapter-14/mac-server/bench_openai_compat.sh
```

OpenAI-compatible 脚本同样每次只压测一个模型，默认先发一次 16-token warmup 请求，再记录 128-token 正式请求，避免把首次请求的模型加载成本算入 tokens/s。

## 本机环境与本轮范围

本次压测环境：

| 项目 | 值 |
| --- | --- |
| 机器 | Mac Studio |
| CPU | Apple M4 Max |
| 内存 | 64GB 统一内存 |
| 系统 | macOS 26.5.2 |
| 推理服务 | Ollama / vLLM-Metal / SGLang MLX / LocalAI |
| context | 2048 |
| 输出长度 | 128 tokens |
| 预热 | 16 tokens，不计入结果 |
| 并发 | 1 |
| prompt | 中文短问题：说明 prefill 和 decode 的区别 |

原计划使用 Qwen3.5 9B，但 SGLang MLX 和 LocalAI 在该模型上分别遇到 GDN / tokenizer 兼容问题。为保证四个服务都能跑通，本轮切换到 Qwen3-8B：

| 服务 | 模型 |
| --- | --- |
| Ollama | `qwen3:8b` |
| vLLM-Metal | `mlx-community/Qwen3-8B-4bit` |
| SGLang MLX | `mlx-community/Qwen3-8B-4bit` |
| LocalAI | `qwen3-8b-mlx`，底层指向 `mlx-community/Qwen3-8B-4bit` |

说明：`qwen3:8b` 是 Ollama 本地模型名；后三者使用同等规模的 Hugging Face MLX 4bit 模型。

### SGLang MLX 修复结果

Qwen3.5 9B 在 SGLang MLX 上会触发 GDN / linear attention 相关初始化问题。切换到 Qwen3-8B 后，SGLang MLX 可以正常启动：

```bash
MODEL="mlx-community/Qwen3-8B-4bit" PORT=18011 \
  AI/chapter-14/mac-server/start_sglang_mlx.sh
```

本轮实际返回 `/v1/chat/completions`，预热后结果为 `59.9 tok/s`。

### LocalAI 修复结果

已添加模型配置：

```text
AI/chapter-14/mac-server/localai/models/qwen3-8b-mlx.yaml
```

配置内容：

```yaml
name: qwen3-8b-mlx
backend: metal-mlx
parameters:
  model: mlx-community/Qwen3-8B-4bit
  temperature: 0
context_size: 2048
```

LocalAI 的 `metal-mlx` backend 原始 venv 中，`mlx_lm` 与 `transformers 5.13.0` 在本机导入时会报：

```text
AttributeError: 'str' object has no attribute '__module__'
```

处理方式是把 backend venv 的 `transformers` 固定到 4.x：

```bash
AI/chapter-14/mac-server/localai/backends/metal-mlx/venv/bin/python \
  -m pip install 'transformers<5'
```

修复后，LocalAI 可以加载 `mlx-community/Qwen3-8B-4bit`，并通过 `qwen3-8b-mlx` 对外提供 OpenAI-compatible API。

## 当前结论

Mac Studio 上优先考虑：

```text
vLLM-Metal / Ollama > LocalAI / SGLang MLX
```

在 Qwen3-8B 这个共同模型口径下，四个服务都已经跑通。当前脚本已统一为单模型、先预热、后压测；因此结果不再包含首次模型加载成本。vLLM-Metal 这轮为避免 Metal OOM，将 `VLLM_METAL_MEMORY_FRACTION` 默认设为 `0.65`。

本轮有效短压测结果：

```text
vLLM-Metal mlx-community/Qwen3-8B-4bit: 80.9 tok/s
Ollama qwen3:8b: 80.5 tok/s
LocalAI qwen3-8b-mlx: 62.5 tok/s
SGLang MLX mlx-community/Qwen3-8B-4bit: 59.9 tok/s
```

后续如果要比较冷启动耗时，可以单独记录首次 warmup 请求耗时；常规吞吐对比应继续使用当前这种 warm 后结果。
