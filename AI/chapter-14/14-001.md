# 推理的流程和架构

## 两个阶段

LLM 推理分为两个计算特征截然不同的阶段：

```
输入 Prompt: "The capital of France is"
                    │
            ┌───────▼────────┐
            │   Prefill 阶段  │  一次性并行处理所有输入 token
            │  （compute bound）│  计算量大，GPU 利用率高
            └───────┬────────┘
                    │ 生成第一个 token："Paris"
            ┌───────▼────────┐
            │   Decode 阶段   │  每次只生成一个 token，自回归
            │  （memory bound）│  计算量小，瓶颈在显存带宽
            └───────┬────────┘
                    │ 逐个生成："," → "which" → "is" → ...
                    ▼
            输出完整序列
```

**Prefill**：将 prompt 中所有 token 一次性送入模型，并行计算，生成第一个输出 token，同时将所有 token 的 K/V 写入 KV Cache。决定 **TTFT（Time to First Token）**。

**Decode**：每步只取上一步生成的 token 作为输入，从 KV Cache 读取历史 K/V，生成下一个 token。重复直到遇到 EOS 或达到 max_tokens。决定**总生成时长**。

## Transformer 层内部计算

```
输入 Token Embeddings
        │
        ▼
┌─────────────────────────────────────────────┐
│           Transformer Layer × N              │
│                                             │
│  ┌──────────────────────────────────────┐   │
│  │           Self-Attention              │   │
│  │                                      │   │
│  │  Q = X · Wq                          │   │
│  │  K = X · Wk  ──→ 写入 KV Cache       │   │
│  │  V = X · Wv  ──→ 写入 KV Cache       │   │
│  │                                      │   │
│  │  Decode 时：                         │   │
│  │  K_all = [历史 K ; 新 K]             │   │
│  │  V_all = [历史 V ; 新 V]             │   │
│  │  Attn = softmax(Q · K_all^T) · V_all │   │
│  └──────────────────┬───────────────────┘   │
│                     │                       │
│  ┌──────────────────▼───────────────────┐   │
│  │              FFN (MLP)                │   │
│  │  up_proj → activation → down_proj    │   │
│  └──────────────────────────────────────┘   │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
            LM Head（线性层）→ logits（vocab_size 维）
                       │
                       ▼
            采样（temperature / top-p / top-k）→ 下一个 token
```

## KV Cache 的作用

Decode 阶段每步只有 1 个新 token，但 Attention 需要看到所有历史 token 的 K/V。
若不缓存，每步都要对整个序列重新计算，代价随序列长度平方增长。

```
不用 KV Cache：
  Step t：对 [t1, t2, ..., t] 全部重算 K/V → O(t²) 总计算量

用 KV Cache：
  Step 1：输入 [t1,t2,t3,t4]，计算并缓存 K/V[1..4]
  Step 2：输入 [t5]，复用 K/V[1..4]，只算 K/V[5]
  Step 3：输入 [t6]，复用 K/V[1..5]，只算 K/V[6]
  → 每步 O(1) 新计算，总体 O(n)
```

代价：KV Cache 随序列长度线性增长，长上下文的显存瓶颈主要来源于此。

## 完整推理架构（以 vLLM 为例）

```
外部请求
    │
    ▼
┌──────────────────────────────────────────────┐
│                 API Server                    │
│   OpenAI 兼容接口 /v1/completions             │
│   流式输出（SSE）/ 非流式                      │
└───────────────────┬──────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│              Scheduler（调度器）               │
│                                              │
│  三个队列：                                   │
│   waiting  → 等待 KV Cache 块分配             │
│   running  → 当前参与计算                     │
│   swapped  → KV Cache 被换出到 CPU            │
│                                              │
│  每个 decode step 决定：                      │
│   • 哪些 waiting 请求升级为 running           │
│   • KV Cache 块的分配与回收                   │
│   • 是否触发抢占（swap / recompute）           │
└───────────────────┬──────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│              Model Executor                   │
│                                              │
│  Prefill：prompt tokens 一次前向传播           │
│  Decode ：所有 running 请求各取最新 token，    │
│           合并成一个 batch 一起前向传播         │
└───────────────────┬──────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│            GPU（Transformer 模型）             │
│                                              │
│  显存布局：                                   │
│  ┌───────────────┬─────────────────────────┐ │
│  │   模型权重     │     KV Cache Pool        │ │
│  │   （静态）     │  PagedAttention 分页管理  │ │
│  └───────────────┴─────────────────────────┘ │
└──────────────────────────────────────────────┘
```

## Prefill vs Decode 性能特征

| | Prefill | Decode |
|--|---------|--------|
| 每步输入 | 整个 prompt（并行） | 单个新 token |
| 计算类型 | 矩阵 × 矩阵（GEMM） | 矩阵 × 向量（GEMV） |
| 瓶颈 | 计算（FLOP bound） | 显存带宽（Memory bound） |
| GPU 利用率 | 高 | 低 |
| 决定的指标 | TTFT | 总生成时长、TPOT |
| 主要优化手段 | FlashAttention、Chunked Prefill | Continuous Batching、投机解码 |

Decode 阶段 GPU 计算强度极低：每步只做一次矩阵向量乘，FLOP 消耗极少，大量时间花在将权重从 HBM（显存）搬运到计算单元。这是为什么大模型推理吞吐远低于 GPU 算力峰值的根本原因。

---

## 性能指标

| 指标 | 全称 | 含义 |
|------|------|------|
| TTFT | Time to First Token | 从请求到第一个 token 输出的延迟，由 Prefill 决定 |
| TPOT | Time Per Output Token | 每生成一个 token 的平均耗时，由 Decode 决定 |
| ITL | Inter-Token Latency | token 间的间隔，与 TPOT 相近 |
| Throughput | 吞吐量 | 单位时间内生成的 token 数（tok/s） |

---

## 影响推理性能的关键因素

```
TTFT 取决于：
  • prompt 长度（越长 prefill 越慢）
  • 服务端队列积压（等待调度的时间）
  • Chunked Prefill（将 prefill 拆块，与 decode 交织，降低 TTFT）

TPOT 取决于：
  • batch size（越大，单个 token 均摊的显存带宽越高，越划算）
  • 模型大小（权重越大，每步搬运的数据越多）
  • KV Cache 大小（序列越长，每步读取的 KV 越多）
  • 量化（FP8/INT4 减少权重体积，降低带宽压力）

吞吐取决于：
  • 并发请求数（max_num_seqs）
  • KV Cache 容量（决定最大并发上限）
  • Continuous Batching（动态填充空闲槽位）
```
