# 多平台验证 GDS：NVMe 到 GPU VRAM

## 背景

目标是验证在云 GPU 机器上能否跑通 NVIDIA GPUDirect Storage（GDS），也就是让本地 NVMe SSD 的数据尽量绕过 CPU 内存中转，直接进入 GPU VRAM。

前面在 WSL2 / Colab 的判断是：

- WSL2 不适合做真正的 GDS direct path，因为缺少完整 Linux 宿主内核、NVMe、GPU 驱动模块链路。
- Colab 也不适合，因为无法控制宿主内核模块、存储拓扑和 `nvidia-fs`。
- vast.ai 看起来更有希望，因为可以租到 Linux 主机、独占 GPU、本地 NVMe 和较高权限容器。

因此先在 vast.ai 上实际租机器验证，随后又阶段性调研/尝试了 AWS、Azure、Vultr、GPU.ai 等平台。

## GDS 能跑通的关键条件

单看 GPU 支持 GDS 不够，还需要宿主和容器同时满足：

1. 宿主安装并加载 `nvidia-fs` 内核模块。
2. 容器内可见 `/dev/nvidia-fs`。
3. 容器内可访问 GDS 支持的本地 NVMe/block device 或对应文件系统挂载。
4. `gdscheck.py -p` 中 `NVMe` / 对应文件系统显示 `Supported`。
5. `gdsio -x 0` 能跑通，其中 `-x 0` 表示 `Storage -> GPU (GDS)`。

如果只看到 `libcufile.so`，并不代表 direct path 可用。`libcufile` 是用户态库，真正的 direct path 还依赖 `nvidia-fs` 和存储设备路径。

## 实测机器

### 1. L40S

第一台机器：

```text
GPU: NVIDIA L40S, 46068 MiB
Driver: 580.65.06
NVMe: SAMSUNG MZQL21T9HCJR-00B7C，多块 NVMe
文件系统: overlay / XFS
```

基础硬件看起来不错，`lsblk` 能看到宿主上的多块 Samsung NVMe，GPU 也是数据中心卡。

检查结果：

```text
/dev/nvidia-fs: 不存在
lsmod: 没有 nvidia_fs
modprobe nvidia-fs:
  Module nvidia-fs not found in directory /lib/modules/5.15.0-186-generic
容器内没有 /dev/nvme* /dev/md*
```

安装 `nvidia-gds-12-8` 时，`gds-tools` 能装上，但 `nvidia-fs` / DKMS 相关包无法在容器里完成配置，因为它需要宿主内核模块和 headers。

`gdscheck.py -p` 关键输出：

```text
NVMe P2PDMA        : Unsupported
NVMe               : Unsupported
properties.use_compat_mode : true

GPU index 0 NVIDIA L40S supports GDS
IOMMU: disabled
Platform verification succeeded
```

这说明 GPU 和平台检查能过，但存储 direct path 不支持，cuFile 会落到兼容模式。

实际 `gdsio`：

```text
CPU-only 写入: 5.94 GiB/s
GDS 读取 -x 0: file register error: internal error
```

结论：L40S 机器硬件支持 GDS，但 vast 容器没有暴露 GDS 所需的内核模块和设备节点，不能跑通真正的 `Storage -> GPU`。

### 2. A100 SXM4

第二台机器换成 A100，并尝试加 Docker 参数：

```text
--env='--privileged'
```

机器信息：

```text
GPU: NVIDIA A100-SXM4-40GB
Driver: 595.58.03
NVMe: INTEL SSDPF2KX038TZ
文件系统: overlay / XFS
```

加了 `--privileged` 后，`lsblk` 能看到宿主 NVMe 拓扑：

```text
nvme1n1 INTEL SSDPF2KX038TZ
nvme2n1 INTEL SSDPF2KX038TZ
```

但真正的设备节点仍不可用：

```text
/dev/nvidia-fs: 不存在
/dev/nvme*: 不存在
/dev/md*: 不存在
lsmod: 没有 nvidia_fs
```

只安装轻量的 `gds-tools-12-8` 后跑 `gdscheck.py -p`，关键输出：

```text
NVMe P2PDMA        : Unsupported
NVMe               : Unsupported
properties.use_compat_mode : true

GPU index 0 NVIDIA A100-SXM4-40GB supports GDS
IOMMU: Pass-through or Enabled
WARN: GDS is not guaranteed to work functionally or in a performant way with iommu=on/pt
Nvidia Driver Info Status: Supported(Nvidia Open Driver Installed)
Platform verification succeeded

modprobe nvidia-fs:
  Module nvidia-fs not found in directory /lib/modules/5.15.0-179-generic
```

结论：`--privileged` 能让容器看到更多拓扑信息，但仍没有 `/dev/nvidia-fs` 和 block device 节点，GDS direct path 不可用。

### 3. H100 NVL

第三台换成 H100 NVL，也是 `hosting_type=1`，并继续尝试 `--privileged`。

机器信息：

```text
GPU: NVIDIA H100 NVL, 95830 MiB
Driver: 580.173.02
NVMe: MTFDKCC7T6TGP-1BK1DABYY
文件系统: overlay / XFS
```

检查结果与 A100 类似：

```text
/dev/nvidia-fs: 不存在
/dev/nvme*: 不存在
/dev/md*: 不存在
lsmod: 没有 nvidia_fs
```

`gdscheck.py -p` 关键输出：

```text
NVMe P2PDMA        : Unsupported
NVMe               : Unsupported
properties.use_compat_mode : true

GPU index 0 NVIDIA H100 NVL supports GDS
IOMMU: disabled
Nvidia Driver Info Status: Supported only on (nvidia-fs version <= 2.17.4)
Platform verification succeeded

modprobe nvidia-fs:
  Module nvidia-fs not found in directory /lib/modules/6.8.0-134-generic
/dev/nvidia-fs:
  No such file or directory
```

结论：即使换到 H100 NVL，GPU 本身支持 GDS，平台检查也能过，但 NVMe 仍是 `Unsupported`，仍然走兼容模式，不能做真正的 NVMe 到 GPU VRAM DMA。

## 总结

这次共实测三类机器：

| GPU | 是否加 privileged | GPU 是否支持 GDS | `/dev/nvidia-fs` | `NVMe` | 结果 |
|-----|-------------------|------------------|------------------|--------|------|
| L40S | 否 | 是 | 无 | Unsupported | `gdsio -x 0` 失败 |
| A100 SXM4 | 是 | 是 | 无 | Unsupported | 只能兼容模式 |
| H100 NVL | 是 | 是 | 无 | Unsupported | 只能兼容模式 |

最终结论：

**vast.ai 默认实例形态不适合做真正的 GPUDirect Storage direct path 实验。**

原因不是 GPU 不支持，而是容器环境没有提供完整的宿主 GDS 内核面：

- 没有加载 `nvidia-fs`。
- 容器里没有 `/dev/nvidia-fs`。
- 容器里没有可直接访问的 `/dev/nvme*` / `/dev/md*` block device。
- 文件路径落在 Docker `overlay` 上。
- `gdscheck.py -p` 虽然显示 GPU supports GDS、Platform verification succeeded，但存储侧 `NVMe` 仍是 `Unsupported`。
- `properties.use_compat_mode=true`，说明 cuFile 会走兼容路径，而不是 direct path。

因此，即使租到 L40S / A100 / H100 / H200 这类高端 NVIDIA GPU，也不能默认认为可以做：

```text
NVMe SSD -> GPU VRAM
```

真正要验证这条路径，应该优先找可控 native Linux 裸机，或者明确要求供应商提供：

```text
host 已安装并加载 nvidia-fs
容器内可见 /dev/nvidia-fs
容器内可访问实际 NVMe/block device
gdscheck.py -p 显示 NVMe: Supported
gdsio -x 0 能跑通
```

没有这些条件，GDS 用户态库存在也只能说明 cuFile API 可用，不能说明磁盘到 GPU 显存的 DMA 路径真的可用。

### 本地购买 GPU：可学习，不保证 GDS

如果购买消费级 GPU，例如 RTX 5070 Ti，并安装 Linux 裸机：

```text
可以体验:
  CUDA
  模型推理
  safetensors mmap
  pinned memory + async H2D
  本地 NVMe 读取
  尝试安装 nvidia-gds / 跑 gdscheck

不保证:
  NVMe SSD -> GPU VRAM direct DMA
```

原因是 GeForce 消费卡通常不是 GDS 的主要支持目标，BAR1 / PCIe P2P / 驱动支持路径都不如数据中心卡稳定。

更适合购买来尝试 GDS 的便宜数据中心/专业卡：

| GPU | 显存 | 适合度 | 备注 |
|-----|------|--------|------|
| A10 / A10G | 24GB | 入门 | 真数据中心卡，便宜但显存小 |
| L4 | 24GB | 入门 | 低功耗，推理好，显存小 |
| RTX A6000 | 48GB | 推荐 | 工作站友好，主动散热，价格相对可控 |
| RTX 6000 Ada | 48GB | 推荐但贵 | 专业卡，性能强 |
| A40 | 48GB | 推荐 | 数据中心卡，多为被动散热 |
| L40 / L40S | 48GB | 更适合 | 数据中心 Ada，推理强 |
| A100 PCIe | 40GB/80GB | 最正统 | 更接近官方 GDS 目标平台，但贵 |

如果目标是“便宜且实用”，优先考虑：

```text
RTX A6000 48GB
```

如果目标是“更像 GDS 正统平台”，优先考虑：

```text
A40 / L40S / A100 PCIe
```

但 A40/L40S/A100 很多是被动散热，普通机箱不能直接用，需要服务器风道。

## 当前阶段性结论

截至目前：

| 平台 | 状态 | 结论 |
|------|------|------|
| WSL2 | 已判断 | 不适合真正 GDS direct path |
| Colab T4 | 已判断 | 不适合，无法控制内核/存储拓扑 |

| AWS | 待定 | DryRun 通过，真实创建卡 quota/容量 |
| Azure | 待定 | 有希望，未实测 |

| Vultr | 待定 | bare metal GPU 需 support 解锁 |

| 自建 Linux + 专业/数据中心卡 | 可行方向 | 成功率取决于 GPU/主板/驱动/NVMe 拓扑 |

最值得继续推进的路线：

1. **AWS p5.4xlarge**：等 `ap-northeast-1` 的 `Running On-Demand P instances` quota 批准到 16 后再试。
2. **Azure NC40ads_H100_v5**：申请 quota 后实测。
3. **Vultr bare metal GPU**：等 support 解锁 `vbm-112c-2048gb-8-a100-gpu` 后实测。
4. **自建 Linux 裸机 + RTX A6000/A40/L40S/A100**：如果长期研究 GDS，这是最可控路线。
