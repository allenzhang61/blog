# 推理加速优化：KV Cache

## 背景

模型加载耗时已通过 mmap 懒加载优化（见 `1.md`）。本篇针对**推理（生成）阶段**：在纯 CPU、fp32 下，8B 模型逐 token 生成较慢，目标是在不改变输出结果的前提下降低生成耗时。

## 优化前的做法与瓶颈

原始生成循环每生成一个新 token，都把**已生成的完整序列**从头前向一遍：

```python
for _ in range(max_new_tokens):
    logits = model(generated)          # generated 每步都变长
    next_id = sample(logits[:, -1, :])
    generated = cat([generated, next_id])
```

瓶颈：生成第 n 个 token 时要重新计算前 n-1 个位置的注意力，而这些位置的 K/V 在之前的步骤里早已算过。整体是 **O(n²)** 的重复计算，序列越长、生成越多，浪费越严重。

## 优化后的做法：KV Cache

核心思想：缓存每层已计算的 K/V，生成时把过程分成两个阶段：

1. **Prefill（预填充）**：喂入完整 prompt，做一次全量前向，得到每层的 K/V 缓存和最后一个位置的 logits。
2. **增量解码（decode）**：之后每步只前向**1 个新 token**，其 K/V 与缓存拼接，历史部分不再重算。每步计算量近似恒定，整体降到近似 **O(n)**。

### 关键实现点

- **透传缓存**：`SimpleLLM` / `DecoderLayer` / `SelfAttention` 的 forward 增加 `past_kv`（历史 K/V）与 `position_offset`（当前输入在完整序列中的起始位置）参数，逐层返回更新后的缓存。
- **RoPE 位置正确性**：增量步只有 1 个新 token，必须用它在完整序列中的**绝对位置**取旋转位置编码的 sin/cos（用 `position_offset` 切片），否则位置会错。
- **KV 拼接**：新算的 K/V 与 `past_kv` 在序列维拼接，形成完整历史；缓存中保存的是 GQA 展开前的 `num_key_value_heads` 份 K/V，节省内存。
- **causal mask 简化**：prefill（seq_len>1）仍需下三角 mask；增量步（seq_len==1）新 token 可见全部历史，无需 mask。
- **兼容性**：`use_cache=False` 时保持原有返回值和行为，旧的一次性前向调用不受影响；生成侧保留 `--no-kv-cache` 基线开关便于对比。
- **正确性保证**：贪心解码下，开/关 KV Cache 的输出逐 token 完全一致，说明是纯加速、无精度损失。

## 关键代码位置

- `model/SelfAttention.py`：`forward(x, past_kv, position_offset)` —— 拼接历史 K/V、按绝对位置取 RoPE、增量步跳过 mask、返回新缓存。
- `model/DecoderLayer.py` / `model/SimpleLLM.py`：透传缓存与位置偏移；`use_cache` 控制是否返回缓存。
- `generate/generate.py`：`_generate_with_cache`（prefill + 增量解码）与 `_generate_no_cache`（基线）。
- `main.py`：`--no-kv-cache` 开关。

## 效果（CPU，8B，fp32，greedy，生成 32 tokens）

| 场景 | 无 KV Cache | 有 KV Cache | 加速 |
|------|------------|------------|------|
| 短 prompt（约 5 tokens） | 31.91s | 13.07s | **2.44x** |
| 长 prompt（约 70 tokens） | 33.49s | 9.68s | **3.46x** |

两种方案在贪心解码下输出逐字相同，正确性一致。

## 关键观察

- **有 KV Cache 时，长 prompt 反而更快**（9.68s < 13.07s）：增量解码每步只算 1 个新 token，与历史长度关系很小；prompt 长只影响一次性的 prefill，而 prefill 是并行的一次前向，成本很低。
- **无 KV Cache 时，长 prompt 更慢**：每生成一个 token 都要重算"整个 prompt + 已生成"，序列越长每步越贵。
- **prompt 越长、生成越多，加速比越高**：无 cache 是 O(n²)，有 cache 近似 O(n)。

## 补充：dtype 在 CPU 上的实测（非本次优化，供参考）

同机 CPU 上对比 fp32 / fp16 / bf16，结论是 **CPU 上 fp32 最快，半精度均为负优化**：CPU 缺乏原生半精度计算单元，半精度矩阵运算需在 fp32 与半精度间来回转换，反而更慢。半精度的提速需依赖具备 fp16/bf16 硬件单元的 GPU。
