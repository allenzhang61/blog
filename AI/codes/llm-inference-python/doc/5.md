# Qwen3.5-4B 推理耗时分阶段拆解与 llama.cpp 对比

## 测试口径

这次目标是把 Python / Transformers 路径的推理耗时拆细，并和 llama.cpp 在同一台 RTX 3080 上的 GGUF 推理做对比。

环境：

```text
host:  
WSL distro: Ubuntu-D
project: /home/zyl/llm-inference-python
GPU: NVIDIA GeForce RTX 3080 12GB
prompt: 介绍一下 TCP 三次握手
input tokens: 15
generated tokens: 64
decoding: greedy
```

Python 路径使用当前优化后的入口：

```text
AutoModelForCausalLM + AutoTokenizer
dtype: float16
device: cuda
KV cache: dynamic cache
```

llama.cpp 路径使用：

```text
llama-bench
CUDA backend
-ngl 99
-fa on
load_mode=mmap
KV cache: f16/f16
```

注意：Python 路径可以拆出 tokenizer、input copy、prefill、decode、sample、CPU gap、text decode 等阶段；llama.cpp 的 `llama-bench` 主要拆出 prompt processing / prefill 与 token generation / decode，不直接拆 tokenizer、采样和 CPU gap。

## Python 全量耗时拆解

### 未预热口径

命令：

```bash
python main.py \
  --prompt '介绍一下 TCP 三次握手' \
  --device cuda \
  --dtype float16 \
  --max-new-tokens 64 \
  --greedy \
  --cache-dir /home/zyl/hf-cache \
  --profile-timing
```

结果：

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 模型加载 | 10.91s | 加载 tokenizer、配置和 FP16 权重到 GPU |
| tokenize | 0.0161s | chat template + tokenizer |
| input_to_device | 0.0005s | input ids / attention mask 搬到 GPU |
| prefill | 0.9080s | 输入 15 token，建立第一轮 KV cache |
| decode_model_total | 3.0208s | 后续 token 的模型 forward，总计 63 次增量 decode |
| decode_model_avg | 47.95ms/token | 每个 decode token 的模型 forward 平均耗时 |
| decode_model_min | 32.98ms | 最快单 token forward |
| decode_model_max | 95.64ms | 最慢单 token forward |
| sample_total | 0.0139s | argmax / 采样总耗时 |
| sample_avg | 0.217ms/token | 每 token 采样耗时 |
| CPU gap total | 0.0023s | 每轮 decode 之间 CPU 空隙总和 |
| CPU gap avg | 0.036ms/token | CPU 调度 gap 很小 |
| text_decode | 0.0002s | token ids 转文本 |
| 推理 wall time | 3.95s | `--profile-timing` 整体推理计时 |
| decode speed | 21.09 tok/s | 按 decode + sample 计算 |

从这个拆解看，Python 路径的主要耗时不是 tokenizer、采样、CPU gap 或文本 decode，而是：

```text
decode_model_total: 3.0208s
decode_model_avg: 47.95ms/token
```

也就是每个新 token 的模型 forward。

### 预热后口径

为尽可能对齐 `llama-bench` 的重复运行口径，Python 侧新增了 `--warmup-runs` 参数。预热会在 tokenizer 和 input_to_device 之后、正式推理计时之前，按同一条生成路径先跑 N 次；预热耗时单独记录，不计入 `infer_wall_s`。

命令：

```bash
python main.py \
  --prompt '介绍一下 TCP 三次握手' \
  --device cuda \
  --dtype float16 \
  --max-new-tokens 64 \
  --greedy \
  --cache-dir /home/zyl/hf-cache \
  --profile-timing \
  --warmup-runs 1
```

结果：

| 阶段 | 未预热 | 预热 1 次后 | 变化 |
|------|--------|-------------|------|
| prefill | 0.9080s | 0.0510s | 大幅下降 |
| decode_model_total | 3.0208s | 2.4953s | 下降约 17.4% |
| decode_model_avg | 47.95ms/token | 39.61ms/token | 下降约 17.4% |
| sample_total | 0.0139s | 0.0063s | 下降 |
| CPU gap total | 0.0023s | 0.0028s | 基本不变 |
| 推理 wall time | 3.95s | 2.56s | 下降约 35.1% |
| decode speed | 21.09 tok/s | 25.58 tok/s | 提升约 21.3% |

预热后 `prefill` 从 0.9080s 降到 0.0510s，说明原来的 prefill 统计里混入了大量冷启动成本，例如 CUDA lazy init、allocator/cache 初始化、kernel autotune/JIT 等。decode 也有改善，但改善幅度明显小于 prefill，说明 decode 慢仍主要是每 token forward 的执行效率问题。

### decode_model 进一步拆分

`decode_model_total` 是 63 次增量 decode 的模型 forward 总和，也就是生成第 2 到第 64 个 token 时，每次只输入 1 个新 token，并复用已有 KV cache。

这部分是 Python / Transformers 路径的 token 级统计。

按 token 统计：

| 指标 | 数值 |
|------|------|
| decode forward 次数 | 63 |
| 总耗时 | 3.0208s |
| 平均 | 47.95ms/token |
| min | 32.98ms |
| p50 | 36.53ms |
| p90 | 74.05ms |
| p95 | 78.72ms |
| max | 95.64ms |

耗时分布：

| 区间 | token 数 |
|------|----------|
| `< 40ms` | 36 |
| `40ms - 60ms` | 11 |
| `60ms - 80ms` | 13 |
| `>= 80ms` | 3 |

前 16 个 decode token 的模型 forward 耗时：

```text
85.24ms, 76.82ms, 39.08ms, 35.94ms,
37.59ms, 43.35ms, 71.79ms, 36.10ms,
74.56ms, 35.79ms, 58.78ms, 95.64ms,
38.33ms, 63.30ms, 54.56ms, 35.16ms
```

最后 16 个 decode token 的模型 forward 耗时：

```text
34.33ms, 70.35ms, 47.98ms, 44.79ms,
74.05ms, 35.31ms, 35.66ms, 36.53ms,
34.36ms, 35.65ms, 35.74ms, 55.07ms,
60.10ms, 48.24ms, 36.40ms, 35.55ms
```

可以看到，decode 并不是每个 token 都稳定在 48ms 左右。更常见的单 token forward 是 35ms 到 40ms，少量 70ms 到 95ms 的慢 token 把平均值拉高。`sample_total` 只有 13.90ms，`CPU gap total` 只有 2.28ms，所以更细看之后结论仍然一样：慢点主要在模型 forward 内部，而不是采样或 Python 循环间隙。

llama.cpp 的 `llama-bench` 没有输出逐 token 的内部 forward 耗时，只输出每轮 64-token decode 的样本。按 5 次样本换算：

| 指标 | Python / Transformers FP16 | llama.cpp BF16 |
|------|-----------------------------|----------------|
| 统计粒度 | 预热 1 次后，63 次逐 token forward | 5 次 64-token decode run |
| decode 总耗时 | 2.4953s model forward / 2.5016s 含 sample | 0.8049s |
| 每 token 平均 | 39.61ms | 12.58ms |
| min | 32.61ms | 12.55ms |
| p50 | 34.49ms | 12.58ms |
| p90 | 63.30ms | 12.61ms |
| max | 92.20ms | 12.61ms |
| decode 速度 | 25.58 tok/s | 79.5 tok/s |

llama.cpp BF16 的 5 次 64-token decode 样本：

```text
0.803315s, 0.803942s, 0.805495s, 0.806870s, 0.804892s
```

换算到每 token：

```text
12.55ms, 12.56ms, 12.59ms, 12.61ms, 12.58ms
```

因此 llama.cpp 不只是平均更快，而且 run 级波动很小；Python / Transformers 这边则有明显长尾 token。

Top CUDA / kernel 里主要看到：

```text

```

这说明 Python / Transformers 路径慢的核心不是外围逻辑，而是 batch=1 decode 场景下大量小粒度 linear / matmul / GEMM / GEMV 调度和 kernel launch 开销。

## 结论

Python / Transformers 路径已经确认：

- tokenizer、input copy、sample、CPU gap、text decode 都不是主要瓶颈。
- 主要瓶颈是每 token 的模型 forward。
- 未预热时，64 token decode 大约是 3.02s，约 21 tok/s。
- 预热 1 次后，64 token decode 大约是 2.50s，约 25.6 tok/s。

llama.cpp 路径：

- BF16 GGUF 在同一张 3080 上 decode 约 79.5 tok/s。

因此即使按预热后的高精度口径对比，llama.cpp decode 也大约是 Python / Transformers 的 3.11 倍。预热可以解释大部分 prefill 差距，也能改善一部分 decode 长尾，但不能消除 batch=1 decode 下 PyTorch / Transformers 的小 GEMM、kernel launch、通用调度和 KV cache 管理开销。要继续逼近 llama.cpp，单靠 Transformers `generate()` 开关空间有限，更现实的方向是使用专用推理 runtime，例如 llama.cpp server、vLLM、SGLang、TensorRT-LLM 或 ExLlamaV2。
