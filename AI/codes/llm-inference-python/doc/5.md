# Qwen3.5-4B 推理耗时分阶段拆解与 llama.cpp 对比

## 测试口径

这次目标是把 Python / Transformers 路径的推理耗时拆细，并和 llama.cpp 在同一台 RTX 3080 上的 GGUF 推理做对比。

环境：

```text
host:  
WSL distro: Ubuntu-D
project: /home/zyl/llm-inference-python
GPU: NVIDIA GeForce RTX 3080 12GB
prompt: 介绍一下 TCP 三次握手
input tokens: 15
generated tokens: 64
decoding: greedy
```

Python 路径使用当前优化后的入口：

```text
AutoModelForCausalLM + AutoTokenizer
dtype: float16
device: cuda
KV cache: dynamic cache
```

llama.cpp 路径使用：

```text
llama-bench
CUDA backend
-ngl 99
-fa on
load_mode=mmap
KV cache: f16/f16
```

注意：Python 路径可以拆出 tokenizer、input copy、prefill、decode、sample、CPU gap、text decode 等阶段；llama.cpp 的 `llama-bench` 主要拆出 prompt processing / prefill 与 token generation / decode，不直接拆 tokenizer、采样和 CPU gap。

## Python 全量耗时拆解

命令：

```bash
python main.py \
  --prompt '介绍一下 TCP 三次握手' \
  --device cuda \
  --dtype float16 \
  --max-new-tokens 64 \
  --greedy \
  --cache-dir /home/zyl/hf-cache \
  --profile-timing
```

结果：

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 模型加载 | 10.91s | 加载 tokenizer、配置和 FP16 权重到 GPU |
| tokenize | 0.0161s | chat template + tokenizer |
| input_to_device | 0.0005s | input ids / attention mask 搬到 GPU |
| prefill | 0.9080s | 输入 15 token，建立第一轮 KV cache |
| decode_model_total | 3.0208s | 后续 token 的模型 forward，总计 63 次增量 decode |
| decode_model_avg | 47.95ms/token | 每个 decode token 的模型 forward 平均耗时 |
| decode_model_min | 32.98ms | 最快单 token forward |
| decode_model_max | 95.64ms | 最慢单 token forward |
| sample_total | 0.0139s | argmax / 采样总耗时 |
| sample_avg | 0.217ms/token | 每 token 采样耗时 |
| CPU gap total | 0.0023s | 每轮 decode 之间 CPU 空隙总和 |
| CPU gap avg | 0.036ms/token | CPU 调度 gap 很小 |
| text_decode | 0.0002s | token ids 转文本 |
| 推理 wall time | 3.95s | `--profile-timing` 整体推理计时 |
| decode speed | 21.09 tok/s | 按 decode + sample 计算 |

从这个拆解看，Python 路径的主要耗时不是 tokenizer、采样、CPU gap 或文本 decode，而是：

```text
decode_model_total: 3.0208s
decode_model_avg: 47.95ms/token
```

也就是每个新 token 的模型 forward。

PyTorch profiler trace：


注意：启用 PyTorch profiler 后，推理 wall time 从干净计时的 3.95s 增加到 19.65s，因此 profiler 结果只适合看算子分布，不适合当真实推理耗时。

Top aten 算子：

| 算子 | 累计耗时 |
|------|----------|
| `aten::linear` | 1017ms |
| `aten::matmul` | 988ms |
| `aten::mm` | 754ms |
| `aten::to` | 455ms |
| `aten::_to_copy` | 427ms |
| `aten::copy_` | 361ms |
| `aten::add` | 297ms |
| `aten::mul` | 260ms |
| `aten::bmm` | 90ms |

Top CUDA / kernel 里主要看到：

```text
cudaLaunchKernel
cublas / cutlass fp16 GEMM
gemv2T kernel
Triton JIT / autotuner / cache
```

这说明 Python / Transformers 路径慢的核心不是外围逻辑，而是 batch=1 decode 场景下大量小粒度 linear / matmul / GEMM / GEMV 调度和 kernel launch 开销。

## 结论

Python / Transformers 路径已经确认：

- tokenizer、input copy、sample、CPU gap、text decode 都不是主要瓶颈。
- 主要瓶颈是每 token 的模型 forward。
- 当前 64 token decode 大约是 3.02s，约 21 tok/s。

llama.cpp 路径：

- BF16 GGUF 在同一张 3080 上 decode 约 79.5 tok/s。
- Q8_0 约 118.3 tok/s。
- Q4_K_M 约 149.5 tok/s。

因此即使按 BF16 高精度口径对比，llama.cpp decode 也大约是 Python / Transformers 的 3.77 倍。要继续逼近 llama.cpp，单靠 Transformers `generate()` 开关空间有限，更现实的方向是使用专用推理 runtime，例如 llama.cpp server、vLLM、SGLang、TensorRT-LLM 或 ExLlamaV2。
