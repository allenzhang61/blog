# Qwen3.5 推理流程：prefill 和 decode

这篇记录当前 `llm-inference-cpp` 中 CUDA 推理路径的主流程。代码入口主要在：

- `src/main.cpp`：解析参数、加载配置和权重、创建 `QwenModel`
- `src/model/QwenModel.cpp`：组织一次生成过程
- `src/kernels/cuda/cuda_ops.cpp`：执行 CUDA kernel / cuBLAS 计算

当前项目只保留 CUDA 路径，不再保留 CPU fallback。CUDA 路径失败时直接抛异常，避免静默走到慢路径导致性能或行为难以判断。

## 总体流程

一次生成分成两个阶段：

```text
prompt token ids
    |
    v
prefill: 一次性处理完整 prompt，建立 attention cache，得到最后一个 prompt token 的 hidden
    |
    v
decode: 根据当前 hidden 生成下一个 token，再把这个 token 喂回模型，循环生成 max_new_tokens
```

对应代码在 `QwenModel::generate()`：

```text
1. 分配 generated token 的 CUDA buffer
2. 调用 cuda_prefill_batch(...) 处理 prompt
3. 对 prefill 返回的最后一个 hidden 做 final norm + logits argmax，得到第 1 个新 token
4. 如果还要继续生成，把刚生成的 token 留在 device 上，调用 forward_token_device(...)
5. 重复第 3-4 步，直到生成 max_new_tokens
6. 一次性把 generated ids 从 device 拷回 host
```

## RunState 的作用

`RunState` 保存一次生成过程中的跨 token 状态：

```text
RunState
  seq_len: 已经处理过的 token 数
  linear:  每层 linear attention 的 CUDA recurrent state
  full:    每层 full attention 的 CUDA KV cache
```

这些状态在 prefill 阶段初始化并写入，在 decode 阶段继续追加更新。

对于 full attention，`FullAttentionState::max_seq_len` 会按 `input_tokens + max_new_tokens + 4` 预留 cache 空间。这样 decode 每生成一个 token，只需要把当前位置的 K/V 写入 cache，不需要重新计算历史 token。

## Prefill 流程

prefill 处理的是输入 prompt，例如当前默认 prompt 有 15 个 token。它的目标不是马上生成很多 token，而是：

1. 把 prompt 的每个 token 都过一遍模型。
2. 建好 linear attention 的 recurrent state。
3. 建好 full attention 的 KV cache。
4. 返回最后一个 prompt token 对应的 hidden，作为第一个 decode token 的输入。

当前实现走 `cuda_prefill_batch(...)`，不是逐 token 调 `forward_token_device(...)`。也就是说，prompt 会被组织成 `[T, hidden]` 的 batch，其中 `T = prompt_ids.size()`。

大致流程：

```text
prompt ids
    |
    v
拷贝到 CUDA token id buffer
    |
    v
embedding batch lookup -> current: [T, hidden]
    |
    v
for each layer:
    input RMSNorm -> BF16
    attention 子层 batch 计算
    residual + post RMSNorm
    MLP batch 计算
    residual
    current/next 双缓冲交换
    |
    v
seq_len += T
返回最后一个 token 的 hidden: current[T - 1]
```

### Linear Attention 层

linear attention 层在 prefill 中会批量处理 prompt 中所有 token：

```text
input norm
    |
    +--> in_proj_qkv
    +--> in_proj_z
    +--> in_proj_b
    +--> in_proj_a
    |
conv1d batch
    |
linear recurrent batch
    |
gated RMSNorm
    |
out_proj
```

这里会更新两类状态：

- `conv_state`：供后续 token 的 causal conv 使用。
- `recurrent_state`：linear attention 的递推状态，decode 时继续从这里接着算。

prefill 结束后，batch 临时 buffer 会释放，但真正跨 token 使用的 state 会保留在 `RunState.linear[layer].cuda_state` 中。

### Full Attention 层

full attention 层在 prefill 中会把 prompt 的 K/V 写入 KV cache：

```text
input norm
    |
    +--> q_proj
    +--> k_proj
    +--> v_proj
    |
q_norm + RoPE
k_norm + RoPE + 写入 KV cache
    |
对 [0, 当前 token] 做 causal attention
    |
o_proj
```

prefill 会一次性填充 prompt 区间的 KV cache。之后 decode 第 `i` 个新 token 时，只需要在位置 `seq_len` 追加新的 K/V，然后让当前 Q attend 到已有 cache。

## Decode 流程

decode 每次只处理 1 个新 token。`QwenModel::generate()` 中循环 `max_new_tokens` 次：

```text
hidden
    |
final RMSNorm
    |
embedding weight 作为 lm_head 做 logits matvec
    |
argmax 得到 next token id
    |
如果还没结束：
    next token id -> embedding lookup
    forward_token_device_layers(...)
```

这里有一个容易误解的点：`cuda_final_norm_argmax_to_device(...)` 后面调用 `forward_token_device(...)`，不是重新处理刚才的 hidden，而是把刚生成出来的 token id 当作下一轮输入。

也就是：

```text
第 N 轮 hidden -> 预测 token_N
token_N -> embedding -> transformer layers -> 得到第 N+1 轮 hidden
```

生成出来的 token id 会先留在 CUDA buffer 中，只有整个 decode 结束后才通过 `cuda_copy_generated_tokens_to_host(...)` 一次性拷回 CPU。

## 单 token forward

decode 阶段的单 token forward 在 `QwenModel::forward_token_device(...)`：

```text
token id
    |
embedding lookup -> current hidden
    |
forward_token_device_layers(current, next, state)
```

每层执行的是整层 fused 路径：

```text
attention input RMSNorm
    |
linear attention full layer
或 full attention full layer
    |
attention residual
    |
post attention RMSNorm
    |
MLP
    |
MLP residual
```

`forward_token_device_layers(...)` 中每过一层就交换 `current` / `next` 两个 CUDA hidden buffer。所有层跑完后：

```text
state.seq_len += 1
return current
```

返回的 `current` 就是下一个 decode step 做 final norm + argmax 的输入。

## Prefill 和 Decode 的核心区别

| 阶段 | 输入 | 主要目标 | 计算形态 | cache 行为 | 输出 |
|------|------|----------|----------|------------|------|
| prefill | 完整 prompt | 建立历史上下文 | batch `[T, hidden]` | 填充 linear state / KV cache | 最后一个 prompt token 的 hidden |
| decode | 单个新 token | 逐 token 生成 | batch=1 | 追加更新 state/cache | 下一轮 hidden 和 generated token |

性能上，prefill 更容易做 batch GEMM，所以当前优化后耗时已经比较低。decode 是自回归过程，必须一个 token 一个 token 生成，batch=1 GEMV 和 kernel launch 数量会更影响性能，这也是当前和 llama.cpp 仍有差距的主要位置。
