# 推理引擎横向定位：local-llm vs llama.cpp vs SGLang vs vLLM

> 本文是 [`4.md`](4.md) 的补充。4.md 是 local-llm 与 llama.cpp 在**同一张 RTX 3080、同一 Qwen3.5-4B-Base（BF16）、单请求贪心解码**下的严格同机实测；本文把视野放大到 SGLang / vLLM，做一次**定位性**对比。
>
> **重要口径声明**：**local-llm 与 llama.cpp 是本机同机同模型实测**（数据来自 4.md），二者可逐格对比。**vLLM / SGLang 也已在本机 RTX 3080（12GB）单请求实测**，但因该 Qwen3.5-4B 为多模态模型、8.8GB 权重在 12GB 卡上被迫关闭 CUDA Graph（eager），其数字属「显存受限下界」，**不能与 local-llm/llama.cpp 逐格对比**（详见第二节注释）。多并发一节引用的数字来自**第三方公开 benchmark（不同硬件、不同模型、不同并发）**，仅用于说明「设计定位与适用场景」，**不能与本机 3080 单请求数字逐格相减**。

## 一、一句话定位

| 引擎 | 定位 | 最佳场景 | 单请求单卡小模型 | 多并发服务 |
| --- | --- | --- | --- | --- |
| **local-llm** | 自研教学/研究型推理引擎 | 理解推理全链路、可控地做算子级优化 | 可用（本文实测基线） | 不支持批处理/连续批 |
| **llama.cpp** | 便携单机推理引擎 | 个人/工作站单用户、GGUF 量化、跨平台（含 CPU/Apple Silicon） | **强项**（低占用、成熟融合核） | 弱（KV 连续分配、无连续批） |
| **SGLang** | 服务化框架，主打结构化生成 | RAG / agent / 工具调用 / 共享前缀多轮 | 非设计场景 | **强**（KV 复用、连续批） |
| **vLLM** | 生产级多用户服务事实标准 | 5–100+ 并发 API 服务 | 非设计场景（单请求优势不明显） | **强**（PagedAttention + 连续批） |

一句话：**单请求单卡下四者差距很小、主要由量化格式决定；引擎的真正分野在「并发」——local-llm/llama.cpp 面向单流低延迟，SGLang/vLLM 面向多流高吞吐。**

## 二、单请求 · 单卡吞吐（低并发口径）

这是 local-llm 的主战场，也是四者差距最小的区间。多份第三方 benchmark 都指出：单流下引擎间差距小，**主要变量是量化格式而非引擎**。

| 引擎 | 场景 / 来源 | decode 吞吐 | 说明 |
| --- | --- | --- | --- |
| **local-llm** | 本机实测：RTX 3080，Qwen3.5-4B-Base BF16，贪心，单请求 | **64.8 → ~69.3 tok/s** | 见 4.md；64.8 为优化前 baseline，经去逐层同步 + 算子融合 + CUDA Graph + GPU argmax 等一系列优化后稳定约 69.3 tok/s（+7%），全程数值零回归 |
| **llama.cpp** | 本机实测：同上，BF16 GGUF，`tg64` | **86.8 tok/s** | 见 4.md；同机同模型，是唯一可与 local-llm 逐格对比的一列 |
| **vLLM** | 本机实测（211 机器 RTX 3080 12GB，vLLM 0.27.1，单请求贪心，96 tok，**eager**） | **~40 tok/s** | 三组 prompt：40.1 / 40.1 / 38.5 tok/s（端到端）。**受 12GB 显存限制被迫 `enforce_eager`（关 CUDA Graph）**，非 vLLM 最优；口径见下方注释 |
| **SGLang** | 本机实测（同上，SGLang 0.5.18，单请求贪心，96 tok，**eager**） | **~51 tok/s** | 三组 prompt：51.8 / 51.6 / 48.8 tok/s（端到端）。同样 `disable_cuda_graph`，非 SGLang 最优 |

> **本机实测口径与限制（重要）**：vLLM/SGLang 已在 211 机器（RTX 3080 12GB）实测，但有三点必须说明，**不能与 local-llm/llama.cpp 逐格对比**：
> 1. **模型是多模态**：`Qwen3.5-4B-Base` 实为含视觉塔的多模态模型（权重 8.8GB，含 297 个 visual 张量）。vLLM/SGLang 会连视觉塔一起加载，而 local-llm/llama.cpp 只跑纯文本 language_model 部分——**加载的权重量不同**。
> 2. **被迫 eager**：8.8GB 权重在 12GB 3080 上余量极小，vLLM/SGLang 的 CUDA Graph 池放不下，只能 `enforce_eager` / `disable_cuda_graph` 运行。**关掉 CUDA Graph 后 decode 明显偏慢**（而 local-llm 的 69.3 恰恰用了 CUDA Graph）。因此这里的 40/51 tok/s 是「显存受限的下界」，不代表两框架在充裕显存下的真实水平。
> 3. **端到端口径**：上表 vLLM/SGLang 为 input≤8 + output 96 的端到端 tok/s（短 prompt 下 prefill 占比很小，近似 decode 吞吐）；vLLM 0.27 的 per-request metrics 字段已变动，未单独拆出纯 decode 段。
>
> 结论：在**同一张 12GB 3080、同一多模态权重、单请求 eager** 这个受限口径下，SGLang(~51) > vLLM(~40)，与「小模型单流下 SGLang 调度 overhead 更低」的定性预期一致；但两者都因显存受限关掉了 CUDA Graph，**这个数字不能用来说明 vLLM/SGLang 弱于 local-llm/llama.cpp**——后两者是纯文本 + CUDA Graph 的更优配置。要做真正对等对比，需换更大显存的卡（放得下 CUDA Graph）或纯文本权重。

**要点**：在 local-llm 关心的「单卡单请求」区间，vLLM 相对 llama.cpp 的领先只有个位数百分比——因为此时 GPU 没有被并发喂满，PagedAttention / 连续批的价值发挥不出来。local-llm 优化后与 llama.cpp 仍有约 **20% 差距**（~69.3 vs 86.8 tok/s）；据 4.md 最新结论，此时瓶颈已从「launch-bound」转向 **kernel 计算效率本身**（attention/GEMM 核的 tensor-core 利用、量化 GEMM、fused attention），是同一量级内的实现差异，而非架构问题。

## 三、多并发 · 服务化吞吐（SGLang/vLLM 的主场）

一旦并发数超过个位数，格局反转——这正是 SGLang/vLLM 存在的意义，也是 local-llm/llama.cpp 的短板。

| 引擎 | 场景 / 来源 | 聚合吞吐 | 说明 |
| --- | --- | --- | --- |
| vLLM（他测参考） | H100 80GB，Llama-3.3-70B FP8，50 并发 | ~1,850 tok/s | 聚合吞吐，非单请求 |
| SGLang（他测参考） | 同上 | ~1,920 tok/s | 共享前缀 / RAG 场景更强 |
| （对照）llama.cpp（他测参考） | 无连续批，50 并发 | 随并发几乎不增 | 请求排队串行化，聚合吞吐无法随 batch 扩展 |

- **vLLM**：PagedAttention 把 KV cache 当分页虚存管理，显存利用率 60%→96%，配合 continuous batching 让 GPU 在并发下维持 85–92% 占用；50 并发时相对无连续批的单流引擎可达 **10–20×** 聚合吞吐。
- **SGLang**：在结构化生成、工具调用、共享前缀多轮（RAG/agent）上靠 KV-cache 复用领先；H100 高并发下与 vLLM 相差约 14% 以内，排名随 workload 变动。
- **llama.cpp / local-llm**：KV 连续分配、无连续批，并发下请求排队串行，聚合吞吐无法随 batch 扩展——**这是架构选择而非实现打磨问题**。

> H100/70B/FP8/多并发的数字与本机 3080/4B/BF16/单请求完全不同源，**仅用于说明「并发区间 SGLang/vLLM 领先一个数量级、且彼此接近」**，不可与前两节数字混用。

## 四、选型建议（映射到 local-llm 的定位）

| 你的场景 | 推荐 | 理由 |
| --- | --- | --- |
| 学习/研究推理内核、想逐算子优化 | **local-llm** | 全链路可读可改，本仓库正在做的事 |
| 个人单机、单用户、要跨平台/CPU 兜底 | **llama.cpp** | 低占用、GGUF 量化、成熟融合核 |
| RAG / agent / 工具调用 / 共享前缀多轮 | **SGLang** | KV 复用 + 结构化生成延迟低 |
| 5–100+ 并发的生产 API | **vLLM** | 连续批 + PagedAttention，多用户吞吐事实标准 |

**结论**：local-llm 的合理对标是 **llama.cpp（单请求单卡）**，这也是 4.md 严格同机对比的对象；SGLang/vLLM 属于另一维度（多并发服务化），把它们放进来是为了**界定 local-llm 的定位边界**——它是单流研究型引擎，不与服务框架在并发吞吐上正面竞争。4.md 第八节列出的方向中，去逐层同步、序列建模算子融合、CUDA Graph、GPU argmax 均已落地（baseline 64.8 → ~69.3 tok/s）；要继续缩小与 llama.cpp 的约 20% 差距，剩余空间已进入深水区——attention/GEMM 核的 tensor-core 利用、量化 GEMM、fused attention（FlashAttention 化）、KV f16，这类改动风险与收益都更大，需单独立项。

## 五、来源与口径限制

- **local-llm / llama.cpp**：本机 RTX 3080 同机同模型实测，见 [`4.md`](4.md) 与 [`stats-detail/20260823/`](stats-detail/20260823)。
- **vLLM / SGLang**：已在本机 211 机器（RTX 3080 12GB）单请求实测（vLLM 0.27.1 ~40 tok/s、SGLang 0.5.18 ~51 tok/s，均为 12GB 显存受限下的 eager 口径，见第二节表格与注释，**不与 local-llm/llama.cpp 逐格对比**）；本文多并发一节的数字为 2026 年公开第三方 benchmark（H100 80GB 多并发），**不同硬件 / 模型 / 量化 / 并发**，仅用于定位性对比。凡本机未复现的数字，本文一律标注为「他测参考」，不与本机实测混算。
