# 推理引擎横向定位：local-llm vs llama.cpp vs SGLang vs vLLM

> 本文是 [`4.md`](4.md) 的补充。4.md 是 local-llm 与 llama.cpp 在**同一张 RTX 3080、同一 Qwen3.5-4B-Base（BF16）、单请求贪心解码**下的严格同机实测；本文把视野放大到 SGLang / vLLM，做一次**定位性**对比。
>
> **重要口径声明**：只有 **local-llm 与 llama.cpp 是本机同机同模型实测**（数据来自 4.md）。**SGLang / vLLM 未在本机测**——它们是面向多并发在线服务的框架，单请求单卡小模型并非其设计场景。下表中 SGLang/vLLM 的数字来自**第三方公开 benchmark（不同硬件、不同模型、不同并发）**，仅用于说明「设计定位与适用场景」，**不能与 local-llm/llama.cpp 的 3080 单请求数字逐格相减**。

## 一、一句话定位

| 引擎 | 定位 | 最佳场景 | 单请求单卡小模型 | 多并发服务 |
| --- | --- | --- | --- | --- |
| **local-llm** | 自研教学/研究型推理引擎 | 理解推理全链路、可控地做算子级优化 | 可用（本文实测基线） | 不支持批处理/连续批 |
| **llama.cpp** | 便携单机推理引擎 | 个人/工作站单用户、GGUF 量化、跨平台（含 CPU/Apple Silicon） | **强项**（低占用、成熟融合核） | 弱（KV 连续分配、无连续批） |
| **SGLang** | 服务化框架，主打结构化生成 | RAG / agent / 工具调用 / 共享前缀多轮 | 非设计场景 | **强**（KV 复用、连续批） |
| **vLLM** | 生产级多用户服务事实标准 | 5–100+ 并发 API 服务 | 非设计场景（单请求优势不明显） | **强**（PagedAttention + 连续批） |

一句话：**单请求单卡下四者差距很小、主要由量化格式决定；引擎的真正分野在「并发」——local-llm/llama.cpp 面向单流低延迟，SGLang/vLLM 面向多流高吞吐。**

## 二、单请求 · 单卡吞吐（低并发口径）

这是 local-llm 的主战场，也是四者差距最小的区间。多份第三方 benchmark 都指出：单流下引擎间差距小，**主要变量是量化格式而非引擎**。

| 引擎 | 场景 / 来源 | decode 吞吐 | 说明 |
| --- | --- | --- | --- |
| **local-llm** | 本机实测：RTX 3080，Qwen3.5-4B-Base BF16，贪心，单请求 | **64.8 tok/s** | 见 4.md；去逐层同步优化后短 prompt 约 69 tok/s |
| **llama.cpp** | 本机实测：同上，BF16 GGUF，`tg64` | **86.8 tok/s** | 见 4.md；同机同模型，是唯一可与 local-llm 逐格对比的一列 |
| llama.cpp（他测参考） | RTX 4090，Llama-3.1-8B，单流 | ~65 tok/s | 不同卡/模型/量化，仅示意量级 |
| vLLM（他测参考） | RTX 4090，Llama-3.1-8B，单流 | ~71 tok/s | 单流下相对 llama.cpp 仅略高，优势不在此区间 |
| Ollama（他测参考） | RTX 4090，Llama-3.1-8B，单流 | ~62 tok/s | 底层即 llama.cpp |

> 引用来源为社区聚合的 RTX 4090 / Llama-3.1-8B 单流对比，与本机 3080 / Qwen3.5-4B 不同硬件不同模型，**只用于说明「单流下 vLLM ≈ llama.cpp ≈ Ollama，量级接近」这一定性结论**，不能与本机两列直接比。原文结论：*"The runtime is not the determining factor at this scale; quantization choice is."*

**要点**：在 local-llm 关心的「单卡单请求」区间，vLLM 相对 llama.cpp 的领先只有个位数百分比——因为此时 GPU 没有被并发喂满，PagedAttention / 连续批的价值发挥不出来。local-llm 与 llama.cpp 的 25% 差距（4.md）反而更多来自 **linear attention 融合程度与 tensor-core 利用**，是同一量级内的实现差异。

## 三、多并发 · 服务化吞吐（SGLang/vLLM 的主场）

一旦并发数超过个位数，格局反转——这正是 SGLang/vLLM 存在的意义，也是 local-llm/llama.cpp 的短板。

| 引擎 | 场景 / 来源 | 聚合吞吐 | 说明 |
| --- | --- | --- | --- |
| vLLM（他测参考） | H100 80GB，Llama-3.3-70B FP8，50 并发 | ~1,850 tok/s | 聚合吞吐，非单请求 |
| SGLang（他测参考） | 同上 | ~1,920 tok/s | 共享前缀 / RAG 场景更强 |
| （对照）Ollama（他测参考） | 50 并发 | ~155 tok/s | 无连续批，请求被串行化 |

- **vLLM**：PagedAttention 把 KV cache 当分页虚存管理，显存利用率 60%→96%，配合 continuous batching 让 GPU 在并发下维持 85–92% 占用；50 并发时相对 Ollama 可达 **10–20×** 聚合吞吐。
- **SGLang**：在结构化生成、工具调用、共享前缀多轮（RAG/agent）上靠 KV-cache 复用领先；H100 高并发下与 vLLM 相差约 14% 以内，排名随 workload 变动。
- **llama.cpp / local-llm**：KV 连续分配、无连续批，并发下请求排队串行，聚合吞吐无法随 batch 扩展——**这是架构选择而非实现打磨问题**。

> H100/70B/FP8/多并发的数字与本机 3080/4B/BF16/单请求完全不同源，**仅用于说明「并发区间 SGLang/vLLM 领先一个数量级、且彼此接近」**，不可与前两节数字混用。

## 四、选型建议（映射到 local-llm 的定位）

| 你的场景 | 推荐 | 理由 |
| --- | --- | --- |
| 学习/研究推理内核、想逐算子优化 | **local-llm** | 全链路可读可改，本仓库正在做的事 |
| 个人单机、单用户、要跨平台/CPU 兜底 | **llama.cpp / Ollama** | 低占用、GGUF 量化、成熟融合核 |
| RAG / agent / 工具调用 / 共享前缀多轮 | **SGLang** | KV 复用 + 结构化生成延迟低 |
| 5–100+ 并发的生产 API | **vLLM** | 连续批 + PagedAttention，多用户吞吐事实标准 |

**结论**：local-llm 的合理对标是 **llama.cpp（单请求单卡）**，这也是 4.md 严格同机对比的对象；SGLang/vLLM 属于另一维度（多并发服务化），把它们放进来是为了**界定 local-llm 的定位边界**——它是单流研究型引擎，不与服务框架在并发吞吐上正面竞争。要缩小与 llama.cpp 的 25% 差距，方向仍是 4.md 第八节列出的序列建模算子融合、FlashAttention 化、KV f16、CUDA Graph。

## 五、来源与口径限制

- **local-llm / llama.cpp**：本机 RTX 3080 同机同模型实测，见 [`4.md`](4.md) 与 [`stats-detail/20260823/`](stats-detail/20260823)。
- **SGLang / vLLM / Ollama**：均为 2026 年公开第三方 benchmark（RTX 4090 单流、H100 80GB 多并发），**不同硬件 / 模型 / 量化 / 并发**，只用于定位性对比。凡本机未复现的数字，本文一律标注为「他测参考」，不与本机实测混算。
