# 性能对比（RTX 3090）：local-llm vs llama.cpp（Qwen3.5-4B-Base）

本文记录一次 local-llm 与 llama.cpp 在**同一张 RTX 3090** 上、跑**同一 Qwen3.5-4B-Base 模型（BF16）**的 decode 稳态性能对比，并附上 local-llm 的**逐算子性能明细**（借助其内置的 `--profile` 采集能力，见 [`StatsReport.h`](../src/utils/stats/StatsReport.h)）。原始明细数据见 [`stats-detail/20260810/`](stats-detail/20260810)。

**结论先行**：公平对比应看**关闭明细采集的基础墙钟耗时**。local-llm 关闭 `--profile` 时 decode 稳态为 **66.5 tok/s（15.0 ms/token）**，llama.cpp 为 **88.3 tok/s（11.3 ms/token）**，local-llm 约为 llama.cpp 的 **75%**（慢约 33%）。

需要特别强调：local-llm 的 `--profile` 采集本身有**不可忽略的开销**——它对每个算子做 `cudaEventSynchronize`（逐 kernel 强制同步，打断 CUDA 流水线），使 decode 从 66.5 tok/s 掉到 43.9 tok/s（**慢约 34%**）。因此 profile summary 里的绝对吞吐**不能**当作 local-llm 的真实性能，只能用于看**算子间相对占比**。本文最初一版误用了 profile 口径（43 tok/s）做对比，故本次修正为基础墙钟口径。

即便用修正后的公平口径，差距（慢约 33%）仍明显大于 [`2.md`](2.md) 里标准 Qwen（纯 full attention）上的 ~9.5%，主因是**本模型 24/32 层是 linear attention（类 Mamba/GDN 递归）**，而 local-llm 的递归+卷积状态更新路径尚未做 kernel 融合与访存优化，llama.cpp 在该结构上有成熟的融合实现。这不是正确性问题（两者输出均正常），而是清晰可定位的**优化空间**。

## 一、测试环境与口径

- **硬件**：RTX 3090（24GB，显存带宽约 936 GB/s），CUDA 12.4，驱动 580.95.05，CPU AMD EPYC 7282
- **模型**：`Qwen/Qwen3.5-4B-Base`（`Qwen3_5ForConditionalGeneration` / `model_type=qwen3_5`），32 层混合注意力（24 层 linear attention + 8 层 full attention），SwiGLU MLP，BF16 权重，`tie_word_embeddings=true`。架构详见 [`qwen_architecture.md`](qwen_architecture.md)。
- **权重格式**：
  - local-llm：原始 safetensors（BF16），mmap 零拷贝加载
  - llama.cpp：由 `convert_hf_to_gguf.py` 转出的 GGUF（BF16，8.06 GiB，441 tensors）
- **解码**：greedy，生成 64 tokens
- **构建**：均 Release，`-DCMAKE_CUDA_ARCHITECTURES=86`
- **计时口径**：统一看 **decode 稳态每 token 耗时**（warmup 之后、逐 token 生成阶段的平均值），几乎不受 prompt 长度影响，最能代表 decode 性能。
  - local-llm **基础墙钟（公平对比口径）**：不加 `--profile`，`main.cpp` 在 warmup 之后用一段纯 `std::chrono` 墙钟包住稳态 decode 循环，循环结束 `cudaDeviceSynchronize()` 后停表，打印 `[decode] ... tokens_per_sec=`。无逐算子埋点、无 CUDA event、无采样线程、无落盘。
  - local-llm **profile 口径（仅看相对占比）**：加 `--profile` 后每个算子用 `ScopedGpuTimer` 计时，析构时 `cudaEventSynchronize`，会逐 kernel 打断流水线，**绝对吞吐被拉低约 34%**，不可用于跨实现对比。
  - llama.cpp：`llama-bench` 的 `tg64`（纯稳态生成，天然不含 prefill 与冷启，也无逐算子同步）。

## 二、运行命令

local-llm 基础墙钟（公平对比口径，不采集明细）：

```bash
PROMPT="法国的首都是" ./build-release/local_llm \
    --model qwen --model-dir /root/models/Qwen3.5-4B-Base \
    --max-output-tokens 64
# 输出：[decode] tokens=64 wall_ms=... avg_ms_per_token=... tokens_per_sec=...
```

local-llm 开启性能采集（产出 jsonl + json/md summary，仅用于看算子相对占比）：

```bash
PROMPT="法国的首都是" ./build-release/local_llm \
    --model qwen --model-dir /root/models/Qwen3.5-4B-Base \
    --max-output-tokens 64 --profile --profile-dir /root/stats-out
```

llama.cpp（先转 GGUF，再 `llama-bench`）：

```bash
python3 convert_hf_to_gguf.py /root/models/Qwen3.5-4B-Base \
    --outtype bf16 --outfile /root/models/Qwen3.5-4B-Base-BF16.gguf

./build/bin/llama-bench -m /root/models/Qwen3.5-4B-Base-BF16.gguf \
    -ngl 99 -fa on -p 15 -n 64 -r 5
```

## 三、总体结果（同一张 RTX 3090）

| 实现 / 口径 | 权重格式 | KV/state 精度 | decode 每 token | decode 吞吐 | 相对 llama.cpp |
| --- | --- | --- | --- | --- | --- |
| **llama.cpp** (tg64) | GGUF BF16 | KV f16 + FlashAttention | **11.3 ms** | **88.3 tok/s** | 1.00× |
| **local-llm（基础墙钟，公平口径）** | safetensors BF16 | KV/state fp32，无 FA | 15.0 ms | **66.5 tok/s** | **0.75×** |
| local-llm（--profile，逐算子同步） | safetensors BF16 | 同上 | 22.8 ms | 43.9 tok/s | 0.50×（含采集开销，不作数） |

- llama.cpp `tg64 = 88.31 ± 0.15 tok/s`，`pp15 = 1026.79 tok/s`（数据高度稳定，tg 抖动 < 0.2%）。
- local-llm 基础墙钟两次：`66.26 / 66.59 tok/s`（15.09 / 15.02 ms/token），稳定。
- local-llm `--profile`：`43.88 tok/s`（22.79 ms/token）——比基础口径慢约 34%，差值即逐算子 `cudaEventSynchronize` 的采集开销。
- 两者生成文本均正常连贯（local-llm 输出："哪个城市？…答案本身很明确——巴黎…"）。

**采集开销结论**：local-llm 的 `--profile` 会让每个 decode 步的几十个小 kernel 各自 `cudaEventSynchronize`，把原本可以异步排队的 kernel 强制串成"发一个、等一个"，因此绝对吞吐被压低约 1/3。这解释了本文初版 43 tok/s 的偏低——那不是 local-llm 的真实速度。**做跨实现对比时务必关闭 `--profile`**；profile 数据仅用于第四节的算子相对占比分析。

## 五、分析：公平口径下差距仍存在的原因

> 注：本节 SM / 带宽利用率、逐算子占比均取自 `--profile` 采样（含逐算子同步开销），绝对值会被同步拉低、利用率被低估；但**算子间相对占比**与瓶颈定位仍然成立。

1. **本模型主体是 linear attention（24/32 层），而非标准 attention。** [`2.md`](2.md) 的 ~9.5% 差距是在纯 full attention 的 Qwen 上测的；本模型换成 linear/full 混合后，占主导地位的是 linear attention 的**递归状态更新 + depthwise conv1d**（`linear_attention_recurrent` + `linear_attention_conv`）。这条路径 local-llm 目前是逐步 kernel、fp32 状态、无融合，`linear_attention_recurrent` 单项就吃掉 1.57%，加上其一系列 `in_proj_*` / `out_proj` 投影，linear attention 相关合计占比明显高于 full attention 相关。llama.cpp 对该结构有成熟的融合 kernel，这是拉开差距的第一主因。

2. **KV/state 精度与 FlashAttention。** llama.cpp 用 **f16 KV cache + FlashAttention**（`type_k=f16 / type_v=f16 / flash_attn=1`）；local-llm 是 **fp32 KV/state、无 FA**（`full_attention_attend` 未融合、带宽记 0）。decode 是访存瓶颈，KV 精度减半 + attention 融合直接省一大截访存往返。

3. **设备侧证据一致**：profile 采样期间 **SM 均值仅 53%、显存带宽均值仅 37%**（基础口径下会更高，但仍难以打满），说明 GPU 并未被喂满——既非纯算力瓶颈也非纯带宽瓶颈，而是**大量小 kernel 的启动开销与未融合导致的空转**（逐 token decode 每步要发起几十个小 kernel）。这正是融合优化的典型收益区间。

4. **不是正确性或权重加载问题**：权重一次性 H2D 1.46s（warmup 内完成，不计入稳态），KV/state 仅 55 MiB，显存占用健康（33%）；投影类 GEMM 的有效带宽都在 600–880 GB/s（接近 3090 的 ~936 GB/s 理论值），说明**GEMM 本身没问题，瓶颈在非 GEMM 的序列建模算子与 attention 融合**。

## 六、重要提醒：跨卡 / 跨模型 / 跨采集口径不可直接比

- **跨卡**：本次是 RTX 3090（带宽 ~936 GB/s），[`2.md`](2.md) 是 A4000（~448 GB/s）。decode 是带宽瓶颈，卡不同不可直接比绝对值——所以本次专门在同一张 3090 上重新编译并运行了两者。
- **跨模型**：本次是 `qwen3_5`（linear/full 混合），[`2.md`](2.md) 是标准 full-attention Qwen。**同为 "Qwen 4B" 但架构不同**，性能特征与差距成因都不一样，两篇结论不能混用。
- **跨采集口径**：local-llm 的 `--profile` 会引入约 34% 的逐算子同步开销，其 summary 里的绝对吞吐（43.9 tok/s）**不能**拿去和 llama.cpp（无逐算子同步）比。跨实现对比一律用**关闭 profile 的基础墙钟**（66.5 tok/s）。

## 七、后续可优化方向（按预期收益排序）

1. **优化 linear attention 路径**：把递归状态更新（gated delta / SSM）与 conv1d 做 kernel 融合、状态用 bf16/f16，减少每步的小 kernel 数与访存往返——这是本模型上收益最大的方向。
2. **KV cache 改 f16**：直接减半 full attention 层的 KV 访存量。
3. **引入 FlashAttention 式融合 attention kernel**：替换当前未融合的 `full_attention_attend`。
4. **decode 小 kernel 合并 / CUDA Graph**：SM 利用率仅 53%，用 CUDA Graph 固化 decode 单步的 kernel 序列可显著降低启动开销。
