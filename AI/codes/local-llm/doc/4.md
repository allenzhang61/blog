# 性能对比（RTX 3080）：local-llm vs llama.cpp（Qwen3.5-4B-Base）

本文记录一次 local-llm 与 llama.cpp 在**同一张 RTX 3080** 上、跑**同一 Qwen3.5-4B-Base 模型（BF16）**的 decode 稳态性能对比，并附上 local-llm 的**逐算子性能明细**（借助其内置的 `--profile` 采集能力，见 [`StatsReport.h`](../src/utils/stats/StatsReport.h)）。原始明细数据见 [`stats-detail/20260823/`](stats-detail/20260823)。

**结论先行**：公平对比应看**关闭明细采集的基础墙钟耗时**。local-llm 关闭 `--profile` 时 decode 稳态为 **64.8 tok/s（15.4 ms/token）**，llama.cpp 为 **86.8 tok/s（11.5 ms/token）**，local-llm 约为 llama.cpp 的 **75%**（慢约 25%）。

需要说明 local-llm `--profile` 采集的开销演进：早期实现对每个算子做 `cudaEventSynchronize`（逐 kernel 强制同步、打断 CUDA 流水线），使 decode 从 64.8 掉到 47.3 tok/s（慢约 27%）；改成**批量延迟结算**（只 `cudaEventRecord` 入队、循环末尾统一 `cudaEventElapsedTime`）后降到 56.4 tok/s（慢约 13%），残留开销经三段式对照实验定位为**每步上百次 `cudaEventRecord` 插流本身**的调度开销；最终改为**采样式 profile**（`--profile-sample-every N`，默认 16：仅每 16 步开一次全量 event 计时，其余步 timer 短路、零 event 开销），把开销压到**约 1%（63.8 tok/s）**，同时逐算子明细与带宽指标依旧完整。即便如此，profile summary 的绝对吞吐仍建议只用于看**算子间相对占比**；做跨实现对比一律用基础墙钟口径。

即便用公平口径，差距（慢约 25%）仍明显大于 [`2.md`](2.md) 里标准 Qwen（纯 full attention）上的 ~9.5%，主因是**本模型 24/32 层是 linear attention（类 Mamba/GDN 递归）**，而 local-llm 的递归+卷积状态更新路径尚未做 kernel 融合与访存优化，llama.cpp 在该结构上有成熟的融合实现。这不是正确性问题（两者输出均正常），而是清晰可定位的**优化空间**。

## 一、测试环境与口径

- **硬件**：RTX 3080（12GB，显存带宽约 760 GB/s），CUDA 12.4，驱动 595.84，CPU AMD Ryzen 7 5700X（8 核）
- **模型**：`Qwen/Qwen3.5-4B-Base`（`Qwen3_5ForConditionalGeneration` / `model_type=qwen3_5`），32 层混合注意力（24 层 linear attention + 8 层 full attention），SwiGLU MLP，BF16 权重，`tie_word_embeddings=true`。架构详见 [`qwen_architecture.md`](qwen_architecture.md)。
- **权重格式**：
  - local-llm：原始 safetensors（BF16），mmap 零拷贝加载
  - llama.cpp：由 `convert_hf_to_gguf.py` 转出的 GGUF（BF16，8.06 GiB，441 tensors）
- **解码**：greedy，生成 64 tokens
- **构建**：均 Release，`-DCMAKE_CUDA_ARCHITECTURES=86`
- **计时口径**：统一看 **decode 稳态每 token 耗时**（warmup 之后、逐 token 生成阶段的平均值），几乎不受 prompt 长度影响，最能代表 decode 性能。
  - local-llm **基础墙钟（公平对比口径）**：不加 `--profile`，`main.cpp` 在 warmup 之后用一段纯 `std::chrono` 墙钟包住稳态 decode 循环，循环结束 `cudaDeviceSynchronize()` 后停表，打印 `[decode] ... tokens_per_sec=`。无逐算子埋点、无 CUDA event、无采样线程、无落盘。
  - local-llm **profile 口径（仅看相对占比）**：加 `--profile` 后各算子用 `ScopedGpuTimer` 借一对 CUDA event 计时，采用**批量延迟结算 + 采样式**采集：只 `cudaEventRecord` 入队、每采样步末尾统一结算，且默认每 16 步（`--profile-sample-every`，可调，设为 1 即每步全量最细）才采一次。默认口径下开销**约 1%（63.8 tok/s）**；`--profile-sample-every 1` 全量最细时约 13%（56.4 tok/s）。绝对吞吐仍建议只用于看相对占比，跨实现对比用基础墙钟。
  - llama.cpp：`llama-bench` 的 `tg64`（纯稳态生成，天然不含 prefill 与冷启，也无逐算子同步）。

## 三、总体结果（同一张 RTX 3080）

| 实现 / 口径 | 权重格式 | KV/state 精度 | decode 每 token | decode 吞吐 | 相对 llama.cpp |
| --- | --- | --- | --- | --- | --- |
| **llama.cpp** (tg64) | GGUF BF16 | KV f16 + FlashAttention | **11.5 ms** | **86.8 tok/s** | 1.00× |
| **local-llm（基础墙钟，公平口径）** | safetensors BF16 | KV/state fp32，无 FA | 15.4 ms | **64.8 tok/s** | **0.75×** |
| local-llm（--profile 默认，采样式 every=16） | safetensors BF16 | 同上 | 15.7 ms | 63.8 tok/s | 0.74×（含采集开销，不作数） |
| local-llm（--profile-sample-every 1，全量最细） | safetensors BF16 | 同上 | 17.8 ms | 56.4 tok/s | 0.65×（含采集开销，不作数） |

- llama.cpp `tg64 = 86.80 ± 0.11 tok/s`，`pp15 = 991.94 ± 121.15 tok/s`（tg 高度稳定，抖动 < 0.2%）。
- local-llm 基础墙钟两次：`64.76 / 64.75 tok/s`（15.44 / 15.44 ms/token），稳定。
- local-llm `--profile` 默认采样式：`63.8 tok/s`（15.7 ms/token）——比基础口径仅慢约 1%，逐算子明细与带宽指标仍完整。
- local-llm `--profile-sample-every 1`（每步全量最细）：`56.4 tok/s`（17.8 ms/token）——比基础口径慢约 13%，差值即每步上百次 `cudaEventRecord` 插流的采集开销。
- 两者生成文本均正常连贯（local-llm 输出："哪个城市？"）。

**采集开销结论**：`--profile` 的开销主要来自每个 decode 步给几十个小 kernel 各插一对 CUDA event（`cudaEventRecord`），在单一默认流上累积成调度开销。早期"逐算子 `cudaEventSynchronize`"实现更是把 kernel 强制串成"发一个、等一个"，开销高达约 27%；改为批量延迟结算降到约 13%，再改为**采样式采集（默认每 16 步采一次）**后降到约 1%。**做跨实现对比时务必用基础墙钟（关闭或忽略 profile 绝对吞吐）**；profile 数据仅用于第四节的算子相对占比分析。

## 五、local-llm vs llama.cpp：总耗时与细分环节对比

本节把两者放在同一张 RTX 3080 上做**总耗时**与**细分环节**两级对比。**两侧的细分环节数据都用 `nsys` 采集 GPU 时间线**（同口径可直接横向对比）：llama.cpp 包住 `llama-bench`（pp15 + tg64，`-fa on -ngl 99`），local-llm 包住 `local_llm`（decode 64 tokens）；导出后都用 `nsys stats --report cuda_gpu_kern_sum` 汇总 GPU kernel。原始数据分别见 [`llama_nsys_report.md`](stats-detail/20260823/llama_nsys_report.md) 与 [`local_nsys_report.md`](stats-detail/20260823/local_nsys_report.md)。

> 采集命令（远端）：
> ```bash
> # llama.cpp
> nsys profile --trace=cuda --sample=none -o llama_nsys \
>     ./build-cuda/bin/llama-bench -m Qwen3.5-4B-Base-BF16.gguf -ngl 99 -fa on -p 15 -n 64 -r 1
> # local-llm（--cuda-flush-interval=100 规避本机 importer 的事件乱序 bug）
> nsys profile --trace=cuda --sample=none --cuda-flush-interval=100 -o local_nsys \
>     ./build-release/local_llm --model-dir Qwen3.5-4B-Base --max-output-tokens 64
> # 该机 nsys 只装了 target 组件，需手动补 importer 才能出报告：
> /usr/lib/nsight-systems/host-linux-x64/QdstrmImporter -i <run>.qdstrm -o <run>.nsys-rep -f
> nsys stats --report cuda_gpu_kern_sum <run>.nsys-rep
> ```

### 5.1 总耗时对比

按推理生命周期的三个阶段（都用公平口径：local-llm 基础墙钟 / 采样式，llama.cpp 用 llama-bench 与 nsys memcpy 汇总）：

| 阶段 | local-llm | llama.cpp | 备注 |
| --- | ---: | ---: | --- |
| 权重加载 H2D（一次性） | 851 ms | 787 ms | 8GB BF16 权重上传，同量级；不计入 decode 稳态 |
| prefill（每 token） | ~5.7 ms（22.6 ms / 4 token） | ~1.4 ms（pp15 = 716 t/s） | prompt 长度不同，只可看每 token；llama.cpp 批处理 prefill 明显更快 |
| **decode 稳态（每 token）** | **15.4 ms（64.8 tok/s）** | **11.5 ms（86.8 tok/s）** | 最能代表交互延迟，local-llm 约为 llama.cpp 的 75% |

- 一次性权重加载两者相当（都是 8GB BF16 走 PCIe H2D），不是差距来源。
- **prefill 差距更大**（llama.cpp 每 token 快约 4×）：prefill 是批量 GEMM（compute-bound），llama.cpp 用 `mul_mat_f`（tensor-core BF16 GEMM）一次算完整段。注：local-llm 的 prefill **本就是批量 GEMM**（`gemm_main` 以 token 数为 batch 一次算完整段，见 8b·补的实测澄清），差距主要来自 tensor-core 利用与序列建模算子融合，而非「没有批量 GEMM」。
- **decode 差距约 25%**：decode 是访存瓶颈，差距主要来自 linear attention 与 attention 的融合程度（见 5.2）。

### 5.2 细分环节（GPU kernel 级）对比

两侧都用 `nsys` 采集 GPU 时间线、`nsys stats --report cuda_gpu_kern_sum` 汇总，占比均为各 kernel 占 **本侧 GPU kernel 忙时总和** 的比例（local-llm ≈ 1012.4M ns、llama.cpp ≈ 37.7M ns，都含 warmup / 权重加载 / prefill / decode 全过程），**同一口径、可直接对比**。下表按**功能环节**把两侧的实际 CUDA kernel 归类对齐：

| 功能环节 | local-llm kernel | local-llm 占比 | llama.cpp kernel | llama.cpp 占比 |
| --- | --- | ---: | --- | ---: |
| 矩阵乘（投影 / MLP / lm_head） | `ampere_s16816gemm` / `cutlass wmma gemm` / `gemv2T` / `gemvx` / `splitKreduce` | **84.9%** | `mul_mat_vec_f`（decode GEMV）+ `mul_mat_f`（prefill GEMM，tensor core） | **87.2%** |
| **linear attention 递归** | `linear_attention_recurrent`(+`_batch`) | **6.6%** | 单个融合核 `gated_delta_net_cuda` | 2.0% |
| 归一化 | `rms_norm` + `f32_to_bf16_copy`（精度转换） | 5.0% | `rms_norm_f32` / `l2_norm_f32` | 2.7% |
| **full attention** | `full_attention_attend/kv/q`（**未融合**） | **1.8%** | `flash_attn_ext_f16`（FlashAttention 融合核） | 0.9% |
| 逐元素 / 激活 | `add` / `silu_mul` | 1.2% | `k_bin_bcast` / `unary_gated_op_kernel(silu)` / `scale_f32` / `cpy_scalar` / `rope_multi` | ~6.8% |
| linear attention conv1d | `linear_attention_conv`(+`_batch`) | 0.4% | `ssm_conv_f32` | 0.4% |

> 现在两侧完全同口径（都是「占本侧 GPU kernel 忙时」），可直接横向对比。两个关键差异一目了然：
> 1. **矩阵乘两侧占比几乎相同**（84.9% vs 87.2%）——GEMM/GEMV 本身两边都不是瓶颈，local-llm 的投影类 GEMM 有效带宽已达 500–860 GB/s。
> 2. **序列建模算子 local-llm 明显更重**：linear attention 递归 **6.6% vs 2.0%**（约 3 倍）、full attention **1.8% vs 0.9%**（约 2 倍）。这正是差距根因——llama.cpp 把整条 linear attention 递归融进单个 `gated_delta_net_cuda`、把 attention 融进 `flash_attn_ext_f16`（+f16 KV），local-llm 则是逐步小 kernel、fp32 状态、未融合，同样的功能占用了更大比例的 GPU 时间。

关键差异（这正是 5.3 分析差距的根因）：

1. **linear attention 被融合成单核**：llama.cpp 把整条 gated delta net 递归压进一个 `gated_delta_net_cuda`（72 次、单次均值约 10.4 µs）；local-llm 把同一逻辑拆成 `linear_attention_recurrent`（单次 40 µs）＋若干 `d_in_proj_*` 投影＋`conv` 分散小 kernel，每步要多发好几个核、还要往返读写 fp32 状态。
2. **attention 用了 FlashAttention**：llama.cpp 的 `flash_attn_ext_f16` 把打分/softmax/加权融为一体（且 KV 为 f16）；local-llm 的 `full_attention_attend` 未融合、带宽记 0（纯逻辑无 GEMM 访存），是明确的融合空缺。
3. **矩阵乘两边都占大头**（llama.cpp 87%、local-llm 逐 GEMM 有效带宽 500–860 GB/s），说明 GEMM 本身都不是瓶颈；差距集中在**序列建模算子（linear/full attention）的融合与访存**上。

> 口径与限制：llama.cpp 的 `llama-bench` 本身只产出 pp15/tg64 两个总吞吐，**没有逐算子明细**；上表的 kernel 级数据是额外用 `nsys` 抓取 GPU 时间线得到的，占比为「pp15+tg64 合并采集」下各 kernel 占 **GPU kernel 总时间** 的比例，与 local-llm 的「单次耗时」口径不同，不能逐格数值直接相减，只用于**看两边把每个功能环节实现成了什么、融合到什么程度**。

## 六、分析：公平口径下差距仍存在的原因

> 注：本节 SM / 带宽利用率取自 `--profile-sample-every 16` 采样式采集（开销约 1%，绝对值基本可信）；逐算子只在采样步计时，其 `count`/`total_ms` 不能当作 decode 全程占比，但**单次耗时 `avg_ms`**（第四节表）与瓶颈定位仍然成立。

1. **本模型主体是 linear attention（24/32 层），而非标准 attention。** [`2.md`](2.md) 的 ~9.5% 差距是在纯 full attention 的 Qwen 上测的；本模型换成 linear/full 混合后，占主导地位的是 linear attention 的**递归状态更新 + depthwise conv1d**（`linear_attention_recurrent` + `linear_attention_conv`）。这条路径 local-llm 目前是逐步 kernel、fp32 状态、无融合（`linear_attention_recurrent` 单次 0.04 ms、且需与一系列 `d_in_proj_*` / `d_out_proj` 投影串起来逐步执行）。llama.cpp 则把整条 linear attention 递归收进一个融合核 `gated_delta_net_cuda`（单次均值约 10.4 µs、占 GPU kernel 总时间 2.0%），这是拉开差距的第一主因。

2. **KV/state 精度与 FlashAttention。** llama.cpp 用 **f16 KV cache + FlashAttention**（`-fa on`，对应 `flash_attn_ext_f16` 融合核）；local-llm 是 **fp32 KV/state、无 FA**（`full_attention_attend` 未融合、单次 0.0271 ms、带宽记 0）。decode 是访存瓶颈，KV 精度减半 + attention 融合直接省一大截访存往返。

3. **设备侧证据一致**：采样式 profile 期间 **SM 均值 87.5%（峰值 97%）、显存带宽均值 63.5%（峰值 79%）**，说明 GPU 已经喂得比较满但仍未打满——既非纯算力瓶颈也非纯带宽瓶颈，而是**大量小 kernel 的启动开销与未融合导致的空转**（逐 token decode 每步要发起几十个小 kernel）。这正是融合优化的典型收益区间。

4. **不是正确性或权重加载问题**：权重一次性 H2D 851 ms（warmup 内完成，不计入稳态），KV/state 仅 55 MiB，显存占用健康（67%，受限于 3080 的 12GB）；投影类 GEMM 的有效带宽都在 500–860 GB/s（接近 3080 的 ~760 GB/s 理论值，lm_head 因是大矩阵单发甚至跑到 860），说明**GEMM 本身没问题，瓶颈在非 GEMM 的序列建模算子与 attention 融合**。

## 七、重要提醒：跨卡 / 跨模型 / 跨采集口径不可直接比

- **跨卡**：本次是 RTX 3080（带宽 ~760 GB/s），[`2.md`](2.md) 是 A4000（~448 GB/s）。decode 是带宽瓶颈，卡不同不可直接比绝对值——所以本次专门在同一张 3080 上重新编译并运行了两者。
- **跨模型**：本次是 `qwen3_5`（linear/full 混合），[`2.md`](2.md) 是标准 full-attention Qwen。**同为 "Qwen 4B" 但架构不同**，性能特征与差距成因都不一样，两篇结论不能混用。
- **跨采集口径**：local-llm 的 `--profile` 会引入采集开销（默认采样式约 1%、`--profile-sample-every 1` 全量最细约 13%），其 summary 里的绝对吞吐**不能**拿去和 llama.cpp（无逐算子埋点）比。跨实现对比一律用**关闭 profile 的基础墙钟**（64.8 tok/s）。

## 八、后续可优化方向（按预期收益排序）

1. **优化 linear attention 路径**：把递归状态更新（gated delta / SSM）与 conv1d 做 kernel 融合、状态用 bf16/f16，减少每步的小 kernel 数与访存往返——这是本模型上收益最大的方向。
2. **KV cache 改 f16**：直接减半 full attention 层的 KV 访存量。
3. **引入 FlashAttention 式融合 attention kernel**：替换当前未融合的 `full_attention_attend`。
4. **decode 小 kernel 合并 / CUDA Graph**：SM 利用率仍未打满，用 CUDA Graph 固化 decode 单步的 kernel 序列可显著降低启动开销。

## 八·补、已实施的 linear attention 优化（含 nsys 复测）

按第八节方向 1 实际动手优化了 local-llm 的 linear attention，全程用「贪心解码输出逐字对拍」兜底数值正确（三组固定 prompt 的输出在优化前后完全一致）。

### 8b.1 优化项与落点

1. **in_proj 共享 bf16 转换**（`LinearAttention.cpp` + `TensorTool` 新增 `prepare_lowp_input`/`gemm_lowp`）：linear attention 的 4 个 in_proj（qkv/z/b/a）用的是**同一份** hidden 输入、权重都是 bf16。旧路径每个 GEMM 各自把 f32 hidden 转一次 bf16，decode 每层 4 次冗余转换。改为**只转一次 bf16 复用**。nsys 里 `f32_to_bf16_copy_kernel` 调用次数从 17,430 降到 12,390（−29%）。
2. **recurrent kernel 提占用**（`kernel_internal.cuh` + `launch.cu`）：`linear_attention_recurrent(_batch)` 原来每个 value head 一个 block、仅 **256** 线程，而每 head 的递归状态有 `k_dim*v_dim=128*128=16384` 个元素，内层 decay / delta rule / 读出循环每线程要串行迭代 64 次。RTX 3080 有 68 个 SM，而 grid 只有 `value_heads=32` 个 block，本就欠占用，再叠加长串行内循环。把 block 线程数从 256 提到 **512**（`kLinearRecurBlock`，shared memory 同步按实际 block 尺寸计算），内层迭代次数减半、SM 内延迟隐藏更好。

> 说明：原计划的「融合 conv+recurrent 为单核」被 nsys 数据否掉——conv kernel 只占 0.4%（4.1ms），而 recurrent 占 6.1%（62ms），融合只能省掉 conv 那一次 launch（边际收益），且 `repeat=2` 会让两个 value head 的 block 重复写同一份 q/k conv_state（有竞态风险）。真正的瓶颈是 recurrent kernel 的欠占用，故改为直接提占用。

### 8b.2 nsys 复测（同口径，`--max-output-tokens 64`）

| kernel | 优化前 avg / 总耗时 / 占比 | 优化后 avg / 总耗时 / 占比 | 变化 |
| --- | --- | --- | --- |
| `linear_attention_recurrent`（decode） | 38,040 ns / 62.08 ms / 6.1% | **20,594 ns / 33.61 ms / 3.4%** | **avg −46%** |
| `linear_attention_recurrent_batch`（prefill） | 107,049 ns / 5.14 ms / 0.5% | **52,094 ns / 2.50 ms / 0.3%** | **avg −51%** |
| `linear_attention_conv`（decode） | 2,511 ns / 4.10 ms / 0.4% | 2,506 ns / 4.09 ms / 0.4% | 不变（未触碰） |
| `f32_to_bf16_copy` 调用次数 | 17,430 | **12,390** | **−29%** |

decode 稳态吞吐从 baseline **65.5 tok/s 提到约 66~67 tok/s**（recurrent 只占 GPU 忙时的个位数百分比，故整体吞吐提升幅度小于单 kernel 降幅；瓶颈已从 recurrent 转移到矩阵乘 GEMM）。三组固定 prompt 输出逐字一致，数值正确。

## 八·补·补、去逐层全设备同步（prefill「批量 GEMM」的实测澄清）

原计划要做的「prefill 批量 GEMM 融合」，调查源码后发现**前提不成立**：local-llm 的 prefill 早已是批量 GEMM——`gemm_main`（`cublasGemmEx`）以 `input_size`＝token 数为 batch，一次算完整段所有 token 的投影/MLP，并非逐 token 发射。5.1 节旧表述「无批量 GEMM 融合」据此修正。

真正拖慢 prefill/decode 的是另一处：**每个子层（attn/mlp）和每个 `DecoderLayer` 结尾都插了 `cudaDeviceSynchronize()`**，一次前向约 **96 次全设备同步**，把本可背靠背流水的 kernel 串成「发一批、停一批、CPU 阻塞等全卡清空」，GPU 反复空转。

### 8bb.1 去同步的正确性前提

所有 kernel 都在同一默认流上按序执行，**流内顺序已保证层间数据依赖**，逐层 `cudaDeviceSynchronize` 并非正确性必需，纯属保守/调试残留。整个 prefill/decode 主循环**全程无中途 CPU 读 GPU 结果**；唯一必需的 barrier 是前向末尾 lm_head 的 `to_host`（同步 D2H `cudaMemcpy`，隐式等待默认流所有前置 kernel 完成）。因此逐层同步可安全删除。

落点：把 7 处 `cudaDeviceSynchronize()` 换成非阻塞的 `check_cuda(cudaGetLastError(), ...)`——只返回并清除最近一次 launch/runtime 错误码，不阻塞，保留 launch 错误的即时反馈。涉及文件：`DecoderLayer.cpp`（prefill+decode 各 1）、`LinearAttention.cpp`（prefill+decode 各 1）、`FullAttention.cpp`（prefill+decode 各 1）、`SwiGLUMlp.cpp`（forward 1，被 prefill/decode 共用）。

### 8bb.2 A/B 验证（golden 对拍 + 墙钟/API 计数）

用独立 build 目录编出「带同步」对照 binary 与「去同步」主 binary，同机、同 prompt、同 `--max-output-tokens` 对拍：

| 指标 | 带同步（对照） | 去同步（优化后） | 变化 |
| --- | --- | --- | --- |
| `cudaDeviceSynchronize` API 调用 | 每层数十次（约 96 次/前向） | **全程仅 5 次**（warmup / main.cpp 停表用，层内已清零） | 层内彻底消除 |
| prefill 墙钟（长 prompt ~360 token，3 次均值） | 219.6 ms（218.5/218.8/221.4） | **215.3 ms**（215.5/215.4/215.1） | **−2%（−4.3 ms）** |
| decode 吞吐（短 prompt，2 次） | 67.27 / 67.23 tok/s | **69.09 / 69.06 tok/s** | **+2.7%** |

三组固定 prompt 输出逐字一致，数值零回归。

> 结论：**收益主要在 decode 而非 prefill**。prefill 阶段每步计算量大、GPU 本就喂得满，同步 gap 相对小（只 −2%）；decode 每步计算量小、逐层同步的 gap 占比高，去掉后 +2.7%。这也印证 5.1/六节的判断——prefill 不是「没批量 GEMM」，decode 瓶颈在小 kernel 启动开销与未融合的空转。下一步收益更大的仍是序列建模算子融合与 CUDA Graph（第八节方向 3/4）。

## 八·补·补·补、序列建模算子融合（conv1d→recurrent→读出 单核）+ 递归状态 bf16

承接第八节方向 3（序列建模算子融合）。此前 linear attention 的 decode/prefill 走两个分离 kernel：`linear_attention_conv`（depthwise conv1d + SiLU，结果写回显存中间 tensor `conv_out`）→ `linear_attention_recurrent`（读 `conv_out` 做 gated delta net）。两次 launch + 一次 `conv_out` 全量往返显存。

### 8bbb.1 融合方案与竞态处理

把 **conv1d → recurrent → 读出** 融进单个 kernel，conv 结果只留 shared memory、不落显存，省一次 kernel launch 与一次 `[tokens, conv_dim]` 往返。

关键难点是 q/k 的 conv 通道被 `repeat = value_heads / key_heads = 2` 个 value_head 共享。若按 value_head 分 block，会对同一 q/k conv_state 重复移位 → 竞态。解法：**改为按 key_head 分 block**（`grid = key_heads = 16`），每 block 处理 1 个 key_head 及其 2 个 value_head——q/k conv 每 token 只移位/算一次（放 shared），v conv 与 recurrent 各 value_head 一次。

### 8bbb.2 递归状态 fp32 → bf16

递归状态 `recurrent_state`（`[value_heads, k_dim, v_dim]`，每层 32×128×128）改用 bf16 存储，kernel 内一律 float 计算，只在读写持久 state 时转换（模板参数 `StateT` + `state_to_float`/`float_to_state` 特化，launch 端按 `state_bf16` flag 分派模板实例）。

- 单层 recurrent state：524,288 elems，fp32 2 MB → bf16 1 MB；24 个 linear 层合计 **48 MB → 24 MB（省 24 MB）**。
- bf16 的精度损失不足以翻转贪心 argmax：三组固定 prompt 输出与 fp32 逐字一致。

### 8bbb.3 分阶段验证（golden 对拍）

先做 fp32 融合验证零回归，再切 bf16 state 二次验证：

| 阶段 | decode 吞吐（同 prompt/贪心） | 三组 golden 输出 |
| --- | --- | --- |
| baseline（八节前，两 kernel + fp32 state） | ~64.8 tok/s | 基准 |
| 融合 kernel（fp32 state） | **~66.5 tok/s** | 逐字一致 |
| 融合 kernel + bf16 state | **~66.2 tok/s** | 逐字一致 |

> 结论：融合把两次 launch/一次显存往返合一，decode 吞吐 +2.5% 左右；bf16 state 吞吐基本持平（recurrent 已不是瓶颈），但显存立省 24 MB。两步均**数值零回归**。recurrent 占 GPU 忙时仅个位数百分比，故整体吞吐提升幅度小于单算子降幅——与八节判断一致，后续更大收益仍在 CUDA Graph（方向 4）。
>
> 注：本轮受远端 `nsys` importer 损坏（只产出 `.qdstrm`、无法生成 `.nsys-rep`）限制，未取到融合单核的逐 kernel 纳秒级细分；上表以端到端 decode 吞吐 + golden 对拍为准。

## 八·补·补·补·补、CUDA Graph（decode 单步端到端捕获重放）

承接第八节方向 4。前几轮融合/bf16 只带来个位数百分比的提升，印证 decode 的真正瓶颈是 **launch-bound**：单 token 逐层串行，一步要 launch 几百个小 kernel（32 层 × 每层若干 attention/GEMM/norm/逐元素核 + lm_head + argmax），每个 kernel 本身很快，但逐个 launch 的 host 开销累积可观。llama.cpp 领先的核心手段之一就是把这一整段录成 **CUDA Graph** 一次性重放，消除逐 kernel launch 开销。

### 8bbbb.1 目标边界：含 GPU argmax 的端到端闭环

把 **embedding → 32 层 → final_norm → lm_head GEMM → GPU argmax** 整段纯 GPU 计算录进一张 graph，后续每步 `cudaGraphLaunch` 重放。关键是让「下一个 token」也留在 device，构成闭环，避免每步 D2H logits + CPU argmax 打断 replay：

- 新增 device 常驻 `d_token`（`int`）：embedding 从它读输入 token，末尾 GPU argmax 把下一个 token 写回它 —— `d_token → embedding → … → argmax → d_token` 自成闭环。
- 新增 GPU argmax kernel（单 block，规约求 argmax，并列取最小 index，与 CPU `Sampler::argmax` 严格大于才更新语义一致），替代原「logits D2H → host sampler」。仅贪心可走此路径；带温度/top-k/top-p/重复惩罚时退回原 host 逐步路径。

### 8bbbb.2 让每步 kernel 参数不变（capture/replay 前置条件）

graph 一次 capture、后续 replay 要求每步的 kernel 参数与 shared memory 大小恒定，因此把每步变化的量都改成「从 device buffer 读」或「按上限固定」：

- **pos 改 device buffer**：full attention 的 3 个 decode kernel（q/kv/attend）参数 `int pos` → `const int *pos_dev`，kernel 内 `const int pos = *pos_dev;`。pos 的 device 值每步在 **graph 外** 异步写入 `d_pos`（graph 内 kernel 只读它），故 kernel 启动参数不随步变化。
- **attend 的动态 shared memory 按上限固定**：原来按 `(pos+1+block)` 每步变化，改为按 `(max_seq_len+block)` 固定分配，使 smem 在步与步之间不变。

### 8bbbb.3 迁流 + 首步 eager 预热

CUDA Graph 有两个硬约束，分两处处理：

1. **0 号默认流不可被 stream capture**：先把全部 kernel/cuBLAS/async memcpy 迁到一条进程级非阻塞流（`cublasSetStream` 每次 GEMM 设当前流；H2D/D2H 改 `cudaMemcpyAsync` + 同流 `cudaStreamSynchronize`）。迁流本身先独立验证零回归（修复了 `CPUTensor::to_gpu`/`GPUTensor::to_host` 裸 `cudaMemcpy` 跑在 0 号流、与 compute stream 不同步导致读到未算完 logits 的跨流竞态）。
2. **capture 期间禁止 cudaMalloc**：本项目激活走 grow-only scratch，decode 稳态尺寸 ≤ prefill，但保险起见——每个 session 的**首个贪心 decode 步走 eager**（不 capture，把所有 scratch 撑到 decode 稳态），从第二步起才 `cudaStreamBeginCapture`（`ThreadLocal` 模式）→ `EndCapture` → `Instantiate`，之后每步 `cudaGraphLaunch`。`prefill` 重建 session 时（device buffer 地址变化）自动失效并重新预热+捕获。

每步 graph 外仅剩：2 次 4 字节 async H2D（pos/prev_token）+ 1 次 4 字节 D2H（取回 next token 供 host 做 eos 判断）。

### 8bbbb.4 收益（golden 对拍 + A/B）

同 prompt、贪心、同机（RTX 3080）、同 Qwen3.5-4B BF16：

| 路径 | decode 吞吐（96 tok，`Once upon a time…`） | 三组 golden 输出 |
| --- | --- | --- |
| eager（每步逐 kernel launch，本轮对照） | ~65.4 tok/s（15.28 ms/token） | 逐字一致 |
| CUDA Graph（首步 eager 预热 + 后续 replay） | **~67.5 tok/s（14.81 ms/token）** | 逐字一致 |

> 结论：CUDA Graph 稳定带来 **+3.2%**（省 ~0.47 ms/token 的逐 kernel launch 开销），三组固定 prompt 输出**逐字一致、数值零回归**。
>
> 但这远未追平 llama.cpp（同机同权重贪心 ~86.8 tok/s，~11.5 ms/token）。说明本引擎 decode 的 15 ms/step 中，逐 kernel launch 开销只占约 0.5 ms，**绝大部分是 kernel 计算本身**——瓶颈已从「launch-bound」转向「kernel 效率」。后续要继续逼近 llama.cpp，重点不再是消除 launch，而是提升 attention/GEMM 等核的实现效率（如更好的分块/向量化访存、fused attention、量化 GEMM 走 tensor core 等）。

## 八·补·补·补·补·补、kernel 级微优化三连（argmax 之后的收尾）

承接 8bbbb 的结论——瓶颈已从「launch-bound」转向「kernel 效率」。本轮按易→难顺序清掉三项候选，验证口径统一：每项改动 rsync 远端 → `cmake --build` → 三组固定 prompt golden 逐字对拍（零回归）→ decode 吞吐复测。基线为 CUDA Graph + GPU argmax 后的 ~68.8–69.1 tok/s。

### 8bbbbb.1 f32→bf16 冗余转换合并（同源输入转一次、多 GEMM 复用）

**落点**：`SwiGLUMlp.cpp` 的 gate/up、`FullAttention.cpp` 的 q/k/v。这些 GEMM 吃**同一个** f32 激活输入，原先各自走 `TensorTool::gemm`（内部每次调用都把输入 f32→bf16 转一遍），同源输入被重复转换。

**方案**：仿 `LinearAttention.cpp` 已有范式——先 `prepare_lowp_input` 把输入转一次拿到 lowp 指针，再多次 `gemm_lowp` 复用：

```cpp
const void *d_in_lowp = TensorTool::prepare_lowp_input(
    g_in_f32, weights.s_gate_proj.dtype, scratch, scratch_key::kInputLowp);
const int in_rows = static_cast<int>(g_in_f32.rows());
TensorTool::gemm_lowp(weights.s_gate_proj, d_in_lowp, in_rows, g_gate_f32, "mlp.gate");
TensorTool::gemm_lowp(weights.s_up_proj,   d_in_lowp, in_rows, g_up_f32,   "mlp.up");
```

FullAttention 同理：q/k/v 三次转换合并为一次 `prepare_lowp_input` + 三次 `gemm_lowp`（prefill/decode 两条路径都改）。mlp.down、o_proj 吃的是各自独立的输入，保留原 `gemm`。

| 路径 | decode 吞吐 | 三组 golden |
| --- | --- | --- |
| 合并前 | ~69.2–69.4 tok/s | 逐字一致 |
| 合并后 | ~69.2–69.4 tok/s | 逐字一致 |

> 结论：**数值零回归、吞吐持平**。f32→bf16 是内存带宽型小核，且能与前序 GEMM 在流上重叠，合并只减少 kernel 数、不减墙钟时间。价值在于代码更干净（同源转换一次），性能收益可忽略。

### 8bbbbb.2 add + RMSNorm 融合小核（vLLM 式 fused add-rms-norm）

**落点**：`DecoderLayer.cpp` 的 `h = x + attn(...); post_norm(h)` 这一对。原先是 `add` + `RMSNorm::forward` 两次 launch、一次中间显存往返。

**方案**：新增 `add_rms_norm_kernel`（`kernel.cu`）——每 block 一行，一趟里同时做 `sr[j]=xr[j]+rr[j]`、累加平方和规约出 `inv_rms`、再 `dst[j]=sr[j]*inv_rms*w`。in-place 安全（out_residual==x 时每线程读写同索引，无跨线程竞态）。配套 `launch_add_rms_norm`（`launch.cu`）与 `TensorTool::add_rms_norm` 封装：

```cpp
TensorTool::add_rms_norm(s_post_norm_weight_, g_hidden_f32, g_mixer_f32, g_hidden_f32,
                         g_token_hidden_b_f32, rms_norm_eps, /*one_plus=*/true);
```

prefill/decode 两条路径的 post_norm 都改用融合核（32 层各省 1 次 launch）。input_norm 前的残差 add 是跨层残差、未融合。

| 路径 | decode 吞吐 | 三组 golden |
| --- | --- | --- |
| 融合前 | ~69.2–69.4 tok/s | 逐字一致 |
| 融合后 | ~69.25–69.3 tok/s | 逐字一致 |

> 结论：**数值零回归、吞吐持平**。CUDA Graph replay 下 launch 本就极廉，省 32 次 launch 对墙钟无感；融合核减少一次显存往返，理论上略优，实测在噪声内。保留（更少 kernel、更少中间 buffer）。

### 8bbbbb.3 linear_attention_fused 尝试与回退（教训）

**落点**：`kernel.cu` 的 `linear_attn_fused_step`（decode 版 grid=key_heads=16、block=512，对每个 value_head 的 state 矩阵 16384 元素做 4 趟遍历：decay / kv_mem→delta / update / output）。它是 profiling 里的单步最大头（~1.23 ms/step）。

**尝试**：把 4 趟遍历合并为 2 趟——让每线程独占一个 vd 列、沿 kd 内循环，顺带移除 `delta` shared buffer，意图减少 global 往返、提高访存合并。

**结果**：吞吐 **69.3 → 64.6 tok/s（劣化，15.5 ms/token）**，已完全回退。

> 教训：原实现用 512 线程去遍历 state_size=16384，并行度高、把 SM 喂饱；我改成「每线程独占 1 个 vd 列（v_dim=128）」后只有 128 线程活跃、384 空转，且每线程还要串行遍历 k_dim=128 次——**并行度从 512 骤降到 128，得不偿失**。recurrent state 的递归在 token 维天然串行，要真正提速需更精细的手法（warp 内分工、寄存器 tiling、把 state 常驻寄存器/共享内存复用），风险高、单步仅占 ~8%、收益比低。**暂不深挖**，恢复原 4-pass 高并行实现。

### 8bbbbb.4 本轮小结

| 优化项 | 墙钟收益 | 数值 | 处置 |
| --- | --- | --- | --- |
| argmax 多 block 两阶段规约（上一轮） | 67.5→68.8–69.1 | 零回归 | 保留 |
| f32→bf16 同源转换合并 | 持平 | 零回归 | 保留（代码更干净） |
| add+RMSNorm 融合核 | 持平（噪声内） | 零回归 | 保留（更少 kernel/buffer） |
| linear_attention 2-pass 合并 | 69.3→64.6 劣化 | 零回归 | **回退** |

> 整体：baseline 64.8 → 本轮收尾稳定 **~69.3 tok/s（+7%）**，全程数值零回归。但每项都是边际收益，再次印证 8bbbb 判断——距 llama.cpp（~86.8 tok/s）的差距主要在 attention/GEMM 核的**计算效率本身**（tensor core 利用、量化 GEMM、fused attention），而非 launch 或逐元素小核。这类深水区改动风险与收益都更大，需单独立项评估。
