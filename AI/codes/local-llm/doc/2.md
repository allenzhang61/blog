# 性能对比：local-llm vs llm-inference-cpp vs llama.cpp

本文记录一次三方推理性能对比，用于判断新写的 local-llm 相对参考实现是否存在性能退化。

**结论先行**：local-llm 无实质退化，decode 稳态吞吐与 llm-inference-cpp、llama.cpp 处于同一档位。

## 一、测试环境与口径

- **硬件**：远端 RTX A4000（16GB，显存带宽约 448 GB/s），CUDA 12.4
- **模型**：Qwen3.5-4B，BF16 权重
- **解码**：greedy，生成 64 tokens
- **构建**：三者均以 Release 构建
- **计时口径**：统一看 **decode 稳态每 token 耗时**——即 warmup 之后、逐 token 生成阶段的平均耗时。这是最能代表推理性能且几乎不受 input 长度影响的指标（decode 每步只处理 1 个 token）。

为对齐口径对 local-llm 做了两处临时改动（见 [`main.cpp`](../src/main.cpp)）：

1. 加了 `PROFILE` 计时输出（prefill_s / decode_total_s / decode_per_token_ms / decode_tokens_per_s）；
2. 正式计时前跑一次完整前向 warmup（独立 session），触发权重惰性上传、CUDA context / cuBLAS 初始化与 kernel 首次启动，剔除首步冷启动对稳态计时的污染。

llm-inference-cpp 用其内置的 `--profile-timing --warmup-runs 1`；llama.cpp 用 `llama-bench` 的 tg64（纯稳态生成，天然不含 prefill 与冷启）。

## 二、运行命令

local-llm：

```bash
./build-release/local_llm --model-dir <Qwen3.5-4B snapshot> --max-output-tokens 64
```

llm-inference-cpp（参考项目）：

```bash
./llm-inference-cpp --model-dir <Qwen3.5-4B snapshot> \
    --max-new-tokens 64 --greedy --device cuda --warmup-runs 1 --profile-timing
```

llama.cpp（口径沿用 `llm-inference-python/doc/5.md` 记录）：

```bash
llama-bench -m Qwen_Qwen3.5-4B-bf16.gguf -ngl 99 -fa on -p 15 -n 64 -r 5
```

## 三、结果（同一张 A4000）

| 实现 | 权重格式 | KV cache | decode 每 token | decode 吞吐 |
| --- | --- | --- | --- | --- |
| **llama.cpp** (tg64) | GGUF BF16 | f16 + FlashAttention | **23.1 ms** | **43.2 tok/s** |
| **llm-inference-cpp**（参考） | safetensors BF16 | f16 | 24.3 ms | 41.2 tok/s |
| **local-llm**（本项目） | safetensors BF16 | fp32，无 FA | 25.3 ms | 39.5 tok/s |

数据在多次重复间高度稳定（decode_total 抖动 < 0.5%）。

## 四、分析

- **无实质退化**：local-llm 的 decode 每 token 25.3ms，比参考项目慢约 4%、比 llama.cpp 慢约 9.5%，差距很小且方向可解释。上一篇 [`1.md`](1.md) 的“投影前统一转权重 dtype”改动没有引入额外开销——参考项目本来也做同样的激活转 BF16。
- **llama.cpp 略快是合理的**：它用了 **FlashAttention + f16 KV cache**，更省访存带宽；local-llm 目前是 **fp32 KV cache、无 FA**。decode 阶段是访存瓶颈，KV 精度与 attention 是否融合直接影响带宽占用。这属于可优化空间，不是缺陷。

## 五、重要提醒：跨卡数据不可直接比

`llm-inference-python/doc/5.md` 里 llama.cpp 记录的 **79.5 tok/s 是 RTX 3080** 上测的；同样口径在 A4000 上只有 **43.2 tok/s**。原因是 A4000 显存带宽（~448 GB/s）远低于 3080（~760 GB/s），而 decode 是带宽瓶颈。

因此**性能对比必须在同一张卡上进行**。若直接拿记录里的 3080 数据与 A4000 上的 local-llm 相比，会得出错误的“严重退化”结论。本次专门在 A4000 上重新编译并运行了 llama.cpp，保证三方同卡。

## 六、后续可优化方向（按收益排序）

1. **KV cache 改 f16**：直接减半 attention 阶段的 KV 访存量。
2. **引入 FlashAttention 式融合 attention kernel**：减少中间量的显存往返。
