# llm-train-cpp vs llm-train-python 三后端对比（v4）

本文记录 `AI/codes/llm-train-cpp` 与 `AI/codes/llm-train-python` 在 **train normal / aligned** 口径下的 CPU / Metal / CUDA 三后端性能对比。承接 [v3.md](./v3.md) 的 C++ GPU 后端优化，本轮重点是把 PyTorch 版也扩展为显式 `cpu` / `cuda` / `metal` 三种设备模式，并实际跑出数据。

对比配置：

| 配置 | vocab | ctx | emb | heads | layers | epochs | steps |
|------|-------|-----|-----|-------|--------|--------|-------|
| normal | 50257 | 256 | 768 | 12 | 12 | 10 | 90 |

共同超参：`batch=2`、`stride=ctx`、不 shuffle、`drop_last=True`、种子 123，AdamW `lr=4e-4, weight_decay=0.1`。

测试环境：

- CPU / Metal：Apple M3 Pro，本机 Release 构建。
- CUDA：远端 `lxa@192.168.1.110`，NVIDIA GPU，源码和构建目录放在 `D:\cuda-llm-bench\llm-train-cpp-current`。
- Python CPU / Metal：本机临时 venv，PyTorch `2.13.0`，`torch.backends.mps.is_available() == True`。
- Python CUDA：远端 `lxa@192.168.1.110`，PyTorch `2.5.1+cu121`，GPU 为 NVIDIA GeForce RTX 3080。

运行方式：

```bash
# max_steps=0 表示完整 normal；profile_steps=0 关闭 step profile；log_interval=0 只在最后读取 loss
train_gpt <cpu|metal|cuda> normal 0 0 0

# PyTorch 版；aligned 使用同一份 token id、不 shuffle、drop_rate=0、不做 eval/plot。
# metal 会映射到 torch.device("mps")
python main.py <cpu|metal|cuda|auto> normal aligned 0 0
```

## 1. 最终性能对比

### 1.1 normal aligned 10 steps

| 实现 | 后端 | 耗时 | final loss | 相对 C++ CPU |
|------|------|------|------------|--------------|
| C++ | CPU | 57.24 s | 7.11079 | 1.0x |
| C++ | Metal | 5.45 s | 7.11078 | ~10.5x faster |
| C++ | CUDA | 12.20 s | 7.11078 | ~4.7x faster |
| Python / PyTorch | CPU | 8.37 s | 7.14002 | ~6.8x faster |
| Python / PyTorch | Metal/MPS | 6.84 s | 7.14002 | ~8.4x faster |
| Python / PyTorch | CUDA | 13.37 s | 7.14002 | ~4.3x faster |

### 1.2 normal aligned full（90 steps）

| 实现 | 后端 | 耗时 | final loss | 相对 C++ CPU |
|------|------|------|------------|--------------|
| C++ | CPU | 444.28 s | 0.479891 | 1.0x |
| C++ | Metal | 30.49 s | 0.479799 | ~14.6x faster |
| C++ | CUDA | 75.43 s | 0.479826 | ~5.9x faster |
| Python / PyTorch | CPU | 33.76 s | 0.47616 | ~13.2x faster |
| Python / PyTorch | Metal/MPS | 9.56 s | 0.47616 | ~46.5x faster |
| Python / PyTorch | CUDA | 33.26 s | 0.47616 | ~13.4x faster |

结论：

- PyTorch 三后端的 final loss 完全一致，说明设备间数值路径稳定。
- C++ 三后端 final loss 也一致在 `0.4798~0.4799`，与 PyTorch 的 `0.47616` 同量级；差异主要来自初始化/RNG 实现不同。
- PyTorch CPU 已经比 C++ CPU 快约 **13x**；PyTorch Metal/MPS 最快，full normal 仅 **9.56s**。
- C++ Metal 优化后已经接近可用，full normal **30.49s**，但仍比 PyTorch MPS 慢约 **3.2x**。

### 1.3 内存消耗对比

内存数据使用 normal aligned 10 steps 采样。这个口径已经覆盖模型初始化、前向、loss、反向和优化器更新；对于当前 workload，主要训练峰值通常在第一轮 backward 后已经出现。

测量口径：

- macOS CPU / Metal / MPS：`/usr/bin/time -l`，记录 `maximum resident set size`，同时保留 `peak memory footprint`。
- Windows CUDA：PowerShell 轮询进程 `PeakWorkingSet64`，GPU 显存用 `nvidia-smi --query-gpu=memory.used` 采样，表中显存为相对运行前 baseline 的增量。

| 实现 | 后端 | Host RSS / Working Set | 设备 / 统一内存峰值 | 备注 |
|------|------|------------------------|----------------------|------|
| C++ | CPU | ~10.87 GiB | macOS footprint ~10.86 GiB | host Tensor 以 double 为主，训练中间量较大 |
| C++ | Metal | ~5.68 GiB | macOS footprint ~17.94 GiB | Apple 统一内存；Metal buffer 主要体现在 footprint |
| C++ | CUDA | ~5.36 GiB | GPU +~6.07 GiB | RTX 3080，baseline 约 62 MiB |
| Python / PyTorch | CPU | ~3.88 GiB | macOS footprint ~3.82 GiB | PyTorch CPU 默认 float32，allocator 复用更充分 |
| Python / PyTorch | Metal/MPS | ~0.85 GiB | macOS footprint ~5.42 GiB | MPS/统一内存路径，host RSS 很低 |
| Python / PyTorch | CUDA | ~1.51 GiB | GPU +~3.70 GiB | PyTorch CUDA caching allocator，会保留部分显存池 |

观察：

- C++ CPU 的 host 内存明显高于 PyTorch CPU，主要来自 double host Tensor、中间 Tensor mirror、自研 autograd 节点和缓冲区复用不足。
- C++ Metal 的 RSS 不高，但 macOS footprint 很高，说明大量内存进入 Metal buffer / 统一内存路径。
- PyTorch MPS 在速度和内存上都最优：full normal 9.56s，10-step footprint 约 5.42 GiB。
- CUDA 上 C++ 显存增量约 6.07 GiB，高于 PyTorch CUDA 的 3.70 GiB，说明 C++ CUDA 仍有较多中间 buffer / grad buffer / storage 保留空间。

## 2. CUDA 优化记录

### 2.1 主要问题

优化前 CUDA 路径虽然算子在 GPU 上跑，但整体并不快，核心瓶颈有几类：

1. **matmul 仍是朴素 kernel**：normal 配置中大量 `[B*T, emb] x [emb, vocab]` 和 Linear/MLP 矩阵乘，手写 kernel 无法接近 cuBLAS。
2. **transpose 在 host 预计算 index**：每次 transpose 都在 CPU 上构造「输出 flat -> 输入 flat」索引表，再上传给 `gather_kernel`，normal 下反复发生，GPU 被 host 端准备工作拖住。
3. **cross_entropy 过于串行**：loss / grad 对大词表 `vocab=50257` 的处理不够并行。
4. **每个 kernel 后强制同步**：`cudaDeviceSynchronize()` 让 CUDA 失去默认 stream 的异步排队能力。
5. **GPU 中间 Tensor 分配 host mirror**：中间 logits 等大张量会额外分配 host `std::vector<double>`，带来内存和构造开销。

### 2.2 已完成优化

- `CMakeLists.txt`
  - CUDA 构建时 `find_package(CUDAToolkit REQUIRED)`。
  - 链接 `CUDA::cublas`。

- `cuda_runtime.cu/.hpp`
  - `matmul_buffer()` / `matmul_grad()` 改用 `cublasSgemm`。
  - `sync()` 从 `cudaDeviceSynchronize()` 改为只做 launch error check；必要同步由 D2H copy 或外部读回触发。
  - 新增 `LLM_CPP_CUDA_PROFILE=1` 的 op 级 profiler。
  - 新增设备端 `transpose_buffer()` / `transpose_add_grad()`。

- `cuda_device_kernels.cu/.cuh`
  - 新增 rank <= 4 的 generic transpose kernel。
  - 新增 transpose backward kernel。
  - cross entropy loss / grad 改成更并行的 row-based kernel。

- `cuda_ops.cu`
  - `transpose()` 不再 host 预计算 index，也不再走 `gather/scatter_add_grad`。
  - 中间 CUDA output 不再默认分配大 host mirror。
  - grad buffer 对全零梯度走 device fill，避免大 host zero vector 上传。

### 2.3 CUDA profiler 观察

优化后 3 step profiler 显示：

- 旧的 `gather_buffer` / `scatter_add_grad` 已经从训练路径消失。
- matmul 前/反向耗时已被 cuBLAS 压低。
- 剩余大头主要是首次/逐步的 host->device copy、grad fill 和大量小 kernel 派发。

## 3. Metal 优化记录

### 3.1 主要问题

Metal 优化前比 CPU 慢，关键瓶颈比 CUDA 更集中：

1. **cross_entropy grad 复杂度过高**：旧实现是每个 logit 一个线程，但每个线程又完整扫描一遍 vocab，相当于 `rows * vocab * vocab` 量级；normal 的 `50257` 词表会直接炸。
2. **cross_entropy loss 单线程全量扫所有 row/vocab**：loss 读回时看到 `item_ms` 接近 7s，实际是在等待前面积累的 GPU work 完成。
3. **2D matmul 仍是朴素 Metal shader**：Linear/MLP/输出层需要系统级矩阵乘优化。
4. **transpose 同样在 host 预计算 index**：和 CUDA 一样，host index + gather/scatter 会拖慢 GPU。
5. **中间 Tensor host mirror 和 grad zero vector 开销**：大中间张量不应默认分配 host 数据。

### 3.2 已完成优化

- `CMakeLists.txt`
  - Metal 构建新增链接 `MetalPerformanceShaders`。

- `MetalKernels.mm`
  - 2D `matmul_buffer()` / `matmul_grad()` 改用 `MPSMatrixMultiplication`。
  - `transpose()` 正反向改为设备端 shader。
  - `cross_entropy_loss_buffer()` 改为先按 row 计算 loss，再 sum + scale。
  - `cross_entropy_grad()` 改为每行一个线程扫描 vocab 并写整行梯度，将复杂度拉回 `rows * vocab`。
  - 中间 Metal output 不再默认分配大 host mirror。
  - grad buffer 对全零梯度走 device fill。
  - command buffer 提交时等待上一批完成，避免 full normal 长跑时 in-flight work 堆积不稳定。

- `metal_kernels.metal`
  - 新增 `transpose_kernel` / `transpose_add_grad_kernel`。
  - 新增 `cross_entropy_grad_rows_kernel`。

### 3.3 一个已尝试但回退的方向

曾尝试把 attention 的 `batch_matmul` 也改成 MPS，但实际收益不明显，并且 full normal 长跑会在 70 step 后不稳定。因此最终版本保留原有 batch matmul shader，只使用 MPS 加速 2D matmul。

## 4. benchmark 参数

为避免 benchmark 被每步 `loss.item()` 的 GPU 同步污染，C++ 与 Python 都支持关闭逐步读取 loss。

C++：

```bash
train_gpt [backend] [profile] [max_steps] [profile_steps] [log_interval]
```

参数说明：

- `backend`：`cpu` / `metal` / `cuda`。
- `profile`：`normal` / `small`。
- `max_steps`：限制训练步数；`0` 表示完整配置。
- `profile_steps`：非 0 时输出每步耗时拆分。
- `log_interval`：默认 `1` 每步打印 loss；`0` 表示只在最后读取 loss。

Python：

```bash
python main.py [cpu|cuda|metal|auto] [small|normal] [aligned|demo] [max_steps] [log_interval]
```

参数说明：

- `aligned`：与 C++ benchmark 对齐的纯训练模式。
- `demo`：保留原书籍示例入口，normal 会做 eval、sample、plot。

本轮对比主要使用：

```bash
train_gpt cpu normal 10 0 0
train_gpt metal normal 10 0 0
train_gpt cuda normal 10 0 0

train_gpt cpu normal 0 0 0
train_gpt metal normal 0 0 0
train_gpt cuda normal 0 0 0

python main.py cpu normal aligned 10 0
python main.py metal normal aligned 10 0
python main.py cuda normal aligned 10 0

python main.py cpu normal aligned 0 0
python main.py metal normal aligned 0 0
python main.py cuda normal aligned 0 0
```

## 6. 结论

- **PyTorch 仍是性能标杆**：Python/PyTorch MPS full normal 为 **9.56s**，是本轮最快。
- **C++ GPU 优化有效**：C++ Metal **30.49s**、C++ CUDA **75.43s**，都显著快过 C++ CPU **444.28s**。
- **C++ CPU 差距最大**：PyTorch CPU **33.76s**，约比 C++ CPU 快 **13x**。
- **CUDA 结果有环境差异**：PyTorch CUDA 在 RTX 3080 上 full 为 **33.26s**，C++ CUDA 为 **75.43s**；两者都包含进程启动、模型初始化和完整 90 step 训练。
- **后续优化点**：C++ CUDA 仍有大量小 kernel / grad fill / H2D copy 开销；C++ Metal attention 的 batch matmul 仍是朴素 shader，未来可继续做稳定的 batched GEMM/MPSGraph 路径。
