# 为什么 PyTorch CPU 比 C++ CPU 快很多（v4-1）

本文是 [v4.md](./v4.md) 的补充说明，解释为什么在同样的 `normal aligned` 训练口径下，`llm-train-python` 的 PyTorch CPU 版本会明显快过 `llm-train-cpp` 的 CPU 版本。

v4 中的 full normal（90 step）结果：

| 实现 | 后端 | 耗时 | final loss |
|------|------|------|------------|
| C++ | CPU | 444.28 s | 0.479891 |
| Python / PyTorch | CPU | 33.76 s | 0.47616 |

PyTorch CPU 约比 C++ CPU 快 **13x**。这不是“Python 解释器比 C++ 快”，而是 **PyTorch 背后调用的是成熟深度学习运行时和高度优化的 CPU kernel**；当前 C++ 版则是教学目的的手写 Tensor / autograd / ops 实现。

---

## 1. 不是语言差距，而是运行时差距

`llm-train-python` 的 Python 代码只是前端调度，真正耗时的部分主要在 PyTorch 的 C++/汇编/系统库 kernel 里运行：

- `nn.Linear` / `matmul` 会走 BLAS / oneDNN / Accelerate 等优化路径。
- `cross_entropy` / `softmax` / `layer_norm` 等算子也有专门优化实现。
- 张量内存布局、线程池、SIMD、缓存分块、临时内存复用都由 PyTorch runtime 处理。

`llm-train-cpp` 虽然是 C++ 写的，但它本质上是一个教学框架：

- 自研 Tensor。
- 自研动态图 autograd。
- 很多算子是朴素循环或逐 op 调度。
- 内存复用、算子融合、线程池、向量化覆盖都不完整。

所以这里比较的是：

> PyTorch 成熟训练运行时 vs 手写教学版 C++ autograd。

不是：

> Python 语言 vs C++ 语言。

---

## 2. C++ CPU 只优化了 matmul，其他大算子仍是短板

v2 已经把 C++ CPU 的 matmul 接到了 macOS Accelerate BLAS，matmul 前向/反向快了很多。但 normal 配置的瓶颈不只有 matmul：

| 算子类型 | normal 下的问题 |
|----------|-----------------|
| cross_entropy | `vocab=50257`，每个 token 都要处理大词表 |
| softmax / log_softmax | 大量 `exp` / `sum` / normalize |
| layernorm | 每层多次统计 mean/var |
| elementwise / grad 累加 | 大量小算子，多次遍历内存 |
| autograd 调度 | 每个 op 都有 TensorNode / parents / backward closure |

PyTorch 对这些算子都有高度优化；C++ CPU 版很多仍是朴素实现。因此 BLAS 把 matmul 拉起来后，瓶颈会转移到这些非矩阵乘算子上。

这也是为什么 C++ GPU 优化时，Metal 的最大收益来自 **cross_entropy**：旧 Metal CE 反向复杂度过高，修完之后 full normal 从慢于 CPU 直接降到 30.49s。

---

## 3. float32 vs double / host mirror 的差异

PyTorch 默认训练使用 `float32`：

- 内存占用更小。
- SIMD 吞吐更高。
- cache / memory bandwidth 压力更低。

C++ 版 host Tensor 主要使用 `double`，GPU storage 使用 float，中间还有 host/device dirty 标记和同步逻辑。即使 CPU matmul 接 BLAS，其他 CPU 路径仍会受 double 内存带宽和转换设计影响。

normal 配置中 logits 形状很大：

```text
[batch, ctx, vocab] = [2, 256, 50257]
```

这类张量一旦落到 host double，内存量和遍历成本都会非常明显。

---

## 4. PyTorch 有成熟的多线程和内存调度

PyTorch CPU 后端通常会用线程池和底层库自动并行：

- 大矩阵乘多线程分块。
- softmax / layernorm / loss 等按行或按块并行。
- 临时内存由 allocator 复用，减少频繁 malloc/free。
- op kernel 通常对连续内存和 cache locality 做过优化。

C++ 教学版目前更多是“每个算子自己做一遍事情”：

- 小 kernel / 小循环多。
- 中间 Tensor 分配多。
- autograd 节点和闭包调度开销高。
- 很少做算子融合。

这些工程细节叠加起来，就会形成 v4 里看到的 13x 差距。

---

## 5. 为什么 PyTorch CUDA 没有比 PyTorch CPU 快很多

v4 中 PyTorch CUDA full normal 为 33.26s，PyTorch CPU 为 33.76s，几乎同量级。这个结果看起来反直觉，但有几个原因：

1. 模型和数据很小，只有 90 step，启动、初始化、数据搬运和 kernel launch 开销占比高。
2. batch size 只有 2，ctx=256，对 RTX 3080 来说并不一定能把 GPU 吃满。
3. 远端 CUDA 机器和本机 CPU/MPS 不是同一台机器，不能只看后端名称做绝对判断。
4. PyTorch CPU 后端本身已经非常强，尤其在小 batch / 小训练轮数下。

所以这组数据更适合说明：在当前 workload 下，PyTorch CPU 已经是很强的基线；要让 CUDA 明显领先，需要更大的 batch、更长训练、更少同步、更多连续大 GEMM。

---

## 6. 如果想缩小 C++ CPU 差距

优先级大致如下：

1. **把更多 CPU 算子改成 float32 + SIMD / 多线程**：尤其是 cross_entropy、softmax、layernorm。
2. **减少中间 Tensor 的 host double mirror**：避免大 logits 在 host 侧重复分配和遍历。
3. **减少 autograd 调度开销**：复用节点/缓冲区，避免大量小对象分配。
4. **做算子融合**：例如 cross_entropy 直接从 logits + targets 计算 loss 和 grad，避免显式 log_softmax 大中间张量。
5. **接入成熟 CPU kernel 库**：oneDNN / XNNPACK / Eigen / Accelerate vDSP 等。
6. **引入线程池**：对 row-wise 算子按 batch/token/row 并行。

不过要注意：这些优化会显著增加代码复杂度。当前 `llm-train-cpp` 的价值主要是教学和可调试性；如果目标是训练吞吐，PyTorch 这类成熟框架仍然是合理基线。

---

## 7. 结论

- PyTorch CPU 快，是因为实际计算在高度优化的 native kernel 中完成，不是因为 Python 本身快。
- C++ CPU 慢，是因为当前实现偏教学：自研 Tensor/autograd、朴素非 matmul 算子、double host 数据、内存复用和多线程不足。
- C++ GPU 优化已经证明方向有效：当把热点算子替换为 cuBLAS / MPS / 并行 CE 后，Metal 和 CUDA 都能明显快过 C++ CPU。
- 若继续优化 C++ CPU，重点不应再只看 matmul，而应集中在大词表 CE/softmax、layernorm、elementwise、内存复用和线程化。
