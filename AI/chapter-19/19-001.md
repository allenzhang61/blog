# 大模型评测指标

大模型评测不能只看一个榜单分数。比较完整的评测通常会同时看：

- 模型本身会不会：知识、推理、代码、语言、多模态
- 回答靠不靠谱：幻觉、事实性、安全性、指令遵循
- 在业务里好不好用：任务完成率、格式稳定性、工具调用、RAG 引用
- 部署起来划不划算：延迟、吞吐、上下文长度、成本

## 1. 能力指标

### 知识问答能力

看模型对事实知识、常识、百科类问题的回答是否准确。

常见问题：

- 是否知道基础事实
- 是否能区分相似概念
- 是否会编造不存在的人名、论文、链接、API
- 是否能承认不知道

### 推理能力

看模型是否能完成多步推理，而不是只靠记忆回答。

常见任务：

- 数学题
- 逻辑题
- 多跳问答
- 因果分析
- 复杂条件约束推导

评测时要特别注意：有些题模型可能在训练数据中见过，所以高分不一定代表真实泛化能力。

### 代码能力

代码模型或通用大模型经常会单独评测代码能力。

常见维度：

- 代码生成
- 代码补全
- Bug 修复
- 代码解释
- 单元测试生成
- 根据报错定位问题

常见指标是 **Pass@k**：

$$Pass@k = P(\text{k 个候选答案中至少有一个通过测试})$$

例如 Pass@1 表示模型第一次生成的代码就能通过测试的比例。

### 语言能力

看模型对自然语言的理解和生成质量。

常见任务：

- 摘要
- 翻译
- 改写
- 信息抽取
- 文本分类
- 长文本阅读理解

传统 NLP 指标如 BLEU、ROUGE、METEOR 仍然能用，但它们更适合有标准答案的任务。对于开放式回答，通常还需要人工评测或模型评测。

### 多语言能力

如果模型要用于中文、英文或多语言场景，需要单独评测多语言能力。

需要看：

- 中文表达是否自然
- 中英混合术语是否准确
- 小语种是否明显退化
- 是否能保持同一种语言回答
- 翻译时是否丢信息或过度意译

### 多模态能力

如果是 VLM 或多模态模型，还会看：

- 图像理解
- OCR
- 图表理解
- 图文推理
- 视频理解
- 音频理解
- 跨模态指令遵循

例如给一张图表，模型不仅要读出文字，还要能理解趋势、比较数值、回答推理问题。

## 2. 对齐与安全指标

### 指令遵循能力

看模型是否能准确执行用户要求。

常见检查点：

- 是否遵守输出格式
- 是否回答了所有子问题
- 是否按要求使用指定语言
- 是否能处理约束条件，例如“只输出 JSON”
- 是否不会擅自扩展或改变任务目标

### 幻觉率

幻觉（Hallucination）指模型生成看似合理但实际错误或没有依据的内容。

常见幻觉：

- 编造事实
- 编造论文
- 编造引用来源
- 编造 API 参数
- 错误解释代码行为
- 对不确定信息过度肯定

幻觉评测通常看两个方面：

- **事实正确性**：回答本身是否正确
- **可验证性**：回答是否能被来源、上下文或工具结果支持

### 安全拒答

看模型在危险、违法、隐私、医疗法律等高风险问题上是否有合理边界。

需要同时避免两个极端：

- 该拒绝的时候没有拒绝
- 不该拒绝的时候过度拒绝

所以安全评测不仅看拒答率，还要看拒答是否准确。

### 偏见与公平性

看模型是否对性别、种族、地域、职业、年龄等群体输出不当偏见。

这类指标通常很难靠单一数值完全表达，需要结合测试集、人工审查和场景风险判断。

### 毒性与攻击性

看模型是否输出仇恨、辱骂、歧视、暴力煽动等内容。

常见做法是用分类器、人审或专门安全测试集评估毒性输出比例。

## 3. 任务效果指标

### Accuracy

准确率，适合选择题、分类题、判断题。

$$Accuracy = \frac{\text{预测正确的样本数}}{\text{总样本数}}$$

优点是直观，缺点是对开放式生成任务不够适合。

### Precision / Recall / F1

信息抽取、分类、检索增强任务常用。

**Precision**：模型预测为正的样本中，真正为正的比例。

$$Precision = \frac{TP}{TP + FP}$$

**Recall**：所有真正为正的样本中，被模型找出来的比例。

$$Recall = \frac{TP}{TP + FN}$$

**F1**：Precision 和 Recall 的调和平均。

$$F1 = \frac{2 \cdot Precision \cdot Recall}{Precision + Recall}$$

### BLEU / ROUGE

传统生成任务常用。

- **BLEU**：常用于机器翻译，关注生成文本与参考答案的 n-gram 重合
- **ROUGE**：常用于摘要，关注生成摘要覆盖了多少参考摘要内容

这类指标适合自动化批量评测，但对大模型开放式回答有局限：同一个问题可能有很多种正确表达，n-gram 重合低不一定代表回答差。

### Win Rate

两个模型对比时常用。

做法是给同一批问题分别生成答案，然后让人工或评测模型判断哪个更好。

$$Win\ Rate = \frac{\text{模型 A 获胜次数}}{\text{总对比次数}}$$

如果有平局，也可以单独统计 Tie Rate。

### Human Preference

人工偏好评分更接近真实用户体验。

常见评价维度：

- 正确性
- 完整性
- 有用性
- 表达清晰度
- 是否啰嗦
- 是否遵循指令

缺点是成本高、速度慢，并且不同标注人的标准可能不一致。

## 4. 工程性能指标

### 延迟

常见延迟指标：

| 指标 | 含义 |
|------|------|
| TTFT | Time To First Token，首 token 延迟 |
| TPOT | Time Per Output Token，每个输出 token 的平均耗时 |
| E2E Latency | 从请求发出到完整响应返回的总耗时 |

交互式聊天尤其关注 TTFT，因为用户首先感知到的是模型多久开始输出。

### 吞吐量

吞吐量衡量单位时间能处理多少请求或 token。

常见写法：

- requests/s
- input tokens/s
- output tokens/s
- total tokens/s

线上服务通常要同时看延迟和吞吐。单纯吞吐高但延迟很大，不一定适合实时聊天。

### 上下文长度

上下文长度不只是“最多能塞多少 token”，还要看长上下文下的有效能力。

需要评测：

- 长文档中是否能找到关键信息
- 是否会遗漏中间位置的信息
- 是否能跨多段内容综合推理
- 引用长上下文时是否准确

很多模型在短上下文表现好，但上下文变长后会出现注意力退化。

### 成本

成本通常包括：

- 每百万 input token 价格
- 每百万 output token 价格
- 自部署 GPU 成本
- 并发所需机器数量
- 缓存、向量库、检索服务等周边成本

实际选型时要结合业务请求量和平均输入输出长度估算总成本。

### 稳定性与可控性

实际业务里很重要，但榜单中不一定充分体现。

常见问题：

- 多次调用格式不稳定
- JSON 偶尔不合法
- 表格列名漂移
- 对同一类问题回答风格差异很大
- 温度较低时仍然输出不稳定

如果模型要接到程序里，格式稳定性有时比开放问答分数更重要。

## 5. RAG 场景指标

RAG（Retrieval-Augmented Generation）评测不能只看最终回答，还要拆开看检索和生成。

### 检索命中率

看相关文档是否被召回。

常见指标：

- Recall@k
- Precision@k
- MRR
- nDCG

如果检索阶段没有找出正确资料，后面的生成模型再强也容易答错。

### 答案忠实性

看答案是否真的来自检索到的资料，而不是模型自己编。

常见问题：

- 引用了资料里没有的结论
- 把多个文档的信息错误拼接
- 引用位置正确但解释错误
- 没有资料依据却给出肯定回答

### 引用准确性

如果答案带引用，需要看引用是否支撑对应句子。

好的引用应该满足：

- 引用文档确实包含该信息
- 引用位置足够具体
- 答案没有夸大原文含义
- 多个引用之间没有互相矛盾

## 6. Agent 场景指标

Agent 类任务更关注“能不能把事做完”。

### 工具调用准确率

看模型是否选择正确工具，并填对参数。

常见错误：

- 该查数据库却调用搜索
- 参数名写错
- 时间范围错误
- 忘记使用工具，直接猜答案
- 工具结果已经返回，但模型没有正确使用

### 任务完成率

衡量 Agent 是否完成用户目标。

例如：

- 是否成功订票
- 是否正确生成报表
- 是否完成代码修改并通过测试
- 是否把多步骤流程执行到最后

任务完成率比单步回答准确率更贴近 Agent 的真实价值。

### 轨迹质量

看中间过程是否合理。

需要关注：

- 是否有无效工具调用
- 是否重复调用同一个工具
- 是否走进死循环
- 是否能根据观察结果调整计划
- 是否能在失败后恢复

## 7. 业务评测指标

最终还要回到业务效果。

不同业务会有不同指标，例如：

- 客服：解决率、转人工率、用户满意度、平均处理时长
- 编程助手：补全采纳率、PR 修复率、测试通过率
- 搜索问答：答案点击率、追问率、引用点击率
- 内容生成：人工修改比例、审核通过率、生产耗时
- 数据分析：SQL 正确率、图表正确率、结论可解释性

通用榜单只能作为参考，真正选模型时最好构造一套自己的小型评测集。

## 8. 一个实用评测框架

可以把评测拆成四层：

| 层级 | 关注点 | 示例指标 |
|------|--------|----------|
| 基础能力 | 模型会不会 | Accuracy、Pass@k、F1、Win Rate |
| 可靠性 | 回答靠不靠谱 | 幻觉率、事实正确性、引用准确性 |
| 工程性能 | 能不能稳定上线 | TTFT、TPOT、吞吐、成本、格式稳定性 |
| 业务效果 | 对业务有没有用 | 任务完成率、满意度、转化率、人工修改比例 |

简单说：

> 大模型评测不是问“哪个模型分数最高”，而是问“在我的任务、成本、延迟、安全要求下，哪个模型最合适”。
